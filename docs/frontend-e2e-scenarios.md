# 프론트엔드 배선 후 E2E 테스트 시나리오

**실행할 목표 명세이며, 테스트 통과 보고서가 아니다.** 현재 API 계약과 시드 보존 원칙을 기준으로 갱신한다.

대상은 `../pulsemetry-frontend`의 로그인·개요·팀·구성원·설정 화면이다.
Playwright 테스트 코드는 프론트 레포에 작성하고 실제 Spring API와 로컬 PostgreSQL·ClickHouse를 연결한다.
화면 조작 → API 요청 → 저장/집계 → 재조회 → 화면 반영을 검증한다.

## 기준과 범위

- API 필드·상태 코드: [Enrollment 서버 명세](enrollment-server-spec.md), [Dashboard 서버 명세](dashboard-server-spec.md).
- 시드와 실행 절차: [개발용 시드](../tools/dev-seed/README.md).
- 레포 간 기준: [대시보드 계약](../../docs/contracts/dashboard-api.md).
  허브 문서는 아직 골격이고 프론트·대시보드 구현 상태가 반영되지 않았다. 이 문서는 새 계약을 확정하지 않는다.
- 현재 프론트의 `docs/api/`는 화면의 요청서다. 메일 발송, 역할, 좌석 회수 등은 이번 작업에서 합의한 아래 범위를 따른다.

백엔드는 조직 ID·이메일·비밀번호로 로그인한다. 프론트 개발 화면은 시드 이메일 어댑터를 사용할 수 있으며 실제 IdP SSO는 아니다.
관리자(owner/admin)만 대시보드 API에 접근하고, 초대 API는 코드 발급 방식이다. 초대 UI 배선은 이번 범위에서 제외돼 있다.
벤더 계약은 수동 입력하며 실제 벤더의 좌석 변경·구독 해지·메일 발송은 실행하지 않는다.
원문 수집 선택은 저장하되 기존 설치로의 원격 정책 배포·알림 실행·보존 설정 변경은 비활성 상태를 검증한다.
텔레메트리 수집부터 적재까지의 E2E와 부하 시험은 별도다. DB에 직접 넣는 이 시드로 ETL 성능을 입증하지 않는다.

## 실행 전 통과해야 할 조건

1. 로그인·로그아웃·세션 갱신·현재 사용자 조회가 실제 API에 연결되어야 한다.
   현재 개발 화면은 이메일만 입력하고 Next의 `/api/dev/seed-login`을 거친다. 어댑터가 허용된 시드 조직 ID와 서버 측 개발 암호를 넣어 실제 백엔드 로그인·me를 호출한다.
   화면에 조직 ID·암호 입력을 새로 요구하지 않는다. 일반 이메일 도메인 탐색·IdP 왕복·운영 SSO 성공으로 해석하지 않는다.
2. 조회는 dashboard-api, 관리 명령과 인증은 enrollment-api에 Bearer 토큰을 붙여 직접 요청한다.
   허용된 프론트 origin에서 CORS가 성공해야 한다.
3. 조직·기간·검색 조건을 TanStack Query 키에 포함하고, 관리 명령 성공 후 관련 조회 캐시를 갱신한다.
4. 시드 검증과 두 서버의 기동이 성공하고, 인증된 실제 개요 조회까지 성공해야 한다.
5. 다음 미완료 사항을 해소해야 한다. 해결되지 않은 항목은 `blocked`이며 `passed`나 조용한 `skip`으로 처리하지 않는다.

| 확인 대상 | 기준 |
| --- | --- |
| 로그인·온보딩·개요·설정 | API 배선 코드가 있어도 실제 서버·DB 재조회까지 확인해야 통과 |
| 팀 분석·구성원·초대 UI | 서버 API 존재만으로 프론트 배선 완료를 간주하지 않음. 해당 화면 미연동은 blocked |
| 조직 ID·세션 | 로그인 응답의 실제 조직 ID 사용. 메모리 데모 조직을 혼합하지 않음 |
| A의 계약 | Claude·OpenAI 활성 좌석 계약, Copilot 만료 계약, Cursor 계약 미입력, 기존 기간 약정을 구분. 시험 쓰기는 별도로 만든 등록만 사용 |
| Storybook·단위/통합 테스트 | UI 오류·입력 상태 및 서버 규칙을 검증하는 별도 증거. 실제 시드 E2E 결과로 대체하지 않음 |

2026-09-28 서버 검증에서는 좌석 순회 오류 수정 후 계약 생성·수정·조회 테스트가 통과했다.
로컬 두 서버의 기동과 시드 계정 로그인, 온보딩·카탈로그·플랜·개요·설정 조회 200도 확인했다.
이는 브라우저 E2E 결과와 별개이며, 실행 환경에서는 위 선행 조건을 다시 확인한다.

## 데이터·시간·격리

`D`는 실행일이 아니라 **현재 DB에 적재된 시드의 기준일**이다. 프론트 `E2E_SEED_DATE`를 그 날짜에 맞추고
화면에서 **D-28부터 D-1까지, 종료일 포함**을 직접 선택한다. 새 시드 정의와 다르다고 기존 DB를 자동 초기화하지 않는다.
시드 준비는 Docker `dev-seed`의 init/apply/verify를 사용한다([시드 가이드](../tools/dev-seed/README.md)). `-PseedDate` 방식은 사용하지 않는다.
새 계약 시작일·JWT 만료는 실제 서버 시각 기준이다. 분석 조회 기준일 D와 구분한다.
예: D가 `2026-09-28`이면 `2026-08-31`~`2026-09-27`이다.
브라우저 시계만 바꿔 JWT 만료나 서버 계약 날짜 검증을 시험하지 않는다.

| 데이터 | 용도 | 고정 기대값 |
| --- | --- | --- |
| A: 정상 사용 조직 | 개요·팀·구성원 조회 | 56일 요청·세션 데이터. 건수와 비용은 적재 기준일의 `plan`/공개 fixture를 사용하고 최근 28일 활성 사용자는 8명 |
| B: 신규 조직 | 최초 로그인·온보딩 | 조직과 오너 한 명만 존재. manifest·수집 이력·팀·계약 없음 |
| C: 예외 데이터 조직 | 누락·미확인 모델·과거 사용 | 구성원 8명, 전체 이벤트 14·선택 기간 13, 계약 없음 |

`2026-09-29` 기준 새 A 시드는 전체 요청 7,181건, 최근 28일 요청 4,074건, 최근 가상 환산 비용 `283.87701946 USD`다.
다른 기준일은 요일 분포에 따라 수치가 달라진다. 기존 ready DB는 자동 갱신되지 않으므로 새 코드의 수치를 그대로 대입하지 않는다.

A의 현재 활성 관리자 2명·일반 구성원 10명과 초대 대기 2명을 구분한다. `로스터`가 활성 구성원만 세는지 등
응답 DTO의 정의대로 검증하고 화면의 서로 다른 카운트를 무조건 14로 맞추지 않는다.
A의 팀 이동 구성원은 `member2@seed-a.example.test`, 미배정 사용자는 `member9@seed-a.example.test`다.
`member10`은 최근 수신 이력은 있지만 사용 이벤트가 없고, `member11`은 선택 기간 이전 사용만 있다.

로그인 계정·조직 UUID·개발 암호는 시드 README를 사용한다. **일반 구성원 시드에는 로그인 암호가 없다.**
일반 구성원 인가 시험은 관리자 초대 → signup API로 시험 계정을 만든 뒤 로그인한다.
초대 만료 시험은 Docker `plan`의 만료 코드를 사용하고, 신규 가입 시험은 각 테스트가 발급한 별도 코드를 쓴다.

- 조회 묶음을 먼저 실행한 다음 변경 묶음을 실행한다. 변경은 A 조직의 시험용 자원에 한정한다.
- 변경 이름과 이메일에 실행 식별자를 붙인다. 예: `e2e-<runId>-team`, `e2e-<runId>@example.test`.
- 처음에는 `workers=1`로 실행한다. 고정 A/B/C 조직을 공유하면서 병렬 초기화하지 않는다.
- 테스트별 독립 브라우저 컨텍스트·세션을 사용한다. 회전하는 RT가 담긴 동일 storageState를 여러 worker가 공유하지 않는다.
- 현재 기본 실행 범위는 조회와 정리 가능한 쓰기다. 테스트에서 생성한 ID를 기록해 finally에서 해당 자원만 정리한다.
  등록 제품은 기존 목록에 없는 kind를 선택한다. 모두 등록돼 있으면 준비 불가로 보고하고 기존 등록을 삭제하지 않는다.
- 기존 A/B/C 초기화·기본 계약 수정·기본 구성원의 팀 변경은 자동 수행하지 않는다.
  B 온보딩 완료, 정책 판 변경, 가입처럼 원상 복원이 불가능한 흐름은 별도 테스트 DB 또는 승인된 초기화 범위가 필요하다.
- 제품·팀 삭제는 이력을 지우지 않으므로 정리 후 DB가 바이트 단위로 원본 시드와 같아지는 것은 아니다.
  Docker `verify`는 원본 시드 정합 검증이다. 사용자 변경이 있는 DB의 API E2E 실행 조건으로 무조건 강제하지 않는다.

## P0 — 배선 완료의 필수 조건

아래 표의 각 행이 한 시나리오다. 자원 준비를 API로 하더라도 **검증 대상 동작은 브라우저로 실행**한다.
인증·권한 경계의 상태 코드 확인은 Playwright의 API 요청을 보조 증거로 사용할 수 있다.

| ID | 화면·준비 | 사용자 행동 | 기대 결과 |
| --- | --- | --- | --- |
| AUTH-01 | 로그인, A owner | 시드 이메일 입력 후 회사 계정으로 계속 | 개발 어댑터가 실제 login·me 호출 후 200, A 세션으로 개요 조회 200. 가짜 토큰이나 목 응답 없음. 실제 SSO 검증으로 표시하지 않음 |
| AUTH-02 | 별도 API 컨텍스트, 잘못된 비밀번호 | 백엔드 login을 1회 호출 | 401, 토큰 미발급. 현재 이메일 전용 UI에는 암호 입력이 없으므로 API 인증 검증으로 분류 |
| AUTH-03 | 비로그인 새 컨텍스트 | `/overview`, `/teams`, `/members`, `/settings` 직접 접근 | 로그인 유도, 보호 데이터 미노출. 토큰 없는 API 요청은 401 |
| AUTH-04 | 로그인 완료 | 로그아웃 후 뒤로 가기·보호 URL 재접근 | 로그인 요구, 캐시의 조직 데이터가 다시 나타나지 않음. 로그아웃 세션의 기존 AT로 조회해도 401 |
| AUTH-05 | signup으로 만든 member | 로그인 후 대시보드 진입·관리 요청 | 접근 불가 안내, 해당 API 403, 데이터·관리 버튼 이용 불가 |
| AUTH-06 | A 관리자 로그인 | 요청 경로의 조직 ID만 B로 변경 | 404, B 데이터 미노출. A 토큰으로 B 팀 수정도 실패하고 B 값 유지 |
| AUTH-07 | A 로그인 → 로그아웃 | B 관리자로 로그인 | B 조직명·빈 상태만 표시, A 비용·멤버·팀이 잠깐이라도 나타나지 않음 |
| ONB-01 | manifest 없는 B 오너 로그인 | version 0으로 수집하지 않음 저장 → 재접속 | 로그인 200, 최초 manifest 생성, confirmed=true·collectRawContent=false, 벤더 단계 재개 |
| ONB-02 | 정책 저장된 B | 벤더만 등록하고 플랜·좌석·단가 생략 → 팀 단계 건너뛰고 완료 | contract=null인 벤더 유지, 완료 200, 재접속 시 온보딩 재요구 없음 |
| ONB-03 | 필수 조건 미충족 B | 정책 미선택 또는 벤더 미등록 상태에서 완료 요청 | 서버 409 onboarding_incomplete, 완료 시각 미저장. 프론트 버튼 조작 우회에도 동일 |
| ONB-04 | 기존 manifest가 있는 A | 원문 수집 변경 후 정책 조회 | 프롬프트·응답만 함께 변경, 다른 privacy 설정 유지. 기존 설치 적용 완료로 표시하지 않음 |
| CAT-01 | 벤더 선택 UI | 검색어 입력·다음 페이지 선택 | 서버 q/limit/cursor로 검색, 플랜 전체를 최초 목록에 싣지 않음 |
| CAT-02 | Claude 선택 | 플랜 목록 조회 → 다른 벤더 선택 | 해당 제품의 플랜만 표시, 이전 선택 초기화, 동일 벤더 재선택은 유효 캐시 재사용 |
| CAT-03 | 플랜 조회 중 벤더 변경 | 이전 응답을 지연시켜 새 응답 뒤 도착 | 이전 벤더의 플랜이 새 목록을 덮지 않음. 조회 실패 시 재시도 UI 제공 |
| OVER-01 | A, 고정 조회 기간 | 개요 열기 | 활성 사용자 8, API 비용은 적재 기준일의 시드 기대값과 일치. UI는 정해진 USD 자릿수로 반올림하며 원시 수치를 바꾸지 않음. 혼합 토큰 null을 0으로 표시하지 않음 |
| OVER-02 | A | 기간 변경 후 원래 기간 복귀 | API 날짜·시간대가 선택과 일치, 마지막 선택의 결과 표시. 이전 28일과 최근 28일의 요청·비용·활성 사용자가 구분됨 |
| OVER-03 | 새로 생성한 B | 개요 열기 | 200, `meta.dataState=never_observed`, `ingest.status=empty`. 빈 상태에서 예시 그래프·예시 비용을 표시하지 않음 |
| OVER-04 | C | 개요·모델 분포 열기 | 누락 비용/토큰을 0이나 NaN으로 바꾸지 않음. 알 수 없는 모델도 유실하지 않고 API가 반환한 항목/미확인 상태 표시 |

## Playwright 작성 규칙

1. 기존 `tests/browser`의 fixture/데모 테스트와 별개로 `tests/e2e`와 실제 API용 설정을 둔다.
   기존 테스트 통과를 실제 DB 연동 통과로 대체하지 않는다. 이 문서는 아직 해당 파일들을 만들지 않았다.
2. 정상 흐름은 `route.fulfill`로 API를 대체하지 않는다. 읽기·쓰기 요청이 실제 서버에 도착해야 한다.
   장애 주입은 `@fault` 묶음으로 구분하고 어떤 요청을 바꿨는지 보고서에 적는다.
3. 위 ID를 테스트 제목에 넣고 P0에는 `@p0`, 나머지에는 `@p1`을 붙인다.
   조회 `@read`, 변경 `@write`, 실제 만료 대기 `@slow`도 구분한다.
4. `getByRole`, `getByLabel`을 우선 사용한다. 차트의 접근 가능한 값이 없으면 필요한 범위만 testid를 추가한다.
   좌표·CSS 구조·화면 전체 스냅샷만으로 핵심 수치를 검증하지 않는다.
5. `waitForTimeout` 대신 응답과 화면 조건을 기다린다. `waitForResponse`는 클릭 전에 등록한다.
   API 200뿐 아니라 응답 수치, 화면 표시, 변경 후 실제 재조회까지 확인한다.
6. 조직 비용·사용자 수의 기대값은 시드 원천/검증 결과에서 가져온다.
   API와 UI가 둘 다 틀렸는데 같다는 이유로 통과하지 않도록 독립적인 고정 기대값을 함께 검증한다.
7. 변경 후 `page.reload()`와 독립 로그인 컨텍스트 재조회를 포함해 메모리 상태만 바뀐 경우를 잡는다.
8. 예상하지 않은 pageerror·API 4xx/5xx는 실패로 처리한다. 각 시나리오의 의도된 오류와 요청 취소는 명시적으로 구분한다.
9. 실패 시 screenshot·요청 경로/상태·requestId를 남긴다. 실제 인증 E2E는 토큰 응답을 보존하지 않도록 trace를 기본 off로 둔다.
   토큰·암호·초대 코드·storageState를 로그나 Git에 넣지 않는다. 별도 trace 수집은 비밀 제거·접근 제한을 검토한 경우에만 한다.
10. 첫 실행은 Chromium, workers=1, retries=0으로 실패를 확인한다.
    수정 후 관련 테스트와 P0 전체를 재실행한다. 재시도로만 통과한 테스트는 flaky로 따로 보고한다.

## 실행 순서와 완료 기준

1. 기존 DB와 D 확인 → 선행 조건 확인 → 서버·프론트 기동. DB 준비가 필요하면 시드 가이드의 보존 규칙을 따른다.
2. AUTH-01로 실제 브라우저 로그인·CORS·인증 조회를 먼저 확인한다.
3. A/B/C 조회 → 정리 가능한 관리 변경 → 해당 범위의 충돌·장애·세션 검증 순서로 진행한다. 별도 DB가 필요한 시나리오는 분리한다.
4. 생성한 시험 자원만 정리하고 기존 등록·계약 및 B/C가 의도치 않게 바뀌지 않았는지 확인한다.
5. 보고서에 커밋/작업 트리 상태, D, 실행 주소, 브라우저, 각 ID의 passed/failed/blocked와 증거를 적는다.

현재 승인된 실행 범위(시드 보존 조회·정리 가능한 쓰기)의 완료와 전체 화면 배선 완료를 구분한다.
**전체 배선 완료는 P0 전부 통과하고, 조직 격리·데이터 정확성·저장 지속성에 실패가 없는 경우다.**
P1 결과도 빠짐없이 보고한다. 전체 E2E 완료는 계획된 P0/P1이 모두 통과한 경우에만 선언한다.
미구현 기능을 skip으로 제외한 초록색 결과는 완료가 아니다.
성능은 화면 조작부터 최종 데이터 표시까지와 API 응답 시간을 함께 기록하되,
로컬 1회 결과로 운영 성능이나 ETL 처리량을 판정하지 않는다.

## 이후 실행을 지시할 때 사용할 문구

> `pulsemetry-backend/docs/frontend-e2e-scenarios.md`를 목표 명세로 사용해
> `pulsemetry-frontend`의 실제 API E2E를 Playwright로 구현하고 실행해줘.
> 기존 로컬 Spring·PostgreSQL·ClickHouse와 적재된 A/B/C 기준일을 먼저 확인해.
> 기존 시드를 초기화하지 말고 조회와 정리 가능한 쓰기부터 진행해.
> 시험용 자원은 기존 등록과 겹치지 않게 만들고 생성한 ID만 정리해.
> 정상 흐름을 목 응답으로 대체하지 말고, 미배선·별도 DB 필요·실행 실패를 구분해서 보고해.
> 프론트가 예상하는 값에 맞추려고 백엔드 응답이나 기대값을 바꾸지 마.
