# 0006. 데이터 파이프라인을 백엔드 프로젝트에 병합한다.

## Status
Rejected — 파이프라인 전체 병합은 채택하지 않는다. 실제 방향은 collector 만 이 저장소로 가져와 인증 계층을 심는 것이며([ADR 0007](0007-인증-계층으로-spring-security-사용.md)), 나머지 앱은 `ai-telemetry-pipeline` 에 남는다. RDB(enrollment) 스키마 소유권은 병합과 무관하게 [ADR 0009](0009-enrollment-스키마-native-enum-채택.md) 가 이 저장소의 Flyway 로 확정했고, ClickHouse 스키마 소유권은 파이프라인에 남는다. 전체 이관은 Python·Kotlin 성능 비교 목적의 재논의 여지만 남긴다.

## Context
현재 otel 데이터 수집 및 가공 파이프라인이 다른 레포지토리에서 Python 으로 관리되고 있다.
데스크탑 인증 api와 대시보드 api는 이 레포지토리에서 Kotlin/Spring 으로 관리한다.
데이터 파이프라인과 api가 동일한 데이터베이스에 접근한다.

즉 같은 개념의 스키마가 두 저장소에 두 벌로 존재하고, 한쪽을 바꾸면 다른 쪽은 조용히 어긋난다.

## Decision
- otel 데이터 파이프라인을 백엔드 프로젝트로 병합하고, 애플리케이션 모듈로 편입한다.
- 배포 단위는 그대로 분리된 채 남는다. 수집·가공 워크로드와 API 워크로드는 성격이 다르므로 각각 독립적으로 배포하고 확장한다.
  - 파이프라인의 실행 환경 파일(collector 설정, compose, 로컬용 mock 컨테이너 정의)도 함께 옮긴다.
- 병합 형태는 Kotlin/Spring 재작성이다. Python 소스를 그대로 옮기지 않는다.
  저장소만 합치고 언어가 갈라져 있으면 없애려는 중복(영속성 코드 두 벌)이 그대로 남는다.
- 영속성 코드는 `:libs:` 의 공유 모듈에서 가져다 쓴다.
  파이프라인이 조직 정보를 조회하려고 쿼리를 새로 쓰지 않는다.
- 마찬가지로 ClickHouse 스키마의 소유권도 이 저장소로 가져온다.

## Alternatives
### A. 현재처럼 파이프라인을 다른 프로젝트로 분리한다.
- 장점: 언어와 런타임을 워크로드에 맞게 각자 고를 수 있다. 이미 동작하는 코드가 있어 추가 비용이 0이다. 저장소가 작아 빌드와 CI 가 가볍고, 파이프라인 변경이 API 배포에 영향을 주지 않는다.
- 단점: 조직 스키마가 두 벌로 존재한다. 스키마 변경이 두 저장소에 걸치면 PR도 둘로 갈라진다.
- 탈락 이유: 두 프로젝트가 같은 데이터베이스 스키마를 정의하므로, 책임 분리의 원칙을 지키기 힘들다.

### B. 저장소는 분리한 채, 영속성 코드와 스키마를 별도 아티팩트로 배포해 공유한다.
- 장점: 스키마 정의를 한곳에서 관리하면서도 저장소 분리의 이점(가벼운 빌드, 독립적인 배포 주기)를 유지한다. 언어도 각자 유지할 수 있다.
- 단점: 아티팩트에 버전이 생기고, 결국 사람이 버전 호환을 관리하게 된다. 언어가 다르므로 스키마를 언어별로 두 번 표현하게 된다.
- 탈락 이유: 해결하려는 문제(정의가 갈라짐)를 버전 호환 문제로 바꿔 놓을 뿐이다. 지금 단계에서 레지스트리 운영과 버전 관리를 떠안을 만한 이득이 없다.

## Consequences/Tradeoffs
### Positive
- db 레이어를 공통 모듈로 분리하여 중복 코드를 줄인다.
- 두 프로젝트 간 db 레이어의 불일치를 고민하지 않아도 된다.
- 스키마 변경과 그것을 사용하는 파이프라인, API 변경을 하나의 PR 에서 함께 다룰 수 있다. 어느 버전끼리 맞는지 기억할 필요가 없다.
- ClickHouse 테이블의 DDL 이 마이그레이션 파일로 드러나므로, 적재하는 쪽(파이프라인)과 읽는 쪽(대시보드 API)이 같은 정의를 보고 리뷰할 수 있다.
- 언어와 빌드가 하나로 통일되어 CI, 분석, 테스트 도구를 한 벌만 유지하면 된다.

### Negative
- 동작하는 Python 코드 약 3,800 라인을 재작성해야 한다.
  - **재작성을 막아 줄 테스트가 없다** — enrichment·diagnostics 테스트 962 라인은
    PROJ-40(`0893613`, 2026-08-17)에서 삭제됐다. 회귀 방지는 재작성 전에
    특성화 테스트(characterization test)를 새로 확보하는 것을 전제로 한다.
- 이 리팩토링은 동작이 미묘하게 달라질 위험을 동반한다.
- OTLP 수신과 정규화는 API 요청량과 비교가 되지 않는 처리량의 워크로드다.
  - 배포와 JVM 튜닝은 멀티모듈 구조가 격리한다. 각각이 별도 인프라에 배포되므로 이쪽 튜닝이 API 서버에 영향을 주지 않는다.
- 저장소가 커지고 전체 빌드 시간이 늘어난다. 공유 모듈을 바꿀 때 회귀를 확인할 범위에 파이프라인이 추가된다.

## Follow-up
- 이 결정은 두 레포의 코드·계약에 걸리므로 문서 허브(`soma-376/docs/adr/`)로 이관한다.
  허브 ADR 이 머지되면 이 파일은 링크 stub 으로 줄인다 (허브 반영은 팀 합의 후 착수 — PROJ-80).
- collector 이관으로 새로 생기는 배포 단위는 `:apps:telemetry-ingest` 하나이며,
  collector config 의 소유권이 함께 이동한다.
- ClickHouse 스키마 소유권은 `ai-telemetry-pipeline` 에 남는다.
