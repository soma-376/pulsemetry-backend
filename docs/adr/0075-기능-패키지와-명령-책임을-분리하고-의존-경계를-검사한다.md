# 0075. 기능 패키지와 명령 책임을 분리하고 의존 경계를 검사한다

## Status

Accepted — PROJ-306의 구현 기준이다. ADR 0008의 도메인·모듈 동일시와 관리자 앱 신설 시 분할 예고, ADR 0014의 실행 단계 사이 데이터 타입 간선, ADR 0016의 ArchUnit 도입 유보만 부분 대체한다. ADR 0010의 단계 경계·네임스페이스, ADR 0011의 앱 조립 원칙은 유지하고 자동 검사로 강제한다.

## Context

Backend `origin/develop 52689f9`에서 Dashboard의 화면 코드가 `api`·`analytics`에 흩어져 있고, Enrollment의 `ManagementStore.command`는 HTTP 경로를 분해해 업무를 선택한다. SQL·검증·응답 조립·트랜잭션·멱등 재시도가 같은 클래스에 있다. 또한 적재가 보강 결과 타입만 사용해도 `telemetry-persistence → telemetry-enricher → enrollment-persistence`로 JPA·Flyway가 따라온다.

참고 프로젝트 `gdsc-server df95475`의 기능별 API·application·domain 배치는 탐색성과 행위 배치의 참고다. 폴더를 복제하거나 그 프로젝트의 Modulith 이벤트 재시도·영속화를 가져오지 않는다. 새 비동기 흐름이나 배포 단위를 만들 이유가 없다.

## Decision

### 1. 기능·도메인·모듈·배포 단위를 구분한다

- 기능 패키지는 업무 흐름을 찾는 단위다. Dashboard의 `overview`, `team`, `member`, `settings`, `alert`에 컨트롤러·서비스·응답을 함께 둔다. 좌석 조회는 이를 제공하는 `member`·`settings` 기능에서 찾고, 독립 진입점인 `ingest`, `operation`, `catalog`는 해당 기능에 둔다.
- `analytics`는 여러 기능이 실제 공유하는 집계·값·조회 입력만 갖는다. `snapshot`, `authentication`, `authorization`, `request`, `error`, `store`, `source`, `cache`, `config`는 이름대로 공유 책임을 유지한다. 공유 패키지는 기능의 내부 구현에 의존하지 않는다. 공유 집계의 단방향 의존을 유지하고 HTTP 응답 전용 타입이 역류하면 분리한다.
- Enrollment는 `team`, `member`, `invitation`, `installation`, `policy`, `vendor`, `seat`에서 API와 명시적 명령 실행을 찾는다. 작은 기능은 빈 레이어·형식적인 포트를 만들지 않는다. 공통 명령 실행 관문은 인증된 행위자·트랜잭션·재시도만 조정하며 업무 선택을 하지 않는다.
- domain은 상태 전이·검증을 맡는다. application은 업무 순서와 원자성을 조정하고 persistence의 명시적 저장·조회 연산을 호출한다. API가 요청 파싱·HTTP 상태·헤더·JSON 표현을 소유한다. SQL·JPA와 마이그레이션은 persistence에 남긴다. 전체 엔티티를 별도 도메인 모델로 복제하지 않는다.
- 도메인은 일관성이 필요한 업무 규칙의 경계이며 테이블 묶음·Gradle 모듈·화면과 동일하지 않다. Gradle 모듈은 컴파일·의존 격리를 위한 단위다. enrollment 스키마의 저장 연산·DDL 소유권은 유지한다. 기능 패키지를 추가했다고 관리자 앱이나 별도 스키마를 만들지 않는다.
- 실행 앱 다섯 개와 collector·adapter·enricher·persistence 단계 모듈은 유지한다. 앱 간 의존, 라이브러리의 앱 의존, 모듈 순환은 금지한다.

### 2. 명령의 동작과 재시도 호환성을 보존한다

- 기능 API는 구체적인 유스케이스를 호출한다. HTTP 메서드·경로 문자열을 저장소로 넘겨 분기하지 않는다.
- 조직 활성 행의 `FOR UPDATE` → 행위자 역할 `FOR SHARE` 재검증 → 멱등 응답 조회 → 업무 실행·outbox 기록 → 암호화 응답 저장을 같은 트랜잭션에서 수행한다. 조직별 직렬화, 낙관 버전, 실패 시 전체 롤백을 유지한다.
- 기존 `management_commands.command_path` 값은 이미 저장된 재시도 식별자다. API 경계에서 기존 문자열을 호환 키로 만들되 그 문자열을 실행 분기에 사용하지 않는다. 원본 JSON의 canonical hash, 24시간 만료, AES-GCM·AAD의 tenant/actor/path/key 순서를 유지한다. 요청 파싱은 재시도 관문 안의 실행 시점에 수행해 기존 재시도 판정 순서를 보존한다.
- API 응답·상태·ETag·Location·Cache-Control, 오류 코드·권한 판정, outbox의 공급자 호출 시점, enroll 트랜잭션을 유지한다. 기존 `SeatRules` 및 좌석 원장 규칙을 재사용한다.

### 3. 공유 타입은 실제 소비와 격리 근거가 있을 때 분리한다

- `:libs:telemetry-model`은 adapter·enricher·persistence가 함께 사용하는 관측 값과 보강 결과, 값의 표현 규칙을 소유한다. 실행 정규화기·보강기·JPA·Boot·Kafka 클라이언트를 포함하지 않는다. 적재는 이 모델을 참조하고 보강 실행을 끌어오지 않는다. 단계 순서의 조립은 여전히 ingest 앱이 한다.
- `:libs:enrollment-domain`은 Enrollment 저장 연산·명령과 Dashboard가 실제 공유하는 오류·좌석·계약 등의 순수 규칙과 값을 소유한다. HTTP·SQL·JPA·Spring 의존은 금지한다. 공유가 없는 유스케이스를 이 모듈로 올리지 않는다.
- `api(project(...))`는 공개 시그니처에 나타나는 타입에만 사용하고 빌드 파일에 이유를 적는다. 실행 구현을 타입의 운반 수단으로 노출하지 않는다.
- 라이브러리의 main 의존에는 Boot starter를 두지 않는다. enrollment-persistence는 JPA·Spring Data·JDBC API만 사용한다. JPA/JDBC/Flyway 자동설정과 드라이버는 필요한 실행 앱·도구가 명시적으로 선택한다. 테스트 fixture의 테스트 의존은 별개다.

### 4. 경계 검사는 기존 build의 일부다

- ArchUnit은 각 앱·라이브러리의 실제 main 바이트코드로 기능 내부 접근, 기능 순환, domain의 HTTP·영속성 의존, 라이브러리의 앱 의존, 금지된 Spring 스테레오타입을 검사한다. 위반 전체를 무시하거나 기존 위반을 동결하지 않는다. 테스트 fixture는 main 검사에서 제외한다.
- Gradle 검사는 project 간선의 방향·순환과 라이브러리 runtimeClasspath의 starter 유입을 검사하고 `check`/`build`에 연결한다. telemetry-model·telemetry-persistence의 클래스패스에서 JPA·Flyway·단계 실행 구현이 따라오지 않는 것도 확인한다.
- Dashboard → Enrollment → 공유 타입 순서로 구조 검사와 회귀 검증을 함께 적용한다. 기존 HTTP·OTLP·Kafka·동시성·롤백·outbox 테스트를 유지하고 각 앱의 조립과 bootJar를 검증한다.

## Constraints

HTTP·OTLP·Kafka 외부 계약, 설정 키, protobuf·JSON 형식, DB 스키마·마이그레이션, 원본 보존 삭제 권한·순서는 변경하지 않는다. Modulith 런타임·이벤트 영속화, 새 비동기 업무, 운영 배포·데이터 재처리는 범위 밖이다. 기존 namespace의 어순을 일괄 변경하지 않는다.

Infra의 자원·IAM·환경변수·이미지 target·포트·명령은 유지한다. 새 Gradle 모듈의 build 파일은 Backend Dockerfile의 빌드 입력 목록에 추가해야 한다. 구조 검사는 기존 PR CI의 `./gradlew build`에서 실행되므로 배포 워크플로우나 계약 원본 checkout을 바꾸지 않는다. 실제 변경 영향과 검증 제한은 구현 보고서에 기록한다.

## Alternatives Considered

### A. 레이어 패키지 이름만 바꾼다

변경량은 작지만 HTTP 경로에 의한 영속성 업무 분기와 타입으로 인한 자동설정 유입을 해결하지 못한다.

### B. 기능마다 Gradle 모듈과 별도 도메인 엔티티를 만든다

컴파일 격리는 강하지만 현재 배포·원자성 경계를 불필요하게 쪼개고 변환 비용과 인터페이스만 늘린다.

### C. Modulith 이벤트로 기능을 연결한다

참고 프로젝트와 비슷해지지만 동기 트랜잭션·outbox·재시도의 의미를 바꾼다. 이 티켓의 목표가 아니다.

## Consequences/Tradeoffs

### Positive

- 기능별 진입점과 업무 순서를 찾을 수 있고 영속성이 HTTP로 업무를 고르지 않는다.
- 공유 값 소비자가 실행 구현과 자동설정을 받지 않는다.
- 리뷰로만 지키던 경계가 CI에서 실패로 드러난다.

### Negative

- 실제 공유 모듈 두 개와 앱의 명시 조립 코드가 늘어난다.
- 기존 멱등 기록과의 호환 때문에 내부 재시도 키에 과거 HTTP 형태가 남는다. 이 문자열은 공개 라우팅과 함께 회귀 검증해야 한다.
- 코드 이동이 많아 파일별 diff보다 기능별 회귀·의존 그래프·앱 조립 검증을 함께 검토해야 한다.

## Acceptance Criteria

PROJ-306의 완료 기준을 따른다. 기능별 회귀·구조 검사와 전체 Gradle build 결과, 각 앱 조립 결과, Infra·배포 입력 영향, 환경 제한을 `docs/feature-packages-verification.md`에 기록한다.
