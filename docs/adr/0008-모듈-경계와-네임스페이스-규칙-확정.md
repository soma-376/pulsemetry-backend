# 0008. 모듈 경계와 패키지 네임스페이스 규칙을 확정한다.

## Status
Accepted

## Context

[ADR 0002](0002-멀티모듈-프로젝트-구축.md)는 멀티모듈 구조를 채택하면서 경계 결정을 유보했다.
"구체적인 모듈 이름과 경계는 각 서버 구현에 착수하는 시점에 확정한다"가 그 문장이다.
`:apps:enrollment-api` 가 구현되면서 그 시점이 도래했다.

동시에 모듈이 늘어날 것이 예고되어 있다.
[ADR 0006](0006-데이터-파이프라인을-백엔드-프로젝트에-병합.md)은 OTel 수집·가공 파이프라인을 애플리케이션 모듈로 편입시키고 ClickHouse 스키마의 소유권까지 가져온다.
[ADR 0007](0007-인증-계층으로-spring-security-사용.md)은 웹 대시보드를 전제하며, 관리자가 조직 정보를 등록하고 초대하는 플로우와
수집 파이프라인·API 가 같은 인증 코드를 공유해야 한다는 요구를 함께 적고 있다.
0007 은 Accepted 이고 0006 은 아직 Proposed 지만, 어느 쪽이든 `:apps` 와 `:libs` 에 모듈이 추가된다.

그리고 그 모듈들은 HTTP 만으로 깨어나지 않는다. 파이프라인은 OTLP 를 받고,
수집과 가공은 처리량 성격이 달라 나뉠 수 있으며, 그렇게 나뉘면 그 사이는 이벤트다.

### 무엇을 어느 모듈이 쓰는지가 정해져 있지 않다

현재 스키마는 테이블 14개다(`libs/enrollment-persistence/src/main/resources/db/migration/V1__enrollment_schema.sql`).
그중 JPA 엔티티가 있는 것은 8개뿐이다.

- `contracts`·`contract_term_commitments`·`contract_token_discounts`·`contract_memberships` 네 개는 **쓰는 코드가 없다.**
  마이그레이션의 "enrollment API 는 이 테이블들을 쓰지 않는다" 주석이 직접 적어 두었다.
  주인이 정해지지 않은 테이블 묶음이 이미 존재한다. `teams`·`team_memberships` 도 엔티티가 없다.
- 반대로 `InvitationAdminService.create()` 는 한 서비스에서 구성원과 초대 양쪽에 쓴다 —
  member INSERT 는 `createInvitedMember()` 안의 `members.saveAndFlush()` 로
  (`PROPAGATION_REQUIRES_NEW` 분리 트랜잭션), 초대는 `invitations.save()` 로 저장한다.
  트랜잭션은 분리돼 있으나 **한 서비스가 두 도메인에 쓴다는 사실은 같다.**
  구성원과 초대는 마이그레이션에서도 다른 섹션("조직과 구성원", "초대와 설치")이다.

모듈을 나누는 기준이 없으면 이 상태가 굳는다. 새 모듈의 책임이 "무엇을 쓰는가"가 아니라 "누가 먼저 만들었는가"로 정해진다.

### 현재 두 모듈의 패키지 규칙은 비대칭이며 어디에도 적혀 있지 않다

```text
:apps:enrollment-api          →  com.team376.pulsemetry.enrollment
:libs:enrollment-persistence  →  com.team376.pulsemetry.persistence.enrollment
```

라이브러리에는 역할 세그먼트(`persistence`)가 있고 앱에는 없다.
세 번째 모듈을 만드는 사람은 이 두 사례를 역추적해 규칙을 스스로 유추해야 하는데,
두 사례의 형태가 다르므로 유추 결과가 하나로 수렴하지 않는다.

그리고 **패키지가 겹쳐도 빌드는 실패하지 않는다.** 두 모듈이 같은 패키지를 공급해도 컴파일도 되고 기동도 된다.
어느 클래스가 로드되는지가 클래스패스 순서에 따라 정해질 뿐이다. 컴파일러가 잡아주지 않는 종류의 실수다.

### 공유할 자리가 없어 이미 중복이 발생했다

`PostgresContainerConfig.kt` 가 두 모듈의 테스트 소스에 거의 같은 내용으로 존재한다.

```text
apps/enrollment-api/src/test/kotlin/com/team376/pulsemetry/support/PostgresContainerConfig.kt          (26줄)
libs/enrollment-persistence/src/test/kotlin/.../enrollment/support/PostgresContainerConfig.kt          (28줄)
```

Testcontainers 컨테이너를 빈으로 등록하는 같은 설정이고, 모듈 간에 테스트 지원 코드를 공유할 수단이 없어서 복사됐다.
모듈이 늘어나면 그 수만큼 늘어난다.

## Decision

### 1. 도메인 경계는 쓰기 소유권으로 정한다

> **한 테이블의 쓰기 로직은 한 모듈이 소유한다. 읽는 모듈은 몇 개든 좋다.**
> 도메인이란 한 모듈이 쓰기를 독점하는 테이블 묶음이다.

[ADR 0004](0004-Flyway-마이그레이션과-varchar-CHECK-스키마-관리.md)가 "스키마의 진실원은 Flyway 마이그레이션"으로 못박았으므로,
소유권 질문은 **"이 테이블의 `CREATE TABLE` 이 어느 모듈 아래에 있는가"** 라는 파일 경로 질문으로 환원된다. 리뷰에서 검증할 수 있다.

소유의 단위는 앱이 아니라 **모듈**이다. 여러 앱이 같은 쓰기 모듈을 가져다 써도 된다.
ADR 0006 이 "파이프라인이 조직 정보를 조회하려고 쿼리를 새로 쓰지 않는다"고 한 것을 쓰기까지 확장한 것이다.

이 기준으로 현재 스키마와 예고된 워크로드를 나누면 도메인은 다섯이다.

| 도메인 | 테이블 | 쓰기 소유 |
|---|---|---|
| directory | `tenants`, `members`, `teams`, `team_memberships` | 관리자 API (신규) |
| enrollment | `invitations`, `installations`, `installation_credentials`, `telemetry_tokens`, `installation_manifest_assignments` | `enrollment-api` (현행) |
| policy | `manifests` | 관리자 API (신규) |
| contract | `contracts`, `contract_term_commitments`, `contract_token_discounts`, `contract_memberships` | 관리자 API (신규) |
| telemetry | ClickHouse fact 테이블 | 수집 파이프라인 단독 (신규) |

`installation_manifest_assignments` 는 policy 가 아니라 **enrollment 소유**다.
PK 가 `(installation_id, manifest_id)` 이고 `applied_at` 을 가진다 — 정책의 정의가 아니라 installation 의 배포 상태이며,
installation 과 함께 죽는다. 현재 마이그레이션은 이것을 "manifest 배포" 섹션에 두어 소유가 policy 로 읽힌다.

**도메인 경계가 아닌 것**

| 아닌 것 | 실제로는 |
|---|---|
| 인바운드 프로토콜 (HTTP·OTLP·이벤트·MCP) | 배포 단위를 가르는 축 |
| 읽기 전용 화면 | 읽기 모델. 자기 테이블이 없으면 도메인이 아니다 |
| 화면의 축 (조직별·부서별·비용별) | 같은 테이블을 group by 하는 방향 |
| 횡단 관심사 (인증·로깅) | 공유 라이브러리 |

**두 모듈이 같은 테이블에 쓰려 할 때**는 셋 중 하나로 해결한다.
① 합친다(경계가 실은 없었다) ② 쪼갠다(행 또는 컬럼의 실제 소유자가 다르다)
③ 소유 모듈이 제공하는 연산을 통해서만 쓴다(리포지토리 직접 접근 금지). 대부분 ③이다.

### 2. 패키지는 한 모듈만 공급한다

어떤 패키지도 두 모듈이 공급하지 않는다. 모듈마다 고유한 루트 패키지를 갖는다.

```text
:apps:enrollment-api          →  com.team376.pulsemetry.enrollment
:apps:admin-api               →  com.team376.pulsemetry.admin
:apps:telemetry-ingest        →  com.team376.pulsemetry.telemetry
:apps:dashboard-api           →  com.team376.pulsemetry.dashboard
:libs:enrollment-persistence  →  com.team376.pulsemetry.persistence.enrollment
:libs:telemetry-persistence   →  com.team376.pulsemetry.persistence.telemetry
:libs:security                →  com.team376.pulsemetry.security
```

- **애플리케이션 모듈** `:apps:<context>-<inbound>` → `com.team376.pulsemetry.<context>`.
  `<inbound>` 는 그 배포 단위가 무엇에 의해 깨어나는지를 나타낸다 — `api`(HTTP)·`ingest`(OTLP)·`worker`(이벤트·스케줄)·`mcp`.
  접미사는 배포 단위를 구별할 뿐 패키지에는 반영하지 않는다.
- **한 컨텍스트에 배포 단위가 둘 이상이 되면** 그때 `com.team376.pulsemetry.<context>.<inbound>` 로 한 단계 내린다.
  기계적인 rename 이므로 그 시점까지 미뤄도 비용이 늘지 않는다.
  수집과 가공을 나누어 그 사이를 이벤트로 잇는 구성이 이 조건을 만드는 가장 유력한 경로다.
- **라이브러리 모듈** `:libs:<context>-<role>` → `com.team376.pulsemetry.<role>.<context>`.
  컨텍스트에 속하지 않는 횡단 모듈은 **`:libs:<role>`** → `com.team376.pulsemetry.<role>` 형식을 쓴다.
  ADR 0007 이 요구하는 인증 계층의 자리가 여기다.

모든 모듈은 `com.team376.pulsemetry` 아래에 둔다.
Spring Boot 는 `@SpringBootApplication` 이 붙은 클래스의 패키지를 기준으로 컴포넌트·엔티티·리포지토리를 찾는다.
현재 `PulsemetryApplication` 이 `com.team376.pulsemetry` 에 있고 영속성 모듈이 그 하위에 있어서
`@EntityScan`·`@EnableJpaRepositories` 없이 동작한다. 이 규칙은 그 동작을 우연이 아니라 전제로 만든다.

애플리케이션 모듈의 메인 클래스만 예외로 루트(`com.team376.pulsemetry`)에 둔다. 스캔의 출발점이어야 하기 때문이다.
앱이 여럿이 되면 모든 앱 모듈이 이 루트 패키지를 공급하게 되지만, 규칙 3이 앱 사이의 의존을 금지하므로
두 앱이 한 클래스패스에 함께 오르는 일이 없다. 따라서 이 예외는 규칙 2를 깨뜨리지 않는다.

### 3. 의존 방향

- `:apps:*` 는 `:libs:*` 에만 의존한다.
- `:apps:*` 끼리는 의존하지 않는다.
- `:libs:*` 는 `:apps:*` 에 의존하지 않는다.
- `:libs:*` 사이의 의존은 단방향만 허용한다. 도메인 성격의 모듈이 싱크가 된다.

앱 사이에 협력이 필요할 때 선택지는 둘이고, 서로 다른 것을 위한 것이다.

- **런타임 협력은 이벤트로 한다.** 한 앱의 처리 결과를 다른 앱이 이어받아야 할 때다.
- **`:libs:` 승격은 정의가 갈라지면 안 되는 코드에만 쓴다.** 계약·스키마·정책처럼 두 벌이 되면 조용히 어긋나는 것들이다.

이 구분이 없으면 협력이 필요할 때마다 코드를 `:libs:` 로 밀어 올리는 압력이 생기고, 공유 모듈이 무엇이든 담는 자루가 된다.

`project()` 간선은 기본적으로 `implementation` 으로 선언한다.
`api()` 는 그 타입을 소비자가 직접 다루는 것이 모듈의 계약일 때만 쓰고, 이유를 빌드 스크립트에 주석으로 남긴다.
현행 `:libs:enrollment-persistence` 가 JPA·JDBC 를 `api()` 로 노출하는 것이 그 선례다 —
엔티티와 리포지토리는 앱 코드가 직접 다루는 타입이기 때문이다. 메시징 클라이언트는 계약이 아니므로 `implementation` 으로 감춘다.

**아웃바운드 기술이 둘 이상이면 라이브러리를 기술별로 나눈다** (`-persistence` / `-messaging`).
Spring Boot 의 자동설정은 클래스패스에 무엇이 있는지만 보고 발동한다.
한 모듈이 JPA 와 메시징 클라이언트를 함께 끌고 오면, 메시징을 쓰지 않는 앱에도 그 자동설정이 걸린다.
기동은 되지만 아무도 쓰지 않는 설정이 조용히 살아 있게 된다.

### 4. 이벤트 발행 소유권과 계약

- **이벤트 발행 소유권은 테이블 쓰기 소유권을 따른다.** 한 이벤트의 발행자는 하나다.
  둘 이상이 같은 이벤트를 발행하면 소비자가 출처를 구분할 수 없고, 그 이벤트의 순서를 보장할 주체도 사라진다.
- **이벤트 payload 타입은 `:libs:<context>-event` 가 소유하고 발행자와 소비자가 함께 참조한다.**
  ADR 0002 가 "스키마 정의가 두 벌로 갈라지는 것을 구조적으로 막는다"고 한 것과 같은 문제이며, 이쪽이 **더 위험하다** —
  JPA 는 `ddl-auto: validate`(`apps/enrollment-api/src/main/resources/application.yaml`)로
  엔티티와 스키마가 어긋나면 기동을 막는다. 이벤트 payload 에는 그런 검증이 없다.
  발행자가 필드를 바꿔도 소비자는 역직렬화가 실패하는 런타임에야 안다.
- **이 모듈만은 규칙 5의 "두 번째 소비자" 조건을 미룰 수 없다.**
  이벤트는 정의상 발행자와 소비자가 있으므로, 첫 이벤트를 만드는 시점에 이미 소비자가 둘이다.
- 트랜잭션과 발행을 함께 묶기 위해 아웃박스를 쓴다면, 아웃박스 테이블은 Flyway 마이그레이션이 소유하고(ADR 0004),
  릴레이는 별도 배포 단위가 될 수 있다. 그 경우 한 컨텍스트에 배포 단위가 둘이 되어 규칙 2의 내림 조항이 발동한다.

### 5. 모듈 승격은 두 번째 소비자가 실제로 생겼을 때 한다

코드를 `:libs:` 로 옮기는 것은 두 번째 실사용 소비자가 실제로 생긴 시점에 한다. 예측만으로 쪼개지 않는다.
ADR 0002 의 "경계가 불분명한 단계에서는 모듈을 잘게 쪼개지 않는 편이 안전하다"를 그대로 잇는다.

**예정된 승격은 `:libs:enrollment-persistence` 의 분할이다.**
규칙 1의 도메인 다섯 중 directory·policy·contract 는 쓰기 소유자가 아직 없고, 그 셋의 테이블이 지금 이 모듈 하나에 들어 있다.

- **트리거: 관리자 API 앱의 첫 커밋.** 그 앱이 directory·policy·contract 의 쓰기를 가져가는 시점이다.
- 같은 시점에 Postgres 스키마 이름도 함께 본다. 지금은 네 도메인이 전부 `enrollment` 스키마에 들어 있어 이름이 사실과 다르다.
  어차피 다음 마이그레이션을 쓸 시점이므로 그때가 가장 싸다.
- 같은 시점에 `InvitationAdminService.createInvitedMember()` 의 `members.saveAndFlush()` 를 directory 모듈이 제공하는 구성원 등록 연산 호출로 바꾼다(규칙 1의 해결책 ③).

### 6. 모듈 간 테스트 지원 코드는 `java-test-fixtures` 로 공유한다

테스트 전용 공유 모듈을 새로 만들지 않는다.
공유가 필요한 테스트 지원 코드는 그것을 소유한 모듈의 `testFixtures` 소스셋에 두고,
소비 모듈이 `testImplementation(testFixtures(project(":libs:...")))` 로 가져간다.

### 7. `:apps` 와 `:libs` 는 빌드 스크립트를 갖지 않는다

둘은 모듈을 담는 컨테이너일 뿐이다. 현행 루트 `build.gradle.kts` 가 `buildFile.exists()` 로 이미 건너뛰고 있으며, 이를 규칙으로 고정한다.

### 규칙을 적용하면 나오는 트리

규칙 1·2·3·5 를 함께 적용하면 어떤 구조가 나오는지 예시로 적는다.
**만들 모듈의 목록이 아니다** — Alternative C 가 기각한 것이 바로 그것이며, 규칙 5 가 승격 시점을 트리거로 묶어 두었다.
아래 셋 중 지금 존재하는 것은 첫 번째뿐이다.

**현재**

```text
pulsemetry-backend
├── apps/
│   └── enrollment-api/              com.team376.pulsemetry.enrollment
└── libs/
    └── enrollment-persistence/      com.team376.pulsemetry.persistence.enrollment
                                     └ 14 테이블 (directory 4 · enrollment 5 · policy 1 · contract 4)
```

**읽기 전용 앱이 하나 추가될 때** — 대시보드의 지표군 API 를 예로 든다.

```text
pulsemetry-backend
├── apps/
│   ├── enrollment-api/              com.team376.pulsemetry.enrollment
│   └── dashboard-api/               com.team376.pulsemetry.dashboard      ← 신규 배포 단위
│       └── src/main/kotlin/com/team376/pulsemetry/dashboard/
│           ├── usage/               지표군 · 사용량
│           ├── cost/                지표군 · 비용
│           ├── adoption/            지표군 · 도입률
│           ├── privacy/             지표군 · 정책 준수
│           ├── query/               지표군 공용 — Postgres × ClickHouse 애플리케이션 조인
│           └── config/
└── libs/
    ├── enrollment-persistence/      (그대로 — 아직 쪼개지지 않는다)
    ├── telemetry-persistence/       com.team376.pulsemetry.persistence.telemetry   ← ClickHouse
    └── security/                    com.team376.pulsemetry.security                ← ADR 0007
```

- **지표군은 모듈이 아니라 패키지다.** 규칙 1의 "도메인 경계가 아닌 것" 표가 읽기 전용 화면을 읽기 모델로,
  화면의 축(조직별·부서별·비용별)을 같은 테이블을 group by 하는 방향으로 판정한다. 지표군이 열 개가 되어도 `:libs:` 로 올라가지 않는다.
- **이 시점에 `:libs:enrollment-persistence` 는 쪼개지지 않는다.** 대시보드는 읽기만 하고 규칙 1이 읽는 모듈의 수를 제한하지 않으므로
  쓰기 소유자가 그대로다. 분할 트리거는 여전히 규칙 5의 관리자 API 앱 첫 커밋이다.
- 대시보드를 관리자 API 와 다른 배포 단위로 두는 근거는 인바운드가 아니라 **워크로드 성격**이다. 둘 다 HTTP 지만 확장 축이 다르다.
  ADR 0006 이 수집·가공과 API 를 "성격이 다르므로 각각 독립적으로 배포하고 확장한다"고 한 것과 같은 이유다.

**관리자 API 앱까지 온 뒤** — 규칙 5의 트리거가 당겨진 상태.

```text
pulsemetry-backend
├── apps/
│   ├── enrollment-api/              com.team376.pulsemetry.enrollment
│   ├── admin-api/                   com.team376.pulsemetry.admin
│   ├── telemetry-ingest/            com.team376.pulsemetry.telemetry
│   └── dashboard-api/               com.team376.pulsemetry.dashboard
└── libs/
    ├── directory-persistence/       …persistence.directory    tenants·members·teams·team_memberships
    ├── enrollment-persistence/      …persistence.enrollment   invitations·installations·credentials·tokens·assignments
    ├── policy-persistence/          …persistence.policy       manifests
    ├── contract-persistence/        …persistence.contract     contracts·…
    ├── telemetry-persistence/       …persistence.telemetry    ClickHouse fact
    └── security/                    …security
```

의존은 전부 아래 방향 한 겹이다 (규칙 3 — 앱끼리는 의존하지 않는다).

```text
dashboard-api    ──▶ directory · enrollment · policy · telemetry-persistence · security   (읽기만)
admin-api        ──▶ directory · policy · contract-persistence · security                 (쓰기 소유)
enrollment-api   ──▶ enrollment(쓰기) · directory·policy(읽기) · security
telemetry-ingest ──▶ telemetry(쓰기) · directory(읽기) · security
```

라이브러리 이름은 규칙 2의 `:libs:<context>-<role>` 을 도메인 표에 기계적으로 적용한 결과다.
분할을 네 갈래로 할지는 그 시점에 실제 소비자를 보고 정한다 — 규칙 5가 예측이 아니라 두 번째 소비자를 기준으로 삼기 때문이다.
`<role>` 로 확정된 것은 `-persistence`·`-event` 와 횡단 모듈 `security` 뿐이다. 아래 트리의 `-query` 처럼 그 밖의 역할 이름은 필요한 시점에 정한다.

**한 컨텍스트에 배포 단위가 둘이 될 때** — 대시보드에 MCP 가 붙는 경우를 예로 든다.

MCP 도 HTTP/SSE 로 뜨므로 대시보드 앱에 어댑터 패키지(`dashboard/mcp/`)로 얹을 수 있다.
그 경우 배포 단위가 하나이므로 규칙 2의 내림 조항은 발동하지 않고 모듈도 패키지도 그대로다.
**배포 단위를 나누기로 하면** 그때 내림이 발동한다.

```text
apps/
├── dashboard-api/                   com.team376.pulsemetry.dashboard.api    ← 한 단계 내려간다
│   └── …/dashboard/api/
│       └── usage/  cost/  adoption/  privacy/        HTTP 표현 계층
└── dashboard-mcp/                   com.team376.pulsemetry.dashboard.mcp
    └── …/dashboard/mcp/
        ├── tool/                                     MCP tool 정의
        └── config/

libs/
├── dashboard-query/                 com.team376.pulsemetry.query.dashboard  ← 승격
│   └── 지표군 조회 로직 · Postgres × ClickHouse 애플리케이션 조인
└── (directory · enrollment · policy · telemetry-persistence · security)
```

```text
dashboard-api ──▶ dashboard-query ──▶ directory · enrollment · policy · telemetry-persistence
dashboard-mcp ──▶ dashboard-query ──┘
```

- **지표군 조회가 `:libs:` 로 올라가는 것이 이 갈래의 핵심이다.** 규칙 3이 앱끼리의 의존을 금지하므로
  두 배포 단위가 같은 조회를 쓰려면 그 길밖에 없다. 이때는 규칙 5의 두 번째 소비자가 예측이 아니라 실제로 생긴 상태다.
  지표군 자체는 여전히 모듈이 아니라 그 라이브러리 안의 패키지다.
- 나눌지 말지는 규칙 2가 아니라 워크로드가 정한다. MCP 는 LLM 이 호출하므로 빈도가 예측되지 않고,
  인증 주체도 사람의 브라우저 세션이 아니라 에이전트 토큰이다. 확장 축과 진입점 정책이 화면 트래픽과 다르면 나눈다.
- 규칙 2는 내림을 "기계적인 rename 이므로 그 시점까지 미뤄도 비용이 늘지 않는다"고 적었다.
  따라서 어댑터 패키지로 시작했다가 나중에 나누어도 규칙에 어긋나지 않는다.
- 규칙 2가 내림의 유력한 경로로 든 것은 수집과 가공을 이벤트로 잇는 구성이었다.
  이 갈래는 이벤트 없이 같은 읽기 로직을 두 프로토콜로 노출하는 경우이며, 조건은 같지만 성격이 다른 두 번째 경로다.

**구조가 실제로 바뀌는 지점**

- 대시보드가 **자기 테이블을 갖는 순간** 읽기 모델이 아니라 도메인이 된다. 롤업·사전집계 테이블, 저장된 대시보드나 즐겨찾기,
  알림 임계값 중 하나만 생겨도 발동한다. 그때 `:libs:dashboard-persistence` 가 생기고 쓰기 소유가 대시보드 앱으로 넘어간다.
- 그전까지 실제로 걸리는 것은 **저장소가 둘이라는 사실**이다. 지표군은 대개 조직·설치(Postgres)와 fact(ClickHouse)를 함께 봐야 하는데
  저장소가 달라 SQL 조인이 성립하지 않으므로 애플리케이션 조인이 된다. 규칙 3의 "아웃바운드 기술이 둘 이상이면 라이브러리를 기술별로 나눈다"가
  `telemetry-persistence` 를 별도 모듈로 만드는 지점이 여기다.

## Alternatives

### A. 규칙을 적지 않고 지금처럼 관습으로 둔다
- 장점: 지금 비용이 0이다. 현재 두 모듈 사이에 실제 충돌도 없다.
- 단점: 규칙이 사람의 기억에만 있다. 게다가 현행 두 사례가 비대칭이라 유추 가능한 규칙 자체가 하나가 아니다.
- 탈락 이유: ADR 0002 는 "모듈 간 의존 방향이 빌드 스크립트에 명시되므로, 허용하지 않은 참조를 컴파일 타임에 차단할 수 있다"를 채택 근거의 하나로 삼았다.
  그러나 **패키지 이름이 겹치는 것도, 두 모듈이 같은 테이블에 쓰는 것도 컴파일 타임에 차단되지 않는다.**
  ADR 0002 가 기대한 안전장치가 닿지 않는 영역이고, 이 영역은 규칙을 글로 적는 것 말고 막을 방법이 없다.
  주인 없는 테이블 네 개와 두 섹션에 걸쳐 쓰는 서비스가 이미 그 결과다.

### B. 도메인·엔티티·영속성·애플리케이션 4단으로 지금 전면 재편한다
- 장점: 도메인 타입이 프레임워크에서 분리되고, 의존 규칙 위반이 컴파일 에러가 된다. 영속성 기술을 바꿀 때 도메인이 흔들리지 않는다.
- 단점: 현재 도메인 타입은 JPA 엔티티 8개가 전부다. 이를 도메인 모델과 엔티티로 이중화하면 양방향 매핑 코드만으로 현재 영속성 모듈 전체(594줄)에 육박한다.
  `enroll` 의 절차는 이미 명세로 순서까지 고정되어 있어, 인바운드 포트 인터페이스가 추가로 고정해 줄 계약이 없다.
- 탈락 이유: ADR 0002 가 "모듈 경계를 잘못 나누면 이후 재조정 비용이 발생한다"고 판단했고 그 판단은 아직 유효하다.
  두 번째 소비자가 없는 상태에서는 도메인과 영속성의 경계가 어디여야 하는지 알아낼 근거가 없다.
  경계를 모르는 채로 4단을 세우면, 나중에 재조정할 대상이 두 배가 된다.

### C. 앞으로 필요할 모듈을 지금 미리 만들어 둔다
- 장점: 나중에 코드를 옮길 일이 없다.
- 단점: 규칙 1이 정한 도메인 다섯 중 셋은 아직 쓰는 코드가 없다. 빈 모듈만 생긴다.
- 탈락 이유: B 와 같은 논리다. 지금 확정할 수 있는 것은 모듈이 추가될 때 지켜야 할 규칙이지 모듈 자체가 아니다.
  규칙을 먼저 정해 두면 승격 시점의 작업이 "옮기기" 하나로 줄어든다.

## Consequences/Tradeoffs

### Positive
- 새 모듈의 책임을 "무엇을 쓰는가"로 정할 수 있다. 주인 없는 테이블이 생기면 도메인 표에서 바로 드러난다.
- 소유권 위반이 파일 경로 질문으로 환원되므로 리뷰에서 검증할 수 있다.
- 인바운드가 늘어나도(HTTP·OTLP·이벤트·스케줄·MCP) 패키지 규칙이 답을 준다. 그때마다 규칙을 다시 논의하지 않는다.
- 이벤트 계약의 소유가 정해져, 검증 장치가 없는 payload 드리프트를 코드 공유로 막는다.
- "지금 쪼갤까"를 매번 다시 논의하지 않는다. 승격 트리거가 관리자 API 앱의 첫 커밋으로 명시된다.
- `java-test-fixtures` 로 `PostgresContainerConfig` 중복이 해소되고, 모듈이 늘어도 한 벌로 유지된다.
- 모든 모듈이 `com.team376.pulsemetry` 아래에 있다는 규칙이 명시되면, 지금 암묵적으로 동작하는 컴포넌트 스캔이 우연이 아니라 의도된 설계가 된다.

### Negative
- 규칙을 검증할 자동 수단이 없다. 패키지 충돌도 쓰기 소유권 위반도 컴파일이 아니라 리뷰에서만 걸린다.
  이 ADR 의 실효성은 리뷰 규율에 달려 있다.
- 도메인 다섯 중 셋을 쓰는 코드가 없는 상태로 선언한다. 실제 구현이 시작되면 경계가 달라질 수 있다.
- 애플리케이션과 라이브러리의 패키지 규칙이 비대칭인 채로 확정된다.
  한 컨텍스트에 배포 단위가 둘 이상이 되면 그때 한 단계 내리는 작업이 필요하다.
- `testFixtures` 는 소비 모듈의 테스트 클래스패스를 늘리고, 라이브러리 모듈에 소스셋이 하나 더 생긴다.
- 승격을 미루는 선택이므로, 관리자 API 앱을 만드는 시점에 영속성 모듈 분할과 스키마 이름 정리가 한꺼번에 발생한다.
  그 비용을 없애는 것이 아니라 필요한 시점까지 미루는 것이다.

## Follow-up
- **완료** — 일시 제거됐던 `.github/workflows/build.yml` 은 복구됐다. `Dockerfile` 의 "테스트는 CI 의 build 잡이 이미 돌린다"는 주석은 다시 사실이다.
  ADR 0002 의 Follow-up 중 "모듈별 빌드와 테스트를 수행하는 CI 워크플로를 추가한다" 항목도 이것으로 닫혔다.
- **완료** — `PostgresContainerConfig` 는 `:libs:enrollment-persistence` 의 `testFixtures` 로 옮겨졌고,
  앱 테스트의 `com.team376.pulsemetry.support` 는 제거되어 support 패키지가 한 갈래로 정리됐다.
- 마이그레이션의 `installation_manifest_assignments` 는 소유를 DDL 위 주석으로 명시하는 것으로 닫았다.
  **DDL 을 "초대와 설치" 섹션으로 옮기는 것은 불가능하다** — `fk_installation_manifest_assignments_manifest` 가
  `manifests(id)` 를 참조하므로 생성 순서를 앞당기면 FK 대상이 아직 없어 마이그레이션이 실패한다.
  섹션 위치는 생성 순서 제약이지 소유의 표시가 아니며, 소유가 규칙 1과 일치한다는 사실은 주석이 담는다.
  **주석을 더하면서 V1 파일이 바뀌었으므로 Flyway 체크섬도 바뀌었다.** V1 을 적용한 환경이 남아 있으면 `flyway repair`
  (또는 로컬이라면 볼륨 삭제)가 필요하다. (Testcontainers 는 매번 새 인스턴스를 띄우므로 테스트는 영향받지 않는다.)
- **완료** — manifest 의 유효 범위(배정 단위)는 **tenant 로 확정**해 충돌을 닫았다(PROJ-80).
  `ux_manifests_tenant_active`(V2)의 불변식이 유지되고, ADR 0007 의 Context 는
  tenant 내 manifest 개정 시나리오로 다시 썼다 — 부서 단위 전제와의 양립 불가 문제가 해소됐다.
  부서 단위 배정은 `teams` 가 실제로 쓰이게 될 때 별도 개정 ADR 로 다시 연다.
  결정 자체는 크로스레포이므로 [허브 ADR 0002](../../../docs/adr/0002-manifest-assignment-unit-is-tenant.md) 가 남겼다.
- 세 번째 모듈이 추가되는 시점에 규칙 1·2·3 을 ArchUnit 등으로 테스트에 고정할지 재검토한다. 그 전에는 Gradle 모듈 경계로 충분하다.
- **완료** — 애플리케이션 모듈의 plain `jar` 는 비활성화됐다(`apps/enrollment-api/build.gradle.kts` 의 `tasks.jar { enabled = false }`).
  `Dockerfile` 의 `-plain.jar` 걸러내기 로직도 없어졌다 — `build/libs` 에는 bootJar 산출물 하나뿐이다.
- 규칙 2의 `<inbound>` 축은 한 컨텍스트에 **같은 인바운드를 가진 배포 단위가 둘 이상**이면 성립하지 않는다.
  수집·마스킹·변환·보강을 각각 배포하고 그 사이를 이벤트로 잇는 구성이 그 경우다 —
  마스킹·변환·보강이 모두 이벤트로 깨어나므로 규칙대로면 셋 다 `:apps:telemetry-worker` 가 되어
  같은 규칙의 "어떤 패키지도 두 모듈이 공급하지 않는다"와 충돌한다.
  접미사를 인바운드가 아니라 파이프라인 단계로 바꾸는 개정을 검토한다.
  같은 시점에 수집 단계가 이 저장소가 작성하는 애플리케이션 모듈인지, OTel Collector 를 설정으로 띄우는 것인지도 확정한다.
  후자라면 그 단계는 `:apps:` 에 들어가지 않는다.
- 규칙 1의 도메인 표는 telemetry 의 쓰기 소유를 "수집 파이프라인 단독"으로 적었다.
  파이프라인이 배포 단위 여럿으로 나뉘면 그중 하나를 지목해야
  "한 테이블의 쓰기 로직은 한 모듈이 소유한다"가 성립한다. 나누는 시점에 소유 모듈을 표에 확정한다.
- 이벤트 토픽의 계약을 별도 ADR 로 정한다. 규칙 4는 payload 타입의 소유만 정했고
  토픽 이름·파티션 키·스키마 진화와 호환성 정책은 정해진 바 없다.
  ADR 0004 가 DB 스키마에 대해 "진실원은 Flyway 마이그레이션"을 못박은 것과 같은 수준의 결정이 토픽에는 아직 없으며,
  규칙 4가 지적한 대로 이벤트 payload 에는 `ddl-auto: validate` 같은 기동 시 검증도 없다.
