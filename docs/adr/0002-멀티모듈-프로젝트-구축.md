# 0002. 멀티모듈 프로젝트를 구축한다.

## Status
Accepted

## Context
데스크탑 애플리케이션용 인증 서버와 웹 대시보드 서버가 데이터베이스를 공유한다. (clickhouse 및 postgres)
나중에 우리 서비스 mcp 구축 또는 데이터 수집 파이프라인 또한 병합될 가능성이 있다.
각 모듈은 서로 다른 인프라로 배포될 예정이다.

## Decision
- 단일 Gradle 루트 아래 여러 모듈을 두는 멀티모듈 구조를 채택한다.
- 데이터베이스 접근 코드와 도메인 모델처럼 여러 서버가 함께 쓰는 코드는 공유 모듈로 분리하고, 인증 서버와 웹 대시보드 서버가 이 모듈에 의존하도록 한다. 두 서버가 같은 저장소를 바라보므로 스키마 정의가 두 벌로 갈라지는 것을 구조적으로 막는다.
- 배포 단위가 되는 서버는 각각 독립적인 애플리케이션 모듈로 둔다. 모듈마다 실행 가능한 산출물을 따로 빌드하여 서로 다른 인프라에 배포한다.
- 향후 mcp 서버나 데이터 수집 파이프라인이 추가되면 동일한 규칙에 따라 애플리케이션 모듈로 편입한다.
- 구체적인 모듈 이름과 경계는 각 서버 구현에 착수하는 시점에 확정한다.

## Alternatives
### A. Monolith
- 장점: 빌드 스크립트가 하나뿐이라 초기 설정 비용이 없고, 코드 분리를 고민할 필요가 없어 개발 속도를 내기 쉽다. 공유 코드를 모듈로 떼어낼 필요 없이 같은 소스 트리에서 바로 참조할 수 있다.
- 단점: 산출물이 하나이므로 인증 서버만 배포하거나 대시보드 서버만 스케일 아웃하는 것이 불가능하다. 코드 경계가 컨벤션에만 의존하므로 시간이 지날수록 관심사가 뒤섞이기 쉽다.
- 탈락 이유: 각 모듈을 서로 다른 인프라에 배포한다는 요구사항을 만족할 수 없다. 향후 mcp 서버나 데이터 수집 파이프라인이 합류하면 성격이 다른 워크로드가 한 프로세스에 묶이는 문제도 커진다.

### B. Modular Monolith
- 장점: 코드 경계를 나누어 관심사를 분리하면서도 배포와 운영은 단일 산출물로 단순하게 유지할 수 있다. 분산 시스템의 복잡도(네트워크 호출, 부분 장애)를 떠안지 않아도 된다.
- 단점: 논리적으로는 분리되어 있어도 배포 단위는 여전히 하나이므로, 특정 영역만 독립적으로 배포하거나 확장할 수 없다.
- 탈락 이유: 코드 경계를 나눈다는 점은 채택안과 같지만 배포 단위가 하나로 묶인다. 각 모듈이 서로 다른 인프라로 배포될 예정이라는 전제와 맞지 않아 탈락시켰다.

## Consequences/Tradeoffs
### Positive
- 데이터베이스 스키마와 도메인 모델을 공유 모듈 한 곳에서 관리하므로, 인증 서버와 대시보드 서버 사이에 정의가 어긋나는 문제를 방지할 수 있다.
- 모듈별로 독립적으로 빌드·배포할 수 있어 각 서버를 성격에 맞는 인프라에 배치하고 개별적으로 확장할 수 있다.
- 모듈 간 의존 방향이 빌드 스크립트에 명시되므로, 허용하지 않은 참조를 컴파일 타임에 차단할 수 있다.
- 단일 저장소이므로 공유 모듈 변경과 그것을 사용하는 서버의 변경을 하나의 커밋·PR에서 함께 다룰 수 있다. 저장소를 서버별로 나누는 방식과 달리 버전 호환을 신경 쓰지 않아도 된다.
- mcp 서버나 데이터 수집 파이프라인을 추가할 때 모듈만 추가하면 되므로 확장 비용이 낮다.

### Negative
- 모듈마다 빌드 스크립트를 관리해야 하므로 초기 설정 비용과 플러그인·의존성 버전 관리 부담이 생긴다.
- 전체 빌드 시간이 단일 모듈일 때보다 늘어난다.
- 공유 모듈을 변경하면 이에 의존하는 모든 애플리케이션 모듈이 영향을 받으므로, 변경의 파급 범위가 넓고 회귀 확인 비용이 크다.
- 모듈 경계를 잘못 나누면 이후 재조정 비용이 발생한다.
  - 경계가 불분명한 단계에서는 모듈을 잘게 쪼개지 않는 편이 안전하다고 판단했다.

## Follow-up
- `settings.gradle.kts`에 모듈을 `include`하고, 루트 `build.gradle.kts`는 공통 설정만 담당하도록 정리한다. Kotlin·Spring Boot 플러그인은 루트에서 `apply false`로 선언하고 각 모듈에서 필요한 것만 적용한다.
- 플러그인과 라이브러리 버전을 한곳에서 관리하도록 Gradle 버전 카탈로그(`gradle/libs.versions.toml`) 도입을 검토한다.
- 현재 `src/` 아래에 있는 `PulsemetryApplication`은 첫 애플리케이션 모듈을 만드는 시점에 해당 모듈로 옮긴다.
- 모듈별 빌드와 테스트를 수행하는 CI 워크플로를 추가한다. 현재 `.github/workflows`에는 PR 보조 워크플로만 있고 빌드 검증이 없다.
