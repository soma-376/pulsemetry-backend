# 0031. 개발 시드는 Docker에서만 실행한다

## Status

Accepted — ADR 0027의 서버 자동 시드·공유 코어 분리, ADR 0004·0025·0028·0030의 호스트 수동 실행 및 서버 초기화 경로를 대체한다. 로컬 DB 제한, 완료 데이터 보존, 명시적 초기화, 스키마 소유권은 유지한다.

[ADR 0032](0032-온보딩-완료는-조직에-저장하고-시드는-ABC만-유지한다.md)가 일부 결정을 대체한다. 기본 설치 조직 시드를 제거하고 A/B/C만 유지한다. Docker 실행과 인증 키 준비는 유지한다.

## Context

개발 DB 준비를 Docker로 통일한다. 서버와 도구가 시드 코어를 공유할 필요가 없어졌으며,
서버 시작 여부에 따라 초기 데이터가 달라지는 실행 경로를 제거한다. 변경 범위는 이 저장소의 개발 환경이다.

## Decision

- 생성·적재·검증 코드와 테스트를 `:tools:dev-seed` 하나로 합치고 `:libs:dev-seed-core`를 제거한다.
- 서버의 기본 설치 시더와 A/B/C 시더, 시드 의존성 및 자동 실행 설정을 제거한다.
- Compose의 일회성 프로그램이 기존 소유 모듈의 마이그레이션, 기본 설치 데이터, A/B/C, 대시보드 DB 계정을 준비한다.
- 기본 설치 조직의 고정 ID, manifest, 초대 코드와 기존 데이터 보존 규칙을 유지한다.
- 기본 명령은 `init`이다. `plan`, `apply`, `verify`, `reset`도 같은 컨테이너 진입점에서 실행한다.
  수동 `plan`·`apply`·`verify`는 기준일을 명시하고, `reset`은 선택한 A/B/C 조직에만 적용한다.
- DB 연결은 Compose 표식과 고정 서비스 주소·개발 계정만 사용한다. 호스트 DB 연결과 Docker 소켓 조회를 제거한다.
- 인증 키도 Compose 초기화가 준비해 `build/dev-auth`에 저장한다. 기존 키는 보존한다.
  호스트 바인드 디렉터리에 쓸 수 있도록 개발 Compose의 일회성 컨테이너만 root로 실행한다.
  Dockerfile의 기본 사용자와 운영 앱 이미지는 그대로 유지한다.
- 로컬 실행 스크립트를 제거한다. 각 앱의 `application-local.yaml`이 개발 계정·키 경로·서버 설정을 제공한다.
  서버는 `bootRun --args='--spring.profiles.active=local'`로 실행한다. 키는 없으면 기동이 실패하며 자동 생성하지 않는다.
- `tools`는 개발용 실행 프로그램의 분류다. 추가 도구를 전제로 새 모듈을 만들지 않는다.

## Alternatives Considered

공유 코어를 유지하면 소비자가 하나인 내부 구현에 모듈 경계만 남는다.
SQL이나 다른 언어로 시드를 다시 작성하면 기존 검증과 데이터 정의를 재사용하기 어렵다.
서버 자동 시드를 유지하면 Docker로 실행을 통일하려는 요구와 맞지 않는다.

## Consequences/Tradeoffs

### Positive

서버 클래스패스에서 시드를 제거하고 개발 데이터의 실행 주체를 하나로 고정한다.
기존 Kotlin 로직과 테스트, 마이그레이션 리소스를 재사용한다.

### Negative

개발 데이터를 준비하려면 Docker 이미지 빌드가 필요하다. 서버 기동만으로는 데이터가 생성되지 않는다.
기존 Gradle 시드 명령 사용자는 Compose 명령으로 바꿔야 한다.
개발 인증 키는 호스트 바인드 디렉터리에 남으므로 DB 볼륨 초기화와 별도로 관리한다.
local 프로필은 Gradle bootRun의 앱 디렉터리를 기준으로 키를 찾는다. 다른 작업 디렉터리에서는 키 디렉터리를 명시해야 한다.
