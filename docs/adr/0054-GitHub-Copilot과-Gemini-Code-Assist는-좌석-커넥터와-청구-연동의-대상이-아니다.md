# 0054. GitHub Copilot과 Gemini Code Assist는 좌석 커넥터와 청구 연동의 대상이 아니다

## Status

Accepted — [ADR 0048](0048-좌석-원장은-벤더-계정별-배정-이력이고-연결된-등록-제품에서는-커넥터-동기화가-권위를-갖는다.md)의 커넥터 목록과 GitHub 로그인 계정 종류,
[ADR 0049](0049-좌석-회수와-복원은-미리보기에-묶어-실행하고-벤더-제어가-없으면-관리자-조치-확인으로-끝난다.md)의 구현한 해제·복원 커넥터,
[ADR 0050](0050-실제-청구액은-벤더-비용-지출-API의-정산-기간별-누계만-원천으로-하고-기간이-다른-벤더를-더하지-않는다.md)의 청구 커넥터 후속을 개정한다.

## Context

ADR 0048은 벤더 문서가 좌석 API를 준 네 제품에 커넥터를 두었다 — Claude Enterprise, Cursor Enterprise, GitHub Copilot, Gemini Code Assist.
Copilot과 Gemini 커넥터는 이 저장소에 구현돼 있었다.

- Copilot 좌석은 GitHub 로그인만 준다. 그래서 계정 종류 `github_login`이 생겼고, 그 좌석은 구성원에 자동으로 잇지 못해 관리자가 이어야 했다.
- Copilot 해제는 주기 말 효력(해제 예정)이고, 복원(재배정)은 Copilot과 Gemini만 구현돼 있었다. Gemini는 서비스 계정 키로 토큰을 받는 별도 인증 경로를 가졌다.
- 두 제품의 연결 화면 요구는 프론트의 목 데이터에서 왔다. 제품 담당자는 두 벤더의 연동을 지원 범위에서 뺐다 — 실제 조직의 연결 요구와 실계정 검증 계획이 없다.
- 두 제품은 카탈로그(`V10__vendor_catalog.sql`의 `copilot_*`·`gemini_*` 플랜)와 개발 시드의 등록 제품·계약으로는 이미 있었다. 이것은 커넥터와 별개다.

정하지 않으면 생기는 일: 검증 계획이 없는 커넥터와 인증 경로가 배포에 남아 벤더 자격증명을 받는다. 화면은 지원하지 않는 연결을 제공하는 것처럼 보인다.

## Decision

- **GitHub Copilot과 Gemini Code Assist에는 커넥터가 없다.** 좌석 목록·해제·복원·청구 어느 것도 벤더 API로 하지 않는다.
  두 커넥터 설명과 구현, Gemini 토큰 교환 경로, 설정 `pulsemetry.vendor-connections.gemini-token-url`·`base-urls.copilot`·`base-urls.gemini`를 두지 않는다.
- **카탈로그와 등록은 그대로다.** 두 제품을 등록할 수 있고 계약을 적을 수 있다. 커넥터가 없는 플랜이므로 좌석 원장은 관리자의 기록(수동·CSV)이 권위다(ADR 0048 §3의 1행).
  두 제품에 연결을 만드는 요청은 다른 커넥터 없는 플랜과 같이 거부한다.
- **계정 종류는 이메일 하나다.** API는 `github_login`을 만들지도 받지도 않는다. 기존 마이그레이션의 `account_kind` CHECK에 남은 값은 고치지 않는다 —
  적용된 Flyway 마이그레이션을 고치면 체크섬이 바뀌어 이미 적용한 DB가 기동을 거부한다(ADR 0004의 진실원이 그 파일들이다). 그 값으로 쓰는 경로는 없다.
- **해제를 구현한 커넥터는 Claude Enterprise·Cursor Enterprise 둘이고, 복원을 구현한 커넥터는 없다.** 복원은 모두 관리자 조치 확인으로 끝난다(ADR 0049 §2).
  해제 예정·수락 대기 같은 벤더 제어 결과를 원장에 반영하는 규칙(ADR 0049)과 커넥터 포트의 복원 자리는 그대로 둔다 — 벤더 문서가 근거를 준 복원(Claude Enterprise 재초대)을
  구현하면 같은 규칙을 쓴다.
- **청구 커넥터는 Claude Enterprise·Cursor Enterprise 그대로다.** Copilot·Gemini 청구 경로는 찾지 않는다.

## Alternatives

### A. 커넥터를 남기고 설정으로 끈다
- 장점: 다시 켤 때 코드가 있다.
- 단점: 검증하지 않은 인증 경로와 계정 종류가 배포물에 남는다. 꺼진 기능의 테스트와 문서를 계속 유지해야 한다.
- 탈락 이유: 지원 계획이 없는 기능을 숨긴 채 들고 있지 않는다.

### B. 카탈로그 행까지 지운다
- 장점: 두 제품이 화면 어디에도 없다.
- 단점: 등록·계약·관측 매핑(ADR 0044)과 개발 시드가 함께 바뀐다. 이미 등록한 조직의 계약 기록이 고아가 된다. 새 마이그레이션이 필요하다.
- 탈락 이유: 커넥터를 걷는 결정과 제품을 받지 않는 결정은 다르다. 앞의 것만 정한다.

## Consequences/Tradeoffs

### Positive
- 커넥터 두 개와 별도 인증 경로(서비스 계정 키 서명)가 사라져 검증 대상과 자격증명 종류가 줄어든다.
- 계정 키가 이메일 하나라 구성원 자동 연결이 모든 좌석에 적용된다.

### Negative
- 두 제품을 쓰는 조직은 좌석을 직접 기록해야 한다. 벤더가 바꾼 좌석을 서버가 알지 못한다.
- 커넥터로 복원하는 제품이 없어 복원은 모두 관리자가 벤더 콘솔에서 하고 확인한다.

## Follow-up
- 두 벤더를 다시 지원하려면 새 ADR로 이 결정을 개정하고 커넥터를 실계정 검증 계획과 함께 더한다.
