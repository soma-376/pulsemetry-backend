# 0005. 설치 부트스트랩을 서버가 생성한 스크립트로 제공하고 바이너리를 화이트리스트로 서빙한다.

## Status
Accepted

## Context
사용자는 개발자이지만 이 도구의 설치는 업무가 아니다.
관리자가 초대 메일에 붙여 준 한 줄을 터미널에 붙여넣는 것으로 끝나야 한다.

```
irm 'https://get.../windows?code=ABCD-EFGH-JKMN' | iex
curl -fsSL 'https://get.../unix?code=ABCD-EFGH-JKMN' | sh
```

이 형태에는 두 가지 위험이 붙어 있다.

첫째, **초대 코드가 스크립트 본문에 문자열로 박혀 셸에 그대로 전달된다.**
서버가 코드를 검증하지 않고 스크립트에 끼워 넣으면, `'; rm -rf /` 같은 입력이
사용자 PC 에서 실행되는 명령이 된다. 요청자와 피해자가 다른 원격 코드 실행이다.

둘째, **스크립트가 바이너리를 내려받는 주소도 스크립트 안에 있다.**
그 주소를 요청의 `Host` 헤더에서 만들면, 헤더를 조작한 링크 하나로
사용자가 공격자의 서버에서 실행 파일을 받게 된다.

바이너리 서빙 자체에도 고전적인 위험이 있다. `GET /bin/{filename}` 에서
`filename` 을 그대로 파일 경로에 붙이면 경로 traversal 이 열린다.

## Decision
- `GET /windows`, `GET /unix` 가 부트스트랩 스크립트를 `text/plain; charset=utf-8` 로 내려준다.
  경로에 `/v1` 접두사를 붙이지 않는다 — 사용자가 붙여넣는 URL 이라 짧아야 한다.
  초대 코드가 본문에 박혀 있으므로 `Cache-Control: no-store` 를 붙인다.
- **코드는 정규식 화이트리스트로 먼저 검증하고, 통과한 값만 스크립트에 삽입한다.**
  정규식은 Crockford Base32 12자(`XXXX-XXXX-XXXX`)만 허용하며 이 32자에는 셸·PowerShell
  메타문자가 하나도 없다. **이스케이프에 의존하지 않는다** — 이스케이프할 것이 애초에 없다.
- 이 두 엔드포인트는 **DB 를 조회하지 않는다.** 형식만 맞으면 코드가 실제로 존재하든 아니든
  똑같은 스크립트를 준다.
- 스크립트 안의 서버 주소는 설정값 `pulsemetry.public-base-url` 에서만 온다.
  이 값도 기동 시 정규식으로 검증해 따옴표·공백·명령 치환 문자를 막는다.
- 스크립트 본문은 리소스 파일(`bootstrap/install.ps1`, `bootstrap/install.sh`)에 두고
  자리표시자 두 개만 치환한다.
- `GET /bin/{filename}` 은 **여섯 개 파일명과의 동등 비교만** 한다.
  목록에 없으면 404, 있어도 `pulsemetry.binaries.dir` 에 파일이 없으면 404.
- 바이너리는 서버 로컬 디렉터리에서 서빙한다. S3·GitHub Releases 리다이렉트를 쓰지 않는다.

## Alternatives
### A. 코드를 이스케이프해서 스크립트에 삽입한다
- 장점: 어떤 입력이 와도 스크립트를 만들어 줄 수 있어 사용자가 오타를 내도 설치 흐름이 이어진다.
- 단점: 셸과 PowerShell의 인용 규칙이 서로 다르고 중첩 컨텍스트(`"$(...)"`, 히어독, `iex` 로 다시 파싱되는 문자열)마다 안전한 이스케이프가 달라진다. 한 곳만 놓치면 원격 코드 실행이다.
- 탈락 이유: 이스케이프는 "모든 경우를 빠짐없이 처리했는가" 를 증명해야 하는 방어이고, 그 증명은 코드가 자랄수록 유지되지 않는다. 화이트리스트는 통과 집합이 유한해서 눈으로 확인된다. 게다가 잘못된 코드는 어차피 enroll 단계에서 400 이므로 관대하게 받을 이유가 없다.

### B. 코드를 DB 에서 조회해 유효할 때만 스크립트를 준다
- 장점: 잘못된 코드에 즉시 명확한 오류를 줄 수 있어 사용자 경험이 낫다. 만료·폐기된 코드로 설치를 시작하는 헛수고를 막는다.
- 단점: 응답이 코드의 존재 여부에 따라 갈리므로, 이 엔드포인트가 **코드 탐색 오라클**이 된다. 인증이 없는 공개 엔드포인트라 공격자가 자동화된 요청으로 유효한 코드를 찾아낼 수 있다.
- 탈락 이유: 초대 코드는 그 자체가 자격증명이다. 인증 없는 엔드포인트가 자격증명의 유효성을 알려 주면 안 된다. 유효성 판정은 인증이 실제로 일어나는 `POST /v1/enroll` 한 곳에서만 한다.

### C. 파일명을 정규화·필터링해서 traversal 을 막는다
- 장점: 새 바이너리가 추가돼도 서버 코드를 고치지 않아도 된다. 목록 관리 부담이 없다.
- 단점: `..`, `%2e%2e`, `..%252f`, 유니코드 정규화, 심볼릭 링크까지 변형이 끝없이 나온다. 방어 로직이 복잡해질수록 검증하기 어려워진다.
- 탈락 이유: 이 게임에서는 언젠가 진다. 여섯 개와의 문자열 동등 비교는 어떤 인코딩 변형도 통과할 수 없고, 정확성을 한눈에 확인할 수 있다. 바이너리 목록은 아키텍처 조합이라 자주 늘지 않는다.

### D. 바이너리를 S3 나 GitHub Releases 로 리다이렉트한다
- 장점: 서버가 대용량 전송 대역폭을 쓰지 않고, CDN 으로 다운로드가 빨라진다. 배포 파이프라인과도 잘 맞는다.
- 단점: 스토리지 접근 제어와 서명 URL 이 새 관심사로 들어오고, 리다이렉트 대상 URL 이 또 하나의 신뢰 경계가 된다. 사내망 폐쇄 환경에서는 외부 접근이 막힐 수 있다.
- 탈락 이유: 현재 사용자 수에서 대역폭은 문제가 아니다. 신뢰 경계를 하나 더 만들 만한 이득이 없고, 필요해지면 그때 도입한다.

## Consequences/Tradeoffs
### Positive
- 주입 방어선이 정규식 한 줄로 좁혀져 리뷰와 테스트가 쉽다. 통합 테스트가 셸·PowerShell 주입 9종을 400 으로 막는 것을 확인한다.
- 인증 없는 공개 엔드포인트가 초대 코드의 유효성을 흘리지 않는다.
- `Host` 헤더를 조작해도 스크립트 안의 다운로드 주소가 바뀌지 않는다.
- 경로 traversal 이 구조적으로 불가능하다. 방어가 문자열 동등 비교라 인코딩 변형이 의미를 갖지 못한다.
- 스크립트가 리소스 파일이라 셸·PowerShell 문법 그대로 읽고 고칠 수 있다.

### Negative
- 사용자가 코드를 소문자로 치거나 하이픈을 빼면 400 이다. 스크립트 엔드포인트는 정규화하지 않는다.
  - 정상 경로는 관리자가 준 명령을 그대로 붙여넣는 것이라 실제로는 문제되지 않는다.
    손으로 입력한 코드의 정규화는 `POST /v1/enroll` 이 담당한다.
- 잘못된 코드로 설치를 시작하면 스크립트가 내려온 뒤 enroll 단계에서야 실패한다.
- 바이너리를 추가하려면 서버 코드의 화이트리스트를 고치고 배포해야 한다.
- 서버가 바이너리 전송 대역폭을 직접 부담한다.
- 인코딩된 슬래시(`%2e%2e%2f`)가 섞인 요청은 서블릿 컨테이너가 애플리케이션에 닿기 전에 400 으로 끊는다.
  응답 코드가 404 로 통일되지는 않지만, 파일이 나가지 않는다는 성질은 동일하게 지켜진다.
- 초대 코드가 부트스트랩 URL 의 쿼리 문자열에 실린다(`GET /unix?code=…`).
  `Cache-Control: no-store` 는 중간 캐시 저장을 막을 뿐 **서버·프록시 접근 로그에 남는 것은 막지 못한다.**
  이 위험은 다음 완화 요소를 근거로 **수용한다**: 코드는 일회성이고 TTL 이 짧다,
  이 엔드포인트는 코드를 소비하지 않으므로 로그에 남은 코드는 정상 설치가 끝나 이미 사용됐을
  가능성이 높다, 접근 로그를 열람할 수 있는 사람은 이미 특권 위치에 있다.

## Follow-up
- 바이너리 무결성 검증(체크섬·서명)은 이번 범위에 없다. 스크립트가 내려받은 파일을 그대로 실행한다.
  배포 파이프라인이 갖춰지면 체크섬 파일 서빙과 스크립트의 검증 단계를 추가한다.
- URL 의 코드 노출을 더 줄이려면 일회성 nonce(발급 시 코드와 함께 만들어 URL 에는 nonce 만 싣는 방식)를
  검토한다. MVP 대비 무겁다고 판단해 지금은 위 Negative 의 수용 결정으로 남긴다.
- 사용자 수가 늘어 대역폭이 문제가 되면 D 안(오브젝트 스토리지)을 다시 검토한다.
  그때도 리다이렉트 대상은 설정값으로 고정하고 `Host` 헤더에서 유도하지 않는다.
- 설치 스크립트가 하는 일(설정 충돌 검사·백업·OTel 키 병합·daemon 등록)은 클라이언트와 스크립트의 몫이며
  서버는 관여하지 않는다.
