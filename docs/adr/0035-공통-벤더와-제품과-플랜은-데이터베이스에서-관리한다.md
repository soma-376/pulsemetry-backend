# 0035. 공통 벤더와 제품과 플랜은 데이터베이스에서 관리한다

## Status

Accepted — ADR 0029의 코드 기반 카탈로그와 배포를 통한 목록 변경을 대체한다. API 형식, 조직별 등록, 계약 이력과 온보딩 완료 조건은 유지한다.

## Context

공통 선택지가 `VendorCatalog`의 상수여서 제품과 플랜을 추가할 때 서버를 배포해야 한다. 사용자 요청에 따라 이 목록을 enrollment 스키마의 기준 데이터로 옮긴다. 단일 레포의 저장 방식 변경이며 프론트·CLI 계약을 변경하지 않는다.

## Decision

- Flyway V10이 `enrollment.vendor_catalog_vendors`, `vendor_catalog_products`, `vendor_catalog_plans`를 생성하고 기존 6개 공급사·6개 제품·12개 플랜을 초기화한다. 개발용 시드가 아니라 운영에도 필요한 기준 데이터다.
- 제품은 공급사를 참조하고 플랜은 제품을 참조한다. 제품 ID는 기존 `kind`, 플랜 ID는 기존 `planId`를 유지한다. 같은 플랜 ID는 제품별로 구분한다. 가격은 공통 목록에 두지 않고 조직 계약에 둔다.
- 제품과 플랜은 `active`로 신규 선택 가능 여부를 관리한다. 기존 계약 JSON과 버전 이력은 변경하지 않는다. 신규 등록·계약 저장은 활성 제품·플랜을 DB에서 검증한다. 이력 조회·이름 변경·보관은 기존 이력을 유지한다.
- 목록 API·플랜 API·설정 API와 관리 명령은 같은 DB 저장소를 사용한다. 카탈로그를 프로세스에 캐시하거나 코드 상수로 대체하지 않는다. 라이브러리에 Spring 빈을 만들지 않고 앱이 조립한다.
- 제품과 플랜은 한 SELECT로 일관되게 읽는다. 공개 목록 내용의 SHA-256을 `catalogVersion`으로 반환해 DB 변경 후 기존 커서를 거부한다. 필드 형식과 기존 ID는 유지한다.
- `managed_vendors`와 계약 JSON에 새 외래 키를 소급 추가하지 않는다. 기존 등록·이력의 호환성을 보존하고 신규 선택은 공통 조회를 통해 검증한다.
- 오프라인 프론트 테스트용 export는 고정 fixture를 사용한다. fixture는 운영 조회·저장 검증에서 사용하지 않는다.
- 카탈로그 편집용 관리자 API와 UI는 이번 범위 밖이다. DB 데이터 변경으로 목록을 갱신할 수 있고, 서버 재시작 시 덮어쓰지 않는다. dashboard의 원천 계정은 SELECT만 허용한다.

## Alternatives Considered

테이블만 추가하고 상수를 계속 읽으면 원천이 두 개가 된다. 조직의 등록 테이블을 전역 선택지로 사용하면 조직 경계가 무너진다. 플랜을 JSON 하나로 저장하는 대신 제품별 키와 참조 관계를 DB에서 검증한다.

## Consequences/Tradeoffs

### Positive

공통 목록의 변경이 코드 배포 없이 조회와 입력 검증에 반영된다. 기존 조직 계약은 그대로 남는다.

### Negative

카탈로그 조회도 DB 가용성에 의존한다. 목록이 바뀌면 진행 중인 페이지 조회는 첫 페이지부터 다시 시작해야 한다. 관리 UI가 없어 권한 있는 DB 작업으로 데이터를 관리해야 한다.

## Acceptance Criteria

실제 PostgreSQL에서 초기 데이터·외래 키·기존 이력 보존·재기동 시 편집 보존을 확인한다. DB의 제품·플랜 추가와 비활성화가 목록 및 계약 검증에 반영되고, 카탈로그 변경 뒤 오래된 커서가 거부되는지 검증한다.
