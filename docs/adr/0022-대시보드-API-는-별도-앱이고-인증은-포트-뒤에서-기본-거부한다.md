# 0022. 대시보드 API 는 이 저장소의 별도 앱이고 인증은 포트 뒤에서 기본 거부하며 쓰기는 자기 캐시에 한정한다.

## Status

Proposed — 허브의 대시보드 API 소재 결정([dashboard API 계약](../../../docs/contracts/dashboard-api.md) §2 "Dashboard API 서버가 어디에 사는가")과 허브 [ADR 0007](../../../docs/adr/0007-dashboard-snapshots-and-telemetry-lifetime-summary.md)(분석 snapshot 과 수집 생애주기 요약의 저장소 분리) 채택 시 Accepted. 채택 전에는 이 앱을 배포하지 않는다. §4 의 캐시 계정 권한은 [ADR 0023](0023-대시보드-snapshot-은-dashboard-cache-의-불변-복사본과-manifest-이고-대시보드-앱이-그-DDL-을-적용한다.md) §3 이 넓혔다.

## Context

프론트엔드 화면(개요·팀 분석·구성원·설정)이 읽을 분석 조회 API 가 필요하다. 클라이언트 쪽 요청서는
`pulsemetry-frontend` 의 [화면별 API 구현 요청서](../../../pulsemetry-frontend/docs/api/README.md)이고, 모든 경로가
`/api/v1/organizations/{organizationId}` 아래에 온다.

이 저장소의 현재 사실은 다음과 같다.

- **배포 단위는 둘이다.** `:apps:enrollment-api`(설치 등록 · CLI 계약)와 `:apps:telemetry-ingest`(OTLP 수신부터 적재까지 —
  허브 ADR 0005 의 단일 파이프라인 앱). 앱끼리는 의존하지 않는다([ADR 0008](0008-모듈-경계와-네임스페이스-규칙-확정.md) 규칙 3).
- **대시보드가 읽을 원천은 전부 이 저장소가 스키마를 소유한다.** 분석 테이블 `telemetry_events`·`telemetry_metric_points`와
  수신 ledger `telemetry_ingest_ledger`(ClickHouse, `:libs:telemetry-persistence`,
  [ADR 0020](0020-정규화-계약-2판은-관측을-식별하고-의미-컬럼으로-교체-저장한다.md)·[ADR 0021](0021-수집-운영-기록은-ledger-와-telemetry-ops-스키마에-두고-enrollment-api-가-적용한다.md)),
  조직·팀·구성원·설치(RDS `enrollment`, `:libs:enrollment-persistence`), tenant 생애 요약·백필 기록·삭제 경계(RDS `telemetry_ops`,
  `:libs:telemetry-ops-persistence`). ADR 0020 §7 과 부록 B 가 분석 테이블의 조회 규칙(`FINAL`, primary 행, 의미 프로파일 안에서만 합산)을 정한다.
- **ADR 0008 은 이미 이 자리를 그려 두었다.** "읽기 전용 앱이 하나 추가될 때"의 예시가 `:apps:dashboard-api`(패키지
  `com.team376.pulsemetry.dashboard`)이고, 대시보드는 읽기만 하므로 `:libs:enrollment-persistence` 의 분할 트리거(규칙 5 — 관리자 API 앱의 첫 커밋)가
  당겨지지 않으며, 대시보드를 관리자 API 와 다른 배포 단위로 두는 근거는 인바운드가 아니라 워크로드라고 적었다. 그 절은 예시이지 결정이 아니다.
- **사람의 로그인은 아직 없다.** [ADR 0007](0007-인증-계층으로-spring-security-사용.md)이 Spring Security 가 AT(단수명 JWT — tenant·member·role 클레임)와
  RT 를 직접 발급·검증하기로 정했지만 구현이 없다. `:libs:security` 에는 OTLP 경로의 `ptt_` 검증만 있다.
- **허브의 확정 제약.** [dashboard API 계약](../../../docs/contracts/dashboard-api.md) §1 — Dashboard API 는 파이프라인과 Signal Database 에 쓰지
  않는다(제약 4), User Database 쓰기는 조직 설정 범위로 한정한다(제약 5). §2 — 웹 대시보드에 들어오는 사람은 관리자(`role` 이 `owner`·`admin`)뿐이다.
  허브 ADR 0007(Proposed)은 여기에 좁은 쓰기 예외를 제안한다 — ClickHouse `dashboard_cache` DB 와 RDS `dashboard_cache` 스키마(자기 캐시)에만 쓰고,
  원본 분석·ledger·`telemetry_ops` 에는 쓰지 않으며, Dashboard 계정은 분석 원본에 쓰지 못한다.
- **기존 앱의 기본 닫힘.** [ADR 0016](0016-조립-앱은-인증-체인과-단계-호출을-배선하고-스키마-적용-실패를-견딘다.md) 이후 `:apps:telemetry-ingest` 는 필터 체인 둘을 둔다 —
  계약 경로를 잡는 체인과, `/v1/healthz` 만 열고 나머지를 `denyAll` 하는 체인. 명시적 `SecurityFilterChain` 빈이 있으면 Boot 의 기본 체인이 물러나므로
  둘째 체인이 없으면 새로 얹는 경로가 인증 없이 열린다.
- **오류 본문 규약은 API 마다 있다.** `:apps:enrollment-api` 의 non-2xx 본문은 `{"error": <code>, "message": <text>}`(`ErrorResponse`)이고,
  CLI 가 그 본문을 그대로 터미널에 출력한다 — 허브 [enrollment API 계약](../../../docs/contracts/enrollment-api.md)의 일부다. 예외 메시지를
  응답에 싣지 않는 원칙은 `EnrollmentExceptionHandler` 에 있다. 화면 요청서는 "기존 서버 규약 우선, 없으면
  `{"error":{"code","message","fieldErrors"},"requestId"}`"를 제안하고 400 에 필드 단위 오류(`fieldErrors` 항목 `{field, code}`)를 기대한다.

정하지 않으면 대시보드 경로가 어느 프로세스에 얹힐지, 로그인이 생기기 전에 무엇이 응답하는지, 원본 저장소에 쓸 수 있는 계정이
대시보드에 주어질지가 구현마다 달라진다.

## Decision

### 1. 배포 단위와 모듈

- 대시보드 API 는 이 저장소의 새 배포 단위 **`:apps:dashboard-api`** 다. 루트 패키지는 `com.team376.pulsemetry.dashboard`, 메인 클래스
  `DashboardApiApplication` 만 `com.team376.pulsemetry` 에 둔다(모듈 지도 3절 — 스캔 출발점). 컨텍스트의 배포 단위가 하나이므로 규칙 2 의 내림은 발동하지 않는다.
- 포트는 설정 `server.port`(환경변수 `PULSEMETRY_DASHBOARD_PORT`)이고 로컬 기본값은 8081 이다 — 8080(enrollment-api)·4316(telemetry-ingest)과 겹치지 않게 고른 로컬 편의값이다.
- 이 앱은 `:libs:` 만 의존하고, 원천 스키마를 소유한 라이브러리(`:libs:enrollment-persistence`·`:libs:telemetry-ops-persistence`·
  `:libs:telemetry-persistence`)를 **읽기 소비자**로 쓴다. 규칙 1 은 읽는 모듈의 수를 제한하지 않으므로 어느 도메인의 쓰기 소유도 옮기지 않는다.
  `:libs:enrollment-persistence` 의 분할 트리거는 당겨지지 않는다 — 이 앱은 조직 설정을 쓰지 않는다(§2).
- 화면별 조회는 모듈이 아니라 이 앱 안의 패키지다(ADR 0008 — 읽기 전용 화면은 읽기 모델). 자기 캐시(`dashboard_cache`)의 DDL 과 쓰기 코드를 어디에 둘지는
  그 스키마를 정하는 ADR 이 [모듈 지도](../module-map.md) 6절로 판정한다 — 두 번째 소비자(DDL 을 적용하는 다른 앱, 별도 배포 단위의 정리 worker)가 있으면
  `:libs:dashboard-persistence`(패키지 `com.team376.pulsemetry.persistence.dashboard`), 없으면 이 앱 안이다.

### 2. 쓰기 경계

- 이 앱이 쓰는 곳은 **자기 캐시뿐이다** — ClickHouse 논리 DB `dashboard_cache` 와 RDS 스키마 `dashboard_cache`.
- 분석 테이블(`telemetry_events`·`telemetry_metric_points`·보존 중인 `enriched_events`)과 수신 ledger(`telemetry_ingest_ledger`)는 **읽기 전용**이다.
  삭제도 하지 않는다 — 보존 삭제는 그 대상의 정리 worker 몫이다.
- RDS `enrollment` 와 `telemetry_ops` 는 **읽기 전용**이다. 삭제 경계(`telemetry_ops.tenant_retention_boundary`)를 갱신하지 않는다.
- 이 ADR 이 다루는 범위는 **분석 조회(GET)** 다. 화면 요청서의 쓰기 명령(초대·팀 배정·좌석 회수·벤더 계약·정책·알림 규칙·설치 알림)과
  `GET /operations/{operationId}` 는 이 앱에 없다. 조직 설정 쓰기를 이 앱에 얹을 때는 규칙 5 의 분할 트리거와 이 절을 다시 판정한다.

### 3. 인증은 포트다

- 인증은 앱 안의 포트 `DashboardAuthenticator` 가 한다. 요청을 받아 주체 `DashboardPrincipal`(tenant·member·역할 — ADR 0007 의 AT 클레임과 같은 세 값)을
  돌려주거나, 인증할 수 없으면 `null` 을 돌려준다. 저장소 장애는 `null` 이 아니라 예외다.
- **기본 런타임 구현은 모든 요청을 거부한다**(`RejectingDashboardAuthenticator`). 그래서 지금은 `/api/v1/organizations/**` 의 모든 요청이 401 이다.
  런타임에 주체를 지어내는 설정(개발용 우회 플래그 등)을 두지 않는다. 테스트 전용 구현은 **테스트 소스에만** 두고 테스트가 포트 빈을 바꿔 끼운다.
- 실제 구현은 ADR 0007 의 사용자 인증이 `:libs:security` 에 서면 그 검증을 이 포트에 잇는 어댑터로 만든다. 포트를 라이브러리가 아니라 앱에 두는 것은
  아직 없는 검증 코드의 모양을 라이브러리 API 로 미리 굳히지 않기 위해서다.
- 인증 실패는 401 `unauthenticated`, 포트의 예외는 **401 이 아니라 503 `unavailable`** 이다 — 저장소 장애를 자격 오류로 보이면 클라이언트가 멀쩡한 세션을 버린다
  (`:apps:telemetry-ingest` 의 인증 조회 장애 처리와 같은 이유). 인증 방식이 정해지지 않았으므로 `WWW-Authenticate` 를 싣지 않는다.
- **조직 경로의 공통 관문은 순서가 정해져 있다.** `organizationId` 가 UUID 가 아니면 400, 주체의 tenant 와 다르면 **403 — 그 조직이 있는지 보지 않는다**,
  인가가 거부하면 403, 자기 조직이 없거나 삭제 표시가 있으면 404, 그 다음이 조회 파라미터의 400 이다. 화면 요청서의 `organizationId` 는 `enrollment.tenants.id` 다.
  snapshot 이 있어도 매 요청 다시 판정한다.
- **인가는 주체의 역할로 한다.** 역할 대응과 행위별 허용 규칙은 인가 포트가 소유한다. 저장소 역할의 대응은 이름까지만이다 — `owner`·`admin` 은 `admin`,
  `member` 는 `member` 이고, `lead`·`viewer` 로 옮겨지는 저장소 값은 없다. 합의 전 기본 정책은 **조직 관리자만** 조직 분석·개인 목록을 조회할 수 있고
  나머지 역할은 403 이다 — 허브 계약 §2 의 "웹 대시보드에 들어오는 사람은 관리자뿐"을 넘지 않는 보수적 기본값이다. 팀 리드 범위와 일반 구성원의
  개인 목록 공개는 RBAC 합의 뒤에 정한다.

### 4. 저장소 계정은 역할마다 따로 받는다

- 이 앱은 저장소 연결을 **네 묶음의 설정 키**로 받는다. 물리 인스턴스가 같아도 키를 합치지 않는다.

  | 키 접두 | 쓰임 | 필요한 권한 |
  |---|---|---|
  | `pulsemetry.dashboard.clickhouse.source` | 분석 테이블·ledger 읽기 | SELECT 만 |
  | `pulsemetry.dashboard.clickhouse.cache` | ClickHouse `dashboard_cache` 읽기·쓰기, snapshot 복사의 원본 읽기 | 쓰기는 그 DB 에 한정 · 분석 테이블은 SELECT(ADR 0023 §3) |
  | `pulsemetry.dashboard.rds.source` | RDS `enrollment`·`telemetry_ops` 읽기 | SELECT 만 |
  | `pulsemetry.dashboard.rds.cache` | RDS `dashboard_cache` 읽기·쓰기 | 그 스키마에 한정 · 공개 CAS 를 위한 `telemetry_ops.tenant_retention_boundary` SELECT(ADR 0023 §3) |

- 계정 값에는 **기본값이 없다**. 비어 있으면 기동이 실패한다 — 계정과 권한은 infra 가 정하고, 기본값이 있으면 원본 쓰기 권한이 있는 계정으로 조용히 뜰 수 있다.
  각 묶음은 그 연결을 처음 쓰는 구현이 바인딩한다.
- 권한의 강제는 DB 계정의 권한이 하고, 앱은 그 위에 2차 방어를 더한다 — ClickHouse 원천 조회마다 `readonly=2`, RDS 원천 커넥션은 읽기 전용
  (PostgreSQL 드라이버 `readOnlyMode=always` — 자동 커밋 문장에도 건다). 원천 계정으로 쓰기를 보내는 코드 경로를 만들지 않는다.
  요청마다 설정을 싣기 때문에 ClickHouse 원천 계정의 프로필은 `readonly=2` 이하여야 한다(`readonly=1` 은 설정 변경을 거부한다).
- 원천 조회의 상한(실행 시간·결과 행·결과 바이트)도 기본값 없는 설정이다. 넘으면 **잘라 내지 않고 실패**한다(`result_overflow_mode=throw`) —
  잘린 결과를 정상 총액으로 내지 않는다.

### 5. 오류 본문과 요청 ID

- non-2xx 본문은 `{"error": {"code": <코드>, "message": <문장>, "fieldErrors": [{"field": …, "code": …}]}, "requestId": <요청 ID>}` 다.
  `fieldErrors` 는 항상 배열이다(해당 없으면 빈 배열). 이 앱의 고유 규약이며 `:apps:enrollment-api` 의 본문과 다르다 — 그 본문은 CLI 와의 계약이고 `message` 가
  터미널 사용자에게 쓰인 문장이다. 앱끼리 코드를 나누지 않으므로(규칙 3) 같은 모양을 쓸 이유가 코드 공유에서 오지도 않는다.
- `message` 는 서버가 쓴 고정 문장이다. 예외 메시지·요청 원문을 싣지 않는다(`EnrollmentExceptionHandler` 와 같은 원칙).
- 코드와 상태: `invalid_request` 400 · `unauthenticated` 401 · `forbidden` 403 · `not_found` 404 · `method_not_allowed` 405 · `snapshot_expired` 409 ·
  `internal_error` 500 · `unavailable` 503. 코드를 더하는 것은 이 목록을 늘리는 일이다.
- 400 의 `fieldErrors[].field` 는 요청 파라미터·경로 변수의 이름 그대로이고 `code` 는 `required` · `invalid_format` · `unsupported_value` ·
  `out_of_range` · `invalid_order` · `invalid_cursor` 다. 오류는 모아서 한 번에 낸다.
- 원천 저장소의 일시 장애(연결·제한 시간·상한 초과·인증 실패)는 503 `unavailable`, 원천이 조회 자체를 거부한 것(문법·없는 테이블·읽기 전용 위반)은
  이 앱의 결함이므로 500 `internal_error` 다.
- **503 은 `Retry-After` 를 싣는다.** 값은 필수 설정 `pulsemetry.dashboard.retry-after` 이고 기본값이 없다.
- **모든 응답에 `X-Request-Id` 헤더가 있다**(성공·오류·보안 필터의 거부 모두). 요청에 `X-Request-Id` 가 있고 `[A-Za-z0-9._-]{1,128}` 이면 그 값을 쓰고,
  아니면 서버가 UUID 를 만든다. 오류 본문의 `requestId` 는 그 헤더와 같은 값이다. 로그의 상관 키도 같은 값이다.

### 6. 계약 밖 경로는 닫혀 있다

- 필터 체인은 둘이다. 첫 체인은 `/api/v1/organizations/**` 만 잡고, 포트로 인증하고, 익명 인증을 끄고, 세션을 만들지 않는다.
  인증된 요청이라도 매핑이 없는 경로는 404 `not_found` 다.
- 둘째 체인이 나머지 전부를 잡는다. 생존 확인 `GET /v1/healthz`(기존 두 앱과 같은 경로)만 열고, 그 밖은 `denyAll` 이며 거부 응답은 404 `not_found` 다 —
  API 자원이 아닌 경로에 인증을 요구해 경로의 존재를 알리지 않는다. 내부 ERROR 디스패치는 통과시켜 서버 오류 응답을 보존한다(ADR 0016 과 같은 이중 방어).
- 생존 확인은 저장소를 확인하지 않는다. 저장소 장애가 태스크 교체로 번지지 않게 하는 ADR 0016 의 판단과 같다.
- 보안 응답 헤더는 Spring Security 기본값을 유지한다 — `:apps:telemetry-ingest` 가 끈 이유(OTLP 응답의 바이트 계약)가 이 앱에는 없고, 개인 데이터 응답에는
  `Cache-Control: no-store` 계열이 맞다.

## Alternatives

### A. `:apps:enrollment-api` 에 대시보드 경로를 얹는다
- 장점: 배포 단위가 늘지 않는다. RDS 연결이 이미 있다.
- 단점: 그 앱의 오류 본문·역직렬화 규칙은 CLI 계약이다(`fail-on-unknown-properties`, `{"error","message"}`). ClickHouse 조회와 snapshot 복사의 부하가
  설치 부트스트랩과 같은 프로세스 자원을 나눈다. ADR 0008 이 워크로드를 배포 단위의 근거로 든 경우다.
- 탈락 이유: 계약이 다른 두 클라이언트가 한 프로세스의 오류 처리·보안 체인을 나눠 써야 한다.

### B. `:apps:telemetry-ingest` 에 얹는다
- 장점: ClickHouse 연결이 이미 있다.
- 단점: 그 앱은 허브 ADR 0005 의 파이프라인 단일 앱이고, 계약 밖 경로를 `404 text/plain` 으로 거부하는 OTLP 계약을 진다. 조회 부하가 적재와 같은 JVM 에서 돌면
  수집이 밀린다. 허브 ADR 0007 은 조회 부하가 수집·적재를 방해하지 않게 계정·자원을 분리하라고 한다.
- 탈락 이유: 수집 경로의 가용성을 조회 부하에 묶는다.

### C. 별도 레포에 둔다
- 장점: 배포·권한이 레포 경계로 갈린다.
- 단점: 원천의 스키마(ClickHouse DDL·Flyway)와 조회 규칙(ADR 0020 §7·부록 B)이 이 저장소에 있다. 다른 레포가 읽으면 열 이름·의미 프로파일·null 규칙을 복제하고,
  정규화 개정(`NORMALIZER_REV`)마다 두 레포를 함께 고쳐야 한다.
- 탈락 이유: 조회 규칙의 소유자와 스키마의 소유자가 갈라진다. 다만 레포 소재는 크로스레포 결정이라 허브 결정 전까지 이 ADR 을 Proposed 로 둔다.

### D. 개발 편의를 위해 설정으로 고정 주체를 켠다
- 장점: 로그인 없이 로컬에서 화면을 붙여 볼 수 있다.
- 단점: 설정 하나가 배포 환경에서 켜지면 인증이 통째로 사라진다. 테스트는 런타임 코드 없이 빈 교체로 충분하다.
- 탈락 이유: 기본 닫힘을 설정 한 줄에 맡긴다.

### E. 오류 본문을 `:apps:enrollment-api` 의 모양으로 맞춘다
- 장점: 저장소 안에 오류 모양이 하나다.
- 단점: 필드 단위 오류와 요청 ID 를 담을 자리가 없고, CLI 계약을 바꾸지 않으려면 모양을 넓힐 수도 없다(클라이언트가 모르는 필드를 거부한다).
- 탈락 이유: 화면 요청서가 기대하는 400 의 필드 오류를 표현하지 못한다.

## Consequences/Tradeoffs

### Positive
- 원천 스키마·조회 규칙·조회 앱이 한 저장소에 있어 정규화 개정과 조회 수정이 한 PR 로 닫힌다.
- 로그인이 서기 전에도 앱이 기본 닫힘으로 선다. 무엇이 통과했는지는 포트 구현 하나로 설명된다.
- 원천 읽기와 캐시 쓰기의 계정이 설정에서부터 갈려, 원본 쓰기 권한이 대시보드에 흘러드는 경로가 코드에 없다.
- 오류 본문이 필드 오류와 요청 ID 를 담아 화면이 400 을 필드에 붙이고 로그와 대조할 수 있다.

### Negative
- 배포 단위가 셋이 된다. infra 가 서비스·대상 그룹·계정 네 묶음·설정을 새로 만들어야 한다.
- 사용자 인증이 서기 전까지 이 앱의 조직 경로는 전부 401 이다 — 배포해도 쓸 수 있는 것이 없다. 그래서 Status 조건과 별도로 인증 연결 전에는 배포하지 않는다.
- 저장소 안에 오류 본문 모양이 둘이다. 클라이언트는 호출하는 API 의 모양을 따로 알아야 한다.
- 요청의 `X-Request-Id` 를 받아 쓰므로 클라이언트가 고른 값이 로그의 상관 키가 될 수 있다.
  - 완화: 문자 집합과 길이를 제한하고, 어긋나면 서버 값으로 바꾼다.
- 필수 설정이 늘어 로컬 기동에도 환경변수가 필요하다.

## Follow-up

- 허브에서 대시보드 API 소재를 결정하고(dashboard API 계약 §2) 허브 ADR 0007 이 채택되면 Accepted 로 올린다.
- 사용자 인증(ADR 0007)이 `:libs:security` 에 서면 포트 어댑터를 만든다. 쿠키 세션을 쓰게 되면 CSRF 를 다시 판정한다(지금은 세션이 없고 GET 만 있다).
- 역할 대응과 팀 리드·일반 구성원의 조회 범위는 RBAC 합의 뒤 인가 포트의 정책으로 넓힌다.
- 오류 본문 모양·코드 목록과 `dataThrough` 등 응답 의미는 프론트와 합의한다.
- `dashboard_cache` 의 DDL·적용 주체·쓰기 모듈은 snapshot 저장을 정하는 ADR 이 정한다.
