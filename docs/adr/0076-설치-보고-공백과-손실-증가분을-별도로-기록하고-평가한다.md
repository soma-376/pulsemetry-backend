# 0076. 설치 보고 공백과 손실 증가분을 별도로 기록하고 평가한다

## Status

Accepted — ADR 0040의 보고 저장, ADR 0041의 헤더 수집 상태 표시, ADR 0051의 사용자 설정 규칙만 평가하는 범위를 개정한다.
기존 heartbeat 형식·수집 구간·기간 완전성·보안/비용 규칙·확인 명령은 유지한다.

## Context

허브 ADR 0030은 활성 설치의 168시간 보고 공백과 최근 168시간 보고된 손실을 분리한다.
최신 heartbeat·합쳐진 구간만으로는 손실 증가분의 서버 확인 시각을 복원할 수 없고,
사용자 규칙이 없는 조직도 시스템 공백 규칙을 평가해야 한다.

## Decision

### 1. 증가분 원장과 전환

실행별 `(installation_id, run_id)` 최고 누적값, 양수 증가분 원장, 추적 시작·중단 메타데이터와
감소 등 제한 이력을 enrollment에 저장한다. 기존 설치 행 잠금 트랜잭션 안에서 heartbeat와 함께 쓴다.
새 실행은 0, 기존 실행은 최고 누적값을 기준으로 `max(lost − 기준값, 0)`만 기록하고 최고값은 낮추지 않는다.
관측 조건은 `mode=local && forwarding=true`이며 수신기 가동 시각과 무관하다. 다른 모드의 0은 관측 근거가 아니다.

구 writer 종료 후 추적 시작을 기록하고 최신 heartbeat의 실행·누계를 기준값으로 이관한다.
보존된 과거 구간의 실행 ID는 과거 실행으로 표시하여 재합산을 막는다. 구간 손실의 시간 비례 배분·종료 시각 백필은 금지한다.
구 writer rollback은 중단을 기록하고, 다시 배포할 때 최신 기준값과 집계 가능 시작을 재설정한다.
실행별 커서는 조회 창이 지났다고 삭제하지 않는다. 원장은 기존 보고 보존 기간을 따르되 최소 168시간을 보장한다.

### 2. 손실 조회

집계 창은 서버 기준 `[windowEnd − 168시간, windowEnd)`이며 원장의 서버 확인 시각으로 합산한다.
폐기·모드 전환 이후에도 이미 기록한 손실은 포함한다. 현재 상태의 ClickHouse 실패는 RDS 손실 조회를 덮어쓰지 않는다.
기반·관측 근거 없음과 조회 실패는 null/`unavailable`, 초기 추적·중단·감소 제한은 확인 수량/`partial`이다.
근거가 충분한 `complete`는 실제 모든 전송의 무손실을 보장하지 않는다. 보고 공백만으로 가용성을 낮추지 않는다.
헤더와 영향 기기 목록은 같은 `windowEnd`를 쓰며 기존 cursor 방식·관리자 권한·조직 격리를 적용한다.

### 3. 공백 평가와 원자성

활성 설치의 기준은 마지막 heartbeat `received_at`, 최초 미보고는 설치 `created_at`이다.
평가 시각이 기준 + 168시간 이상이면 `installation_report_gap`/`collection` 알림을 만든다.
사건 키는 조직·설치·기준 시각이며 `eventCount=null`이다. 사용자 규칙 설정 없이 자동 평가한다.

새 기준의 보고를 보면 이전 열린 사건을 `report_resumed`로 종료하고 새 기준에서도 임계에 도달했으면 새 사건을 만든다.
설치 폐기는 `installation_revoked`로 종료한다. `resolutionDetectedAt`은 평가 확인 시각이며 복구 시각이 아니다.
같은 사건의 반복 평가는 새 알림·불필요한 버전 변경을 만들지 않는다. 해소와 확인은 독립이며 재발 사건은 새 미확인 알림이다.
평가 중단 중 이미 해소된 과거 공백은 복원하지 않는다.

원천 조회 이후 cache 트랜잭션에서 조직 선점의 소유자와 만료를 다시 검사한다.
이전 사건 종료·새 사건 생성·평가 결과 기록을 함께 처리하며 선점을 잃은 결과는 폐기한다.
원천 조회 후 도착한 heartbeat는 다음 성공 평가에 반영한다.

### 4. 배포와 권한

새 범주·evidence를 수용하는 프론트 → 구 enrollment writer 종료 → 이관·신규 writer → 신규 테이블 SELECT 검증 → dashboard 순서다.
Recreate가 아니면 기존 writer가 모두 종료되는 동등한 절차를 사용한다. dashboard source는 필요한 테이블만 읽고
cursor 등 내부 쓰기 상태에 불필요한 권한을 주지 않는다. 미래 테이블 전체 grant나 앱 기동 grant는 없다.
메일 등 신규 채널과 사용자 활성화 토글은 추가하지 않는다.

## Alternatives Considered

### A. 기존 구간의 손실 합계를 조회한다

관측 시각·이전 실행 중복을 구분할 수 없으므로 반개구간 집계와 전환 원칙을 충족하지 못한다.

### B. enrollment 보고 수신 때 공백을 종료한다

쓰기 소유가 dashboard cache와 갈리고 평가 선점·결과 기록과 원자적으로 처리할 수 없다. 기존 평가 주기를 유지한다.

## Consequences/Tradeoffs

### Positive

서버 확인 시각으로 손실을 재현하고 같은 실행 감소·재보고를 중복 계산하지 않는다.
보안·비용 알림의 확인 경로를 재사용하며 시스템 상태 해소와 사람의 확인을 분리한다.

### Negative

초기 부분 집계와 장기 실행 커서가 필요하다. 이전에 삭제한 실행과 평가 중단 중 이미 끝난 공백은 복원하지 못한다.
단계별 배포·rollback 기록·DB 최소 권한을 함께 검증해야 한다.
