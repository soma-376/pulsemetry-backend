# 0056. 업무 API와 SSO 인증을 통합한다

## Status

Accepted — 사용자 요청. ADR 0018·0026·0038·0055의 비밀번호 가입·초대 가입 용도를 대체한다. 좌석·메일 outbox·업무 API와 서비스 토큰 검증 규칙은 유지한다.

## Context

PROJ-187 업무 API와 PROJ-186 SSO가 같은 인증·초대·시드 코드를 변경했다. 업무 조회·명령을 유지하면서 사람 인증은 기존 결정인 표준 OIDC로 통일한다.

## Decision

- 가입·비밀번호 로그인·비밀번호 CLI 인가는 410이다. 회사별 OIDC와 사전 등록 회원의 최초 검증 이메일/sub 연결을 사용한다.
- 서비스 AT/RT와 DB 세션 검증은 유지한다. OIDC 요청도 PROJ-187의 설정 가능한 진입 한도를 공유한다.
- 초대 코드는 설치에만 사용한다. 메일은 회사 SSO 로그인 주소와 별도의 CLI 설치 명령을 안내한다. 로그인 주소에는 초대 코드를 붙이지 않는다.
- 기존 signupUsedAt 응답은 이력 호환용이다. used·취소·재발급 판정은 설치 소비 상태를 따른다. 활성 회원의 설치 전용 코드 발급은 유지한다.
- PROJ-187의 V13~V27을 유지하고 SSO 마이그레이션은 V28·V29로 배치한다. 기존 feature 브랜치의 V12/V13을 적용한 개발 DB는 번호만 다른 이력이 있어 그대로 실행하지 않는다. 백업과 실제 스키마·체크섬을 대조해 별도 이관하며 이 PR은 사용자 DB 이력을 자동 변경하지 않는다.

## Consequences/Tradeoffs

새 DB와 PROJ-187 DB에서 동일 순서로 적용할 수 있다. 기존 비밀번호 앱으로 롤백할 수 없고, 실제 IdP 계정 없는 조직의 브라우저 E2E는 별도 준비가 필요하다. 운영 인증 우회는 추가하지 않는다.

## Validation

모의 OIDC의 실제 서명·PKCE·nonce·최초 연결, JWT/RT·요청 제한, 업무 API, Flyway 데이터 보존 테스트를 함께 실행한다. 프론트는 암호화 HttpOnly 쿠키 BFF 경로를 사용한다.

통합 시드는 업무 데이터와 인증 컬럼이 함께 달라져 지문 판을 2로 올린다. 기존 판을 같은 데이터로 간주하거나 자동 삭제하지 않는다. 기존 개발 볼륨은 별도 백업·이관 판단이 필요하며, 검증은 분리된 새 DB에서 수행한다. OTLP 주소만 바뀐 경우 지문은 계속 동일하다.
