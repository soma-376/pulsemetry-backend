# 0052. 인증 요청 제한은 토큰 없는 진입은 IP로, 자격을 가진 요청은 세션으로 센다

## Status

Accepted — [ADR 0018](0018-사용자-인증은-회전-세션과-명시적-키링으로-운영한다.md)의 "인증 API의 IP 제한은 분당 30회" 문장을 개정한다.
계정 잠금, `remoteAddr` 사용, PostgreSQL 공유 상태는 ADR 0018 그대로다.

## Context

ADR 0018 은 인증 API 전체에 IP 제한 하나를 두었다. 구현은 `UserAuthService.limitIp`이고, 키는 `ip:<remoteAddr>`의 SHA-256,
`enrollment.auth_attempts` 행 하나에 60초 고정 창으로 30회까지 센다. enrollment-api 의 사용자 인증 필터가 `/v1/auth/*` 전부와
`GET /v1/manifest`에 이 판정을 건다.

이 버킷을 쓰는 요청은 성격이 둘이다.

- **토큰 없는 진입**: 로그인·가입·CLI 인가 요청·CLI 코드 교환. 비밀번호·초대 코드·인가 코드를 맞히려는 시도가 여기서 일어난다.
- **이미 자격을 가진 요청**: RT 갱신·로그아웃·재조회(`GET /v1/manifest`)와 현재 사용자 조회(`GET /v1/auth/me`). RT·AT 는 256비트 난수이거나
  서명된 JWT 라 추측이 성립하지 않는다. 대시보드는 AT 수명(5분)마다 갱신하고 화면마다 현재 사용자를 읽는다.

둘이 한 IP 버킷을 쓰면, 같은 NAT 뒤의 관리자들과 브라우저 탭이 쓰는 갱신·로그아웃·현재 사용자 조회가 버킷을 채워 서로를 막는다.
ADR 0018 의 Negative 가 적은 대로 프록시 주소만 보이는 배포에서는 배포 전체가 버킷 하나다. 막히는 쪽은 이미 로그인한 사용자이고,
로그아웃이 429 로 막히면 세션을 끊을 수도 없다. 한도를 올리면 진입의 추측 방어가 약해진다.

## Decision

### 범주와 키

| 범주 | 요청 | 키 |
|---|---|---|
| 진입 | `POST /v1/auth/login`·`/signup`·`/cli/authorize`·`/cli/token`, 그리고 아래 자격 보유 표에 없는 `/v1/auth/*` 요청 전부 | `ip:<remoteAddr>` |
| 자격 보유 | `POST /v1/auth/refresh`·`POST /v1/auth/logout`(본문의 RT), `GET /v1/manifest`(`Authorization`의 RT), `GET /v1/auth/me`(`Authorization`의 AT) | `session:<세션 ID>` |

- 세션은 RT 해시의 기록에서 찾는다(회전해도 세션은 같다). 이미 소비한 RT 도 그 세션으로 센다. AT 는 서명·만료를 검증한 뒤 `sid` 클레임을 쓴다 —
  세션 폐기·구성원 상태 검사는 본 처리가 한다.
- **토큰이 없거나 형식이 틀렸거나 모르는 RT 이거나 검증에 실패한 AT 는 진입 버킷으로 센다.** 토큰을 추측하는 비용은 이 결정 전과 같다.
- 범주에 없는 요청(앞으로 생길 진입 경로, 자격 보유 경로의 다른 메서드)은 진입 한도를 따른다.
- 키는 바뀌지 않는 세션 ID 다. 회전마다 바뀌는 RT 해시나 토큰마다 다른 AT 문자열을 키로 쓰면 요청마다 새 버킷이 되어 제한이 없어진다.

### 판정 위치와 순서

- 진입은 사용자 인증 필터가 컨트롤러 앞에서 판정한다(이 결정 전과 같은 위치).
- 자격 보유는 컨트롤러가 토큰을 읽은 직후, 서비스를 부르기 전에 판정한다. 본문을 해석하지 못한 요청은 토큰 판정 전에 400 으로 끝나며 세지 않는다 —
  DB 에 닿지 않는다.
- 카운터는 자기 트랜잭션으로 먼저 커밋한다. 429 는 RT 소비·회전 전에 내므로, 429 를 받은 클라이언트는 `Retry-After` 뒤에 **같은 RT** 로 다시 시도한다.

### 한도와 응답

- 설정 키 `pulsemetry.user-auth.rate-limit.entry.requests`·`entry.window`, `pulsemetry.user-auth.rate-limit.session.requests`·`session.window`.
  기본값은 둘 다 30회·60초다(이 결정 전과 같은 값). 요청 수는 1 이상, 창은 1초 이상이어야 하며 아니면 기동하지 않는다.
- 고정 창이고 상태는 `enrollment.auth_attempts`(키의 SHA-256)에 둔다. 새 테이블·마이그레이션은 없다.
- 초과는 429 `rate_limited`와 `Retry-After`(창이 끝날 때까지의 초)다. 본문은 다른 인증 오류와 같은 `{error, message}`이다.
- `UserAuthService.limitIp(ip)`는 이름과 인자를 유지하며 진입 버킷을 **기본 한도**로 센다. 앱이 조립한 경로는 설정 한도를 쓰는 `AuthRateLimiter`를 부른다.

## Alternatives

- **IP 한도 상향**: 진입의 추측 방어가 약해지고, NAT 공유 문제는 한도만큼 늦게 나타날 뿐이다.
- **구성원 단위 버킷**: 한 사람의 CLI 와 대시보드 탭이 서로를 막는다. 클라이언트의 단위는 세션이다.
- **RT 해시·AT 문자열 키**: 위 Decision 대로 제한이 없어진다.
- **메모리 제한기**: ADR 0018 이 재시작·다중 인스턴스에서 효력이 갈린다는 이유로 배제했다.
- **X-Forwarded-For 신뢰**: 신뢰 프록시 설정 없이는 위조할 수 있다. ADR 0018 그대로 쓰지 않는다.

## Consequences/Tradeoffs

### Positive

- 같은 NAT·프록시 뒤의 사용자가 서로의 갱신·로그아웃·재조회·현재 사용자 조회를 막지 않는다.
- 진입의 추측 방어와 계정 잠금(5회 실패 15분)은 그대로다.
- 한도를 코드 수정 없이 배포 설정으로 조정한다.

### Negative

- 자격 보유 요청은 본 처리 전에 세션 조회(RT 해시) 또는 JWT 검증을 한 번 더 한다.
- `auth_attempts`에 세션마다 행이 생긴다. 운영 정리 쿼리(창 시작 시각 기준)가 같이 지운다.
- 진입 한도를 바꾸면 `limitIp`를 직접 부르는 호출자는 기본 한도를 계속 쓴다. 그런 호출자는 `AuthRateLimiter`로 옮겨야 같은 한도가 걸린다.
- 본문을 해석하지 못한 자격 보유 경로 요청은 세지 않는다.

## Follow-up

- `limitIp`를 직접 부르는 경로가 생기면 `AuthRateLimiter.entry`로 옮긴다.
- 신뢰 프록시 뒤의 클라이언트 주소 복원은 ADR 0018 의 별도 결정으로 남는다.
