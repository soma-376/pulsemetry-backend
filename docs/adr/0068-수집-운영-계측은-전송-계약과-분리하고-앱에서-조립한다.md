# 0068. 수집 운영 계측은 전송 계약과 분리하고 앱에서 조립한다.

## Status

Accepted — PROJ-191의 backend 내부 구현 결정. 공개 OTLP 응답과 Kafka envelope는 바꾸지 않는다.
배포·수집 권한·Grafana 구성은 infra의 계약과 구현을 따른다.

## Context

Gateway의 200은 Kafka 접수이고 consumer의 정상 반환에는 빈 요청과 영구 폐기도 포함된다(ADR 0066).
기존 실패 로그만으로 처리량·단계 지연·JVM 압박을 설명할 수 없다. 라이브러리는 Spring 조립을 하지 않는다(ADR 0011).

## Decision

- `:libs:telemetry-observability`에 Spring 없는 observer와 Micrometer 구현을 둔다. collector와 persistence는
  생성자로 observer를 받으며 기본은 no-op이다. Gateway와 ingest 앱이 registry와 계측을 명시 조립한다.
- Gateway와 ingest만 Actuator/Prometheus를 의존한다. 관리 서버 9404의 GET `/actuator/prometheus`만 노출한다.
  공개 서버 포트에서는 actuator가 닫혀 있고 기존 health 경로·의미와 OTLP 응답 바이트를 보존한다.
- 처리 시도·실패·retry 소진·commit 실패·INSERT 입력 행을 따로 센다. INSERT 입력 행 수를 실제 저장 건수라 부르지 않는다.
  acceptedAt 기준 시간은 처리 시도 시작·정상 완료까지의 경과이고 broker queue 시간이나 유일한 저장 증거가 아니다.
- 단계는 authorize/decode/mask/archive/normalize/enrich/retention/insert/ops이다. decode는 압축 해제를 포함한다.
  초·byte 단위를 사용하고 합산 가능한 histogram만 내보낸다. 시각 역전 표본은 버리고 별도로 센다.
- label은 고정 signal/stage/outcome/reason/table 값이다. payload·Bearer·tenant·installation·message ID·offset·SQL을 싣지 않는다.
  계측 예외가 업무 결과·재시도·offset 확정에 영향을 주지 않도록 observer 경계를 보호한다.
- 직접 생성한 producer에는 KafkaClientMetrics를, consumer factory에는 MicrometerConsumerListener를 등록한다.
  producer binder와 client 수명주기를 함께 닫는다. KafkaTemplate·KafkaAdmin 자동설정은 도입하지 않는다.
- 기존 event 코드와 평문 로그 형식을 보존한다. 앱이 소유한 장애 로그는 원문 예외 메시지 없이
  원인 타입과 제한된 stack frame을 남긴다. 분산 추적·새 요청 문맥·dump 수집을 추가하지 않는다.

## Alternatives

- 라이브러리에 Boot starter를 추가하면 의도하지 않은 앱 자동설정이 생겨 기각한다.
- listener success와 insert 반환값을 저장 완료로 취급하면 영구 폐기·retention fence·재전달을 숨겨 기각한다.
- 요청 식별자 label과 전면 JSON 로그 전환은 이번 진단 목적에 필요하지 않아 보류한다.

## Consequences/Tradeoffs

### Positive

업무 처리 의미를 보존하면서 단계 지연과 장애를 관측한다. 전송 계층에 없는 library 테스트는 no-op을 그대로 쓴다.

### Negative

histogram과 Kafka binder의 메모리·CPU 비용이 추가된다. process counter는 재시작·재전달 때문에 유일 건수 원장이 아니다.
최종 데이터 정합성은 시험 manifest와 ClickHouse 논리 행을 별도로 대조해야 한다.

## Follow-up

실험의 calibration부터 같은 계측 구성을 유지한다. 배포 후 실제 series, 수집 격리와 collector 장애를 검증한다.
