# 0007. 인증 계층을 백엔드의 Spring Security 로 두고 토큰을 직접 발급한다.

## Status
Accepted

## Context

지금까지의 설계는 인증을 **외부 관리형 IdP(Cognito User Pool)와 ALB** 가 담당하는 것을 전제로 했다.
[ADR 0003](0003-enrollment-API-계약과-2단-토큰-모델.md) 의 follow-up 도 "웹 대시보드가 생기면
관리자 인증을 정적 키에서 Cognito 로 옮긴다" 로 남아 있고, `enrollment.members` 에는 그 전제에서 나온
`cognito_user_sub` 컬럼이 있다. 이 ADR 은 그 전제를 다시 검토한 기록이다.

검토의 출발점은 기능 요구가 아니라 하나의 운영 시나리오다 — **tenant 의 manifest 가 개정되면
이미 설치된 PC 의 manifest 는 누가 바꿔 주는가.**
manifest 는 프롬프트·응답을 수집할지 말지를 정하는 프라이버시 정책이므로, 이 질문은 편의 문제가 아니라 정책 집행 문제다.

### 사용자가 telemetryctl 를 설치하는 플로우

1. 관리자가 대시보드에서 사용자 정보를 등록하고 초대한다. 초대 코드(invitation token)가 발급되고, 초대 테이블에 코드와 사용자 정보가 기록된다.
2. 초대 링크가 담긴 메일이 발송된다.
3. 링크로 들어가면 안내 페이지가 뜬다. 그 페이지가 OS 를 감지해 맞는 설치 명령어를 안내한다 — curl 로 URL 에서 스크립트를 받아 셸로 실행하는 형태다.
   (예: `curl -fsSL 'https://get.../unix?code=ABCD-EFGH-JKMN' | sh`, Windows 는 `irm 'https://get.../windows?code=ABCD-EFGH-JKMN' | iex` 를 입력하면 설치와 등록이 자동으로 진행된다.)
4. enrollment 서버가 바이너리 설치 스크립트(bootstrap)를 제공한다.
5. bootstrap 스크립트가 CLI 를 설치한다. enrollment 서버가 서빙하는 바이너리 파일을 내려받는다.
6. 설치가 끝나면 CLI 의 `enroll` 명령이 실행되어 등록이 진행된다. 초대 코드의 소비(consume)는 이때 일어난다.
7. enroll 이 성공하면 manifest 와 토큰 2종이 응답으로 내려온다. manifest 는 무엇을 수집하고 무엇을 수집하지 않을지가 정의된 OTel 설정이다(예: 프롬프트 수집 여부, tool detail 수집 여부).
8. 이 응답을 바탕으로 로컬 OTel 설정을 구성하고 로컬 telemetryctl 데몬이 동작한다.

### (동시에) 사용자가 telemetryctl 인증을 위하여 회원가입을 하는 플로우

1. 관리자가 대시보드에서 사용자 정보를 등록하고 초대한다. 초대 코드가 발급되고, 초대 테이블에 코드와 사용자 정보가 기록된다.
2. 초대 링크가 담긴 메일이 발송된다.
3. 사용자가 메일을 받고 회원가입 링크로 이동해 id + pw + 초대 코드를 입력한다.
4. 회원가입이 끝나면 (앞선 플로우대로) CLI 를 내려받는다.
5. CLI 설치 후 사용자가 로그인한다. 웹 페이지를 띄워 로그인하고, 콜백 URL 로 CLI 에 AT 와 RT 를 전달한다. Codex 나 Claude Code 를 CLI 에서 로그인하는 방식과 같다.
6. CLI 가 초기 설정을 진행한다. 해당 사용자 tenant 의 활성 manifest 를 적용한다.

---

### 인증 흐름

1. 클로드 코드 → 데몬. 로컬 OTLP 이며 로컬 ingest 토큰을 쓴다. 클로드 코드의 `settings.json` 에 로컬 토큰이 저장되어 있다.
2. 데몬 → 서버. 여기서 Cognito 가 준 액세스 토큰을 `Authorization` 헤더에 붙인다.
3. 서버 앞단의 ALB 가 액세스 토큰을 검사한다(Cognito 서명 확인).
   - 토큰이 유효하면 컬렉터로 넘긴다.
   - 유효하지 않으면 401 을 반환한다.

### 토큰 로테이션 흐름

1. 사용자가 로그인한다. 웹에서 로그인시키면 콜백 URL 로 액세스 토큰과 리프레시 토큰을 가져온다. Codex 나 Claude Code 를 CLI 에서 로그인하는 방식과 같다.
2. 데몬이 서버 측으로 신호를 포워딩했을 때 401 이 뜨면, 콜백 URL 로 받았던 RT 로 AT 를 갱신하고 그 AT 로 재시도한다.
3. RT 조차 만료됐다면 사용자를 다시 로그인시킨다.

### 사원들의 local desktop(telemetryctl)의 manifest 변경 시나리오

- tenant 의 manifest 는 개정(revision)으로 바뀐다 — 예: 보안 요구가 높아져
  프롬프트 수집을 끄는 새 버전(v2)을 활성화한다.
- 활성 manifest 가 v1 → v2 로 바뀌었을 때, 이미 v1 을 적용하고 있는 직원 X 의 PC 의
  로컬 manifest 는 어떻게 변경해 주어야 하는가?
- (manifest 배정 단위는 **tenant 로 확정**됐다 — tenant 당 활성 manifest 는 최대 하나이며
  `ux_manifests_tenant_active` 가 그것을 강제한다. 부서 단위 배정은 `teams` 가 실제로
  쓰이게 될 때 별도 개정 ADR 로 다시 연다.)

> Cognito User Pool 에서 발급한 토큰을, 요청이 서버 파이프라인에 닿기 전에 분석할 수 있는가?

- 조건 1. AT 에 manifest 버전 등의 메타데이터를 심어 주어야 하며,
- 조건 2. 파이프라인에 들어오기 전에 AT 를 파싱해서 DB 와 AT 내 메타데이터를 대조하고, 해당 사원이 가져야 하는 manifest 와 다른지 알아내야 한다.

#### 해당 분석을 할 수 있다고 가정해 보자.

그렇게 되면 4xx 번대 에러를 던져서 해당 사원의 manifest 가 맞지 않는다고 알려 줄 수 있다.
즉 "manifest 버전이 안 맞으니 다시 내려받아라" 를 말하는 것이다.

1. 만약 이때 AT 를 같이 바꿔 버리면?
   업데이트 이후 manifest 를 실제로 적용할 책임은 오로지 로컬 데스크탑 데몬(telemetryctl)에 있는데,
   모종의 이유로 적용이 안 되어도 AT 는 이미 바뀌었으니 ALB 에서 과거 manifest 상태가 그대로 통과한다.
2. AT 를 이때 바꾸지 않고 에러만 던져서 CLI 가 manifest 를 업데이트하게 한다면?
   manifest 를 업데이트하더라도 AT 를 바꿔 줄 책임을 지는 곳이 없다.
   과거 메타데이터를 담은 AT 가 그대로 넘어가니 인증이 계속 실패한다.

- Dream State: 2번에서 CLI 가 manifest 업데이트를 진행할 때, 우리 API 에서 신규 AT·RT 또한 함께 내려받도록 한다.
  - 그런데 이렇게 되면 우리 API 가 발급한 AT·RT 가 기존 Cognito 와 호환되어야 한다. 서명 검증 관점에서 가능한지 여부가 불확실하다.

#### 해당 분석을 서버 측에서 담당하지 말고 클라이언트 쪽으로 넘겨 보자.

먼저 Cognito 는 서버리스 인증 서버임을 알고 가자.

1. 부서에서 manifest 를 업데이트한다.
2. 그 부서의 manifest 가 업데이트되었다는 메시지가 데몬으로 전송된다(FCM 느낌).
3. 데몬이 메시지를 수신하고 manifest 를 동기화한다.
   만일 데몬이 꺼져 있었다면? 데몬이 켜질 때 메시지함을 조회해서 manifest 업데이트가 있으면 동기화를 진행한다.

- 우리 자체 인증 서버를 두지 않고 외부 서버리스 인증 서버를 쓰면 외부 의존성이 너무 많아진다.
  - FCM 같은 푸시 인프라가 필요해지고, Cognito 자체에서는 우리 사용자 DB 에 접근할 수 없어 Lambda 등의 우회 방법을 써야 하며,
    인증 책임은 ALB 또는 Gateway 에 또 한 겹으로 놓인다.
  - 이렇게 다 한다고 하더라도 인증 책임을 한곳에서 관리할 수가 없고, 구성 요소마다 장애 모드가 따로 생긴다.

#### 결론은?

애초에 인증 계층을 백엔드의 Spring Security 로 따로 레이어를 두면 편하게 해결될 것이라 생각한다.

- FCM 을 통해 클라이언트 측에서 분석할 이유가 없어진다.
- manifest 메타데이터를 담은 토큰을 쉽게 내려보내 줄 수 있다.
- Cognito 는 자체 유저 DB 를 사용하기 때문에 우리 유저 DB 에 접근하거나 동기화하려면 또 여러 복잡한 동작이 필요해지지만,
  애초에 백엔드 코드베이스에 인증 계층을 두면 바로 유저 DB 로 접근할 수 있으므로 쉽게 해결된다.

## Decision

- **인증·인가 계층을 백엔드 애플리케이션 안의 Spring Security 필터 체인에 둔다.**
  Cognito User Pool 을 인증 서버로 쓰지 않는다. ALB 는 TLS 종료와 라우팅만 하고 토큰을 검사하지 않는다.
  "이 요청이 왜 통과했는가" 의 답이 한 코드베이스 안에 있어야 한다.
- **AT·RT 를 우리가 직접 발급하고 검증한다.** 서명 키는 우리가 보유한다.
  - AT 는 **단수명 JWT** 다. 클레임에 tenant·member·role 과 **적용 중인 manifest revision** 을 담는다.
  - RT 는 DB 에 저장하는 **불투명 토큰**이며 사용 시 회전한다. 폐기가 가능해야 하므로 상태를 갖는다.
  - ADR 0003 이 상태 없는 JWT 를 탈락시킨 근거("이 API 의 핵심 동작은 폐기다")는 그대로 유효하다.
    설치 자격증명(`pit_`·`ptt_`)은 계속 불투명 토큰이고 해시만 저장한다. 단수명 JWT 는 **사용자 세션 AT 에만** 적용하며,
    폐기 경로는 RT 회전과 installation 폐기가 계속 담당한다.
- **manifest revision 대조를 애플리케이션이 한다.** 사용자 세션 AT 가 실리는 **관리자 API 경로**에서
  AT 클레임의 revision 과 DB 의 활성 manifest `version`(tenant 당 하나 — ADR 0004 의 부분 유니크
  인덱스)을 비교하고, 어긋나면 전용 에러 코드로 끊어 클라이언트에게 재동기화를 지시한다.
  **텔레메트리(OTLP) 경로에는 적용되지 않는다** — 그 경로의 `Authorization` 은 불투명 `ptt_` 라
  클레임이 없다. 재동기화는 별도 엔드포인트가 담당한다.
- **manifest 재동기화 응답이 새 AT·RT 를 함께 내려준다.** manifest 갱신과 토큰 재발급을 한 응답, 한 트랜잭션으로 묶는다.
  Context 의 Dream State 가 그대로 성립한다 — 발급자가 우리이므로 호환성 문제가 없다.
  이로써 "AT 를 누가 바꿔 주나" 라는 딜레마가 사라진다. 새 토큰은 **manifest 적용이 끝났다는 증거**이고,
  적용에 실패한 클라이언트는 낡은 토큰을 그대로 들고 있으므로 계속 거부된다(fail-closed).
- **manifest 변경을 push 로 알리지 않는다.** FCM 도, 오프라인 데몬용 메시지함도 두지 않는다.
  동기화는 다음 요청 또는 데몬 기동 시의 대조(pull)로 수렴시킨다.
- 사용자 비밀번호는 우리 DB 에 두고 Spring Security 의 `PasswordEncoder`(bcrypt·Argon2 같은 salted KDF)로 해싱한다.
  ADR 0003 의 결정론적 SHA-256 은 **256비트 난수 비밀에만** 쓰는 방식이며, 사람이 고른 값에는 쓰지 않는다.
- 관리자 API 의 정적 `X-Admin-Token`(`AdminAuthenticator`)은 이 계층이 서는 시점에 role 기반 인가로 대체한다.
  그때까지는 현재 방식을 그대로 둔다.

## Alternatives

### A. Cognito User Pool + ALB 인증 (원안)
- 장점: 인증 서버를 직접 운영하지 않는다. 비밀번호 저장·해싱·재설정·MFA·서명 키 회전을 관리형 서비스가 맡는다. ALB 에서 검증하면 무효 요청이 애플리케이션에 닿기 전에 걸러지고, hosted UI 로 로그인 화면 구현 비용도 없다.
- 단점: 사용자의 진실원이 Cognito user pool 과 `enrollment.members` 두 곳으로 갈라진다. Cognito 는 우리 DB 를 조회하지 못하므로 동기화에 Lambda 트리거가 필요하고, AT 에 manifest revision 을 심으려면 Pre Token Generation Lambda 가 또 필요하며 그 Lambda 도 우리 DB 를 봐야 한다. 무엇보다 **불일치를 발견한 시점에 우리가 새 AT·RT 를 서명해 줄 수 없다.**
- 탈락 이유: 이 ADR 이 풀려는 문제의 해법이 "우리가 토큰을 발급할 수 있는가" 에 달려 있는데, 관리형 IdP 는 바로 그것을 주지 않는다. Context 에 적은 두 갈래(AT 를 같이 바꾼다 / 바꾸지 않는다)가 모두 이 제약에서 막힌다. 그리고 인증 책임이 ALB·Cognito·Lambda·애플리케이션 네 곳으로 흩어져 한곳에서 관리할 수 없다.

### B. Cognito 를 유지하고 manifest 동기화를 클라이언트 push 로 넘긴다
- 장점: 요청 경로에서 대조하지 않으므로 인증 경로가 단순하고 ALB 검증만으로 끝난다. manifest 변경이 즉시 데몬에 전달되어 반영이 빠르다.
- 단점: FCM 같은 푸시 인프라, 오프라인 데몬용 메시지함, Cognito ↔ 우리 DB 동기화 Lambda 가 모두 새 의존성으로 들어온다. 게다가 동기화의 성공 여부가 클라이언트에 달려 있어 **fail-open** 이다. 푸시를 받지 못한 데몬은 낡은 manifest 로 계속 텔레메트리를 보내고, 서버는 그 사실을 알지 못한다.
- 탈락 이유: manifest 는 프롬프트·응답 수집 여부를 정하는 프라이버시 정책이다. 정책 **강화**가 클라이언트의 협조에 의존해서는 안 된다. 부서 B 의 엄격한 manifest 가 적용되지 않은 채 수집이 계속되는 상태를 서버가 감지조차 할 수 없다면, 그것은 동기화 지연이 아니라 정책 위반이다.

### C. 인증을 별도 애플리케이션(Spring Authorization Server 등)으로 분리한다
- 장점: 인증 책임이 한 배포 단위에 모이고, 표준 OAuth2·OIDC 를 구현하므로 나중에 서드파티 클라이언트나 SSO 를 붙이기 쉽다. 인증 트래픽만 따로 확장할 수 있다.
- 단점: revision 대조에 필요한 tenant·member·manifest 상태를 인증 서버가 또 조회해야 하므로 서버 간 호출이나 공유 모듈 의존이 생긴다. 토큰 발급 시점과 manifest 조회 시점이 갈라져 정합성 코드가 늘고, 운영할 서비스도 하나 늘어난다.
- 탈락 이유: 지금 필요한 것은 "우리 DB 를 보고 토큰을 발급한다" 하나이고, 그것은 이미 그 DB 를 쓰는 애플리케이션의 필터 체인에서 가장 짧게 끝난다. 표준 OIDC 발급자가 필요해지는 시점이 오면 그때 다시 본다 — 인증 로직이 Spring Security 위에 있으면 그쪽으로 옮겨 갈 경로가 남아 있다.

### D. revision 을 토큰에 담지 않고 매 요청마다 DB 를 조회한다
- 장점: 토큰과 DB 상태가 어긋날 여지가 애초에 없다. 인사이동이 다음 요청부터 즉시 반영되고, 토큰 재발급을 manifest 갱신에 묶을 필요도 없다.
- 단점: 텔레메트리 수집 경로는 API 요청과 비교되지 않는 처리량이다(ADR 0006). 요청마다 installation → member → team → 활성 manifest 를 조회하면 그 조회가 파이프라인의 병목이 된다. 캐시를 두면 "언제 무효화하나" 라는 같은 문제로 되돌아온다.
- 탈락 이유: 단수명 AT 의 클레임은 사실상 **서명된 캐시**이고, 무효화 시점이 토큰 만료로 자동 결정된다. 새 캐시 무효화 전략을 만드는 대신 이미 있는 만료 시각을 쓴다.

## Consequences/Tradeoffs
### Positive
- 인증 판단이 애플리케이션 필터 체인 한 곳에 모인다. 통과·거부의 근거를 한 코드베이스에서 읽을 수 있고, 통합 테스트로 검증할 수 있다.
- 우리 DB 가 사용자의 유일한 진실원이다. 초대·member·installation·manifest 가 같은 트랜잭션 안에 있으므로 IdP 동기화 코드가 아예 필요 없다.
- manifest 갱신과 토큰 재발급이 한 응답으로 묶여 fail-closed 다. 갱신에 실패하면 낡은 토큰이 남고, 낡은 토큰은 계속 거부된다. 프라이버시 정책이 클라이언트의 성실함에 의존하지 않는다.
- 푸시 인프라(FCM), Pre Token Generation Lambda, user pool 동기화 Lambda 가 전부 필요 없어진다. 외부 의존성과 그 각각의 장애 모드가 사라진다.
- 클레임에 tenant·role 이 들어오므로 대시보드의 tenant 격리와 역할 검사를 `@PreAuthorize` 같은 표준 수단으로 쓸 수 있다. 관리자 API 의 정적 키를 대체할 자리도 여기서 생긴다.
- 로그인·갱신·거부 경로를 Testcontainers + MockMvc 로 전부 재현할 수 있다. Cognito 스텁이나 테스트용 user pool 이 필요 없다.

### Negative
- 비밀번호와 서명 키를 우리가 책임진다. 해싱 파라미터, 키 보관·회전, 로그인 시도 제한, 비밀번호 재설정, 계정 잠금이 전부 우리 몫이 된다. 관리형 서비스가 기본으로 주던 것들이다.
  - 사용자는 사내 사원이라 규모가 작고 가입은 초대로만 열린다. 공개 회원가입 서비스와 위험 표면이 다르다고 판단했다.
- ALB 가 무효 토큰을 걸러 주지 않으므로 인증 실패 트래픽까지 애플리케이션이 받는다.
- 토큰 검증이 애플리케이션 필터에 있으므로 수집 파이프라인과 API 가 같은 인증 코드를 공유해야 한다. `:libs:` 에 인증 계층을 둘 자리가 필요하다(ADR 0002·0006).
- AT 수명 동안은 낡은 manifest revision 이 통과할 수 있다. 인사이동 반영이 즉시가 아니라 AT 만료(또는 다음 갱신) 시점이다.
  - AT 수명을 짧게 잡아 그 창을 줄인다. 즉시성이 필요한 정책 변경은 installation 폐기로 끊는다.
- 자체 발급 토큰에는 표준 OIDC 클라이언트가 그냥 붙지 않는다. 서드파티 연동이나 SSO 가 필요해지면 발급자 역할을 다시 설계해야 한다.
- 스키마의 `members.cognito_user_sub` 와 그 유니크 제약·인덱스가 쓰이지 않게 된다. 이 결정은 ADR 0003 follow-up 의 "관리자 인증을 Cognito 로 옮긴다" 를 **대체**한다.

## Follow-up
- **완료** — manifest 배정 단위는 **tenant** 로 확정했다(PROJ-80).
  `ux_manifests_tenant_active` 의 불변식이 유지되며, 부서 단위 배정은 `teams` 가 실제로 쓰이게 될 때
  별도 개정 ADR 로 다룬다. 결정 근거는 허브 크로스레포 ADR 로 남긴다(작성은 팀 합의 후 착수).
- **이 결정은 infra ADR-0008(ALB 인증 이원화, `Proposed`)의 ALB 인증 전제를 기각한다.**
  인증 종결 지점(애플리케이션)은 허브 크로스레포 ADR 로 확정하며, infra 쪽 Status 정리
  (`Superseded by` 허브 ADR)는 그 ADR 이 머지된 뒤 진행한다 — 크로스레포 결정이다.
- ADR 0003 follow-up 의 "웹 대시보드가 생기면 관리자 인증을 정적 키에서 Cognito 로 옮긴다" 는 이 ADR 로 대체된다.
  `X-Admin-Token` 과 `AdminAuthenticator` 는 이 계층이 서는 시점에 제거하고 관리자 API 를 role 기반 인가로 옮긴다.
- `members.cognito_user_sub` 컬럼·유니크 제약·인덱스를 제거하고 비밀번호 자격증명을 담을 자리를 만드는 마이그레이션이 필요하다.
  스키마의 진실원은 Flyway 이므로(ADR 0004) 새 버전 마이그레이션으로 처리하고, dbml 과 의도적으로 달라진 지점을 기록한다.
- AT 클레임 스키마(발급자, 수명, manifest revision 필드명)와 재동기화 응답 봉투는 CLI 계약이므로 `telemetryctl` 쪽과 함께 확정한다.
  봉투 분리(ADR 0003)를 유지해 manifest 안에 토큰을 넣지 않는다.
- 서명 키의 보관과 회전 절차(`kid` 를 통한 무중단 교체)를 정해야 한다. 키가 하나뿐이면 유출 시 전 사용자 재로그인이다.
- `GET /v1/manifest` 같은 재동기화 API 는 현재 enrollment 서버 명세의 범위 밖이다(§1).
  이 결정을 구현할 때 명세의 범위와 §2 엔드포인트 표를 함께 갱신한다.
- CLI 로그인(웹에서 로그인하고 콜백 URL 로 AT·RT 전달)의 콜백 주소 규칙과 PKCE 적용 여부는 별도 ADR 로 다룬다.
- 데몬 → 서버 구간이 어떤 자격증명을 싣는지(사용자 AT 인지 installation 자격증명인지)를 확정해 명세 §4 에 반영한다.
  현재 이 구간은 installation 에 귀속된 `telemetry_token` 을 쓴다 — `telemetryctl` 의 상위 전달 경로가
  그 토큰을 OTLP 헤더에 실어 보내고, 401/403 을 받으면 토큰을 무효화한 뒤 한 번 재시도한다.
  (클로드 코드 → 데몬 구간의 로컬 토큰은 이것과 별개인 **로컬 ingest 토큰**이다 — 위 「인증 흐름」 1번 참고.)
  이 인증 계층이 서면 데몬 → 서버 구간을 사용자 세션 AT 로 바꿀지, installation 귀속 `telemetry_token`
  을 유지할지 결정해 명세 §4 에 반영해야 한다.
- **fail-closed 주장의 한계 (미결)**: 재동기화 응답은 새 AT 와 manifest 를 한 응답으로 내려주지만,
  클라이언트에서 **새 AT 저장과 manifest 반영은 별개 동작이라 원자적이지 않다.**
  AT 는 저장됐는데 반영이 실패하면 낡은 설정인 채로 유효한 토큰을 들게 되어
  "적용에 실패한 클라이언트는 계속 거부된다" 가 성립하지 않는다. 채택 논의 때
  구현에 착수하기 전에 클라이언트의 원자 적용 프로토콜(반영 완료 후에만 새 AT 를 저장)을 계약으로
  정의하거나, fail-closed 문구를 서버 관점(서버는 낡은 revision 의 AT 를 거부한다)으로 한정해야 한다.
  **`telemetryctl` 과 함께 정하는 계약이다.**
- **보안 통제의 수용 기준 (미결)**: 직접 운영으로 떠안은 로그인 시도 제한(rate limit)·계정
  잠금(lockout)·서명 키 회전은 Negative 와 위 서명 키 항목이 존재만 언급할 뿐 수용 기준이
  결정문에 없다. 각 통제의 기준치와 담당을 구현 착수 전에 명시한다.
