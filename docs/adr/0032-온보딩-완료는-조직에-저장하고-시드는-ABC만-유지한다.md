# 0032. 온보딩 완료는 조직에 저장하고 시드는 A/B/C만 유지한다

## Status

Accepted — ADR 0029의 완료 시각 저장 위치와 ADR 0031의 기본 설치 조직 시드를 대체한다. 정책 확인·완료 조건·Docker 전용 실행은 유지한다.

## Context

조직 테이블에서 온보딩 완료 여부를 직접 확인할 수 있어야 한다.
사용자는 기본 로컬 개발 조직을 제거하고 A 시나리오를 온보딩 완료 상태로 제공하도록 요청했다.

## Decision

- Flyway의 다음 마이그레이션으로 `tenants.onboarding_completed_at`을 추가하고 기존 완료 시각을 이관한다.
  `tenants.onboarding_completed`는 완료 시각의 존재 여부를 계산하는 저장 생성 컬럼이다.
  완료 시각의 원본은 tenants 한 곳이며 기존 `organization_onboarding.completed_at`은 제거한다.
- 정책 확인자·시각과 완료자는 `organization_onboarding`에 유지한다. API 응답 형식은 유지하고
  조회·완료 처리는 tenants의 시각을 사용한다. 완료 재호출은 최초 완료 시각을 보존한다.
- 신규 A 시드는 정책 확인, 활성 수동 벤더 선택, 완료 시각을 함께 넣는다. B/C는 미완료다.
- 기본 설치 조직, `local-owner@example.com`, 별도 팀·manifest·고정 초대를 생성하는 코드는 제거한다.
  설치 시험은 A 시드의 초대 또는 관리자 API로 발급한 초대를 사용한다.
- 기존 개발 DB의 기본 설치 조직은 고정 ID와 slug를 검증한 뒤 관련 RDS·ClickHouse 데이터를 함께 제거한다.
  운영 Flyway에는 특정 개발 조직의 삭제나 A 완료 처리를 넣지 않는다.
  기존 A는 정책과 데이터를 보존한 채 완료 조건을 갖추고 완료 처리한다. B/C 및 다른 조직은 변경하지 않는다.
- 완료된 시드의 자동 덮어쓰기 금지는 유지한다. 기존 볼륨의 시드 보정은 명시적으로 수행한다.

## Alternatives Considered

별도 boolean과 시각을 각각 수정하면 불일치가 생길 수 있다. 생성 컬럼은 시각과 완료 여부를 항상 일치시킨다.
완료 시각을 두 테이블에 복제하면 API와 SQL 조회가 서로 다른 원본을 읽게 된다.
개발 데이터 삭제를 운영 마이그레이션에 넣으면 DDL과 로컬 데이터 관리의 범위가 섞인다.

## Consequences/Tradeoffs

### Positive

조직 조회만으로 완료 여부를 알 수 있고 A는 로그인 직후 완료 상태를 재현한다.
시드 조직을 A/B/C로 단순화한다.

### Negative

기존 완료 시각 컬럼을 옮기므로 마이그레이션과 API 코드를 함께 배포해야 한다.
완료 여부를 SQL로 바꿀 때는 생성 컬럼 대신 완료 시각을 수정해야 한다.
기존 고정 초대 코드를 쓰던 로컬 설치 절차는 새 초대를 발급받아야 한다.
