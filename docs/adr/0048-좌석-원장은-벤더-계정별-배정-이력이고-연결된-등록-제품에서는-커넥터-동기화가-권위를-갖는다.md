# 0048. 좌석 원장은 벤더 계정별 배정 이력이고 연결된 등록 제품에서는 커넥터 동기화가 권위를 갖는다

## Status

Proposed — 커넥터 구현이 서고 그 동기화가 벤더 문서의 요청·응답을 재현한 모의 서버로 검증되면 Accepted.
[ADR 0026](0026-사용자-인증으로-프론트-관리-요청을-연결한다.md)의 "벤더 좌석 제어는 구현하지 않는다"를 대체한다 — 벤더 연결과 좌석 원장을 두고,
제어(회수·복원)는 이 원장 위에서 커넥터가 지원하는 만큼만 한다. "실제 청구액은 구현하지 않는다"는 이 결정의 범위 밖이다.

## Context

- 조직의 계약은 등록 제품(`managed_vendors`)별 버전 이력(`vendor_contract_versions`)이고 등급마다 **구매 수량**(`tiers[].seats`)을 담는다.
  누가 좌석을 갖고 있는지는 어디에도 없다. 구성원 화면의 좌석 상태는 전부 `unknown`, 회수 후보는 원천이 없어 `unavailable`이다.
- 구 `contracts`·`contract_memberships`는 기존 기간 약정이다. 좌석 계약 관리에서 고치거나 환산하지 않는다(module-map §2).
- 벤더마다 좌석 API가 다르다(`docs/vendor-connector-evidence.md`의 "결론 — 구현 방식"):
  - 좌석 조회를 API로 할 수 있는 것은 Claude Enterprise, Cursor Enterprise, GitHub Copilot(전 플랜), Gemini Code Assist(전 플랜)다.
    Claude Team, OpenAI, Cursor Teams, `other`는 공개 API가 없거나 확인할 수 없다. **같은 제품이라도 계약 플랜에 따라 갈린다.**
  - 식별자가 다르다. Copilot 좌석은 GitHub 로그인뿐이고 이메일이 없다. 나머지는 이메일을 준다(Claude·Cursor는 벤더 내부 ID도).
  - 요청 성공이 완료가 아니다. Copilot 회수는 주기 말에 효력이 생기고(`pending_cancellation_date`), Claude 복원은 초대 수락 뒤에 끝난다.
  - 등급(Standard·Premium)을 주는 API는 없다. 활동 시각은 벤더마다 있거나 없고, 없다고 미사용인 것은 아니다.
  - IdP(SCIM·JIT)가 구성원을 관리하는 조직에서는 벤더가 쓰기를 거절한다.
- 관리 명령은 enrollment-api가 받고 쓰기 소유는 `:libs:enrollment-persistence`다. 비밀은 AES-GCM 암호문으로 저장하는 관례가 있다(관리 응답·메일 outbox).
  백그라운드 작업은 enrollment-api 안의 주기 작업과 DB 선점(`FOR UPDATE SKIP LOCKED`)으로 돈다(메일 발송, ADR 0037).
- 벤더 관리자 자격증명이 있는 테스트 조직은 없다. 자격증명이 없다는 사실이 원천의 설계를 정하지 않는다.

정하지 않으면 생기는 일: 좌석 원천이 화면마다 달라지고, 구매 수량이나 사용 이벤트 유무가 배정·미사용으로 쓰인다.
커넥터가 들어와도 수동 기록과 벤더 값이 같은 좌석에 대해 어긋날 때 무엇이 맞는지 정할 규칙이 없다.

## Decision

### 1. 좌석과 식별

- **좌석**은 조직의 등록 제품 하나에서 **벤더 계정** 하나가 차지하는 자리다. 구매 수량은 좌석이 아니다 — 원장을 수량으로 채우지 않는다.
- **벤더 계정 키**는 제품의 계정 종류로 정규화한 문자열이다: 이메일(소문자) 또는 GitHub 로그인(소문자). 계정 종류는 제품의 커넥터 설명이 정하고,
  커넥터가 없는 제품은 이메일이다. 벤더 내부 ID(제어 호출에 필요한 것)는 키가 아니라 따로 남긴다.
- **`seatAssignmentId`**는 (등록 제품, 벤더 계정 키)마다 하나이고 바뀌지 않는다. 해제된 좌석을 같은 계정이 다시 받으면 같은 ID가 다시 보유 상태가 된다 —
  회수와 복원이 같은 좌석을 가리키고 이력이 한 줄로 이어진다.

### 2. 상태·이력·판

| 상태 | 뜻 | 좌석을 차지하는가 |
| --- | --- | --- |
| `assigned` | 배정 | 예 |
| `pending_assignment` | 배정을 요청했고 벤더가 아직 끝내지 않음(초대 수락 전) | 예(대기 중 초대도 좌석을 잡는다) |
| `pending_release` | 해제가 예정됨(주기 말 효력 등). `release_effective_on`이 예정일 | 예 |
| `released` | 해제 | 아니오 |

전이는 원천(§3)마다 허용 범위가 다르다.

| 원천 | 허용 전이 |
| --- | --- |
| 커넥터 동기화 | 벤더가 보고한 보유 상태로 무엇에서든. 목록에 없는 보유 좌석 → `released` |
| 수동·CSV | 없음 → `assigned`, `released` → `assigned`, `assigned` → `released` |
| 벤더 제어 결과 | `assigned` → `pending_release`·`released`, `pending_release` → `assigned`·`released`, `released` → `pending_assignment`·`assigned`, `pending_assignment` → `assigned` |
| 관리자 조치 확인 | `assigned`·`pending_release` → `released`, `released` → `assigned` |

- **판**(`version`)은 좌석마다 1부터 센다. 상태·원천·구성원 연결·등급·메모가 바뀔 때마다 1 오른다. 수동 명령은 `expectedVersion`으로 충돌을 막는다.
  벤더 활동 시각은 관측이라 판을 올리지 않는다.
- **이력**은 판마다 한 행이다 — 바뀐 뒤의 상태·원천·구성원 연결·등급·메모와 행위자(구성원·동기화 실행·작업 중 하나). 지우지 않는다.

### 3. 원천과 우선순위

원천은 `connector`(동기화), `manual`(관리자 단건), `csv`(가져오기), `vendor_control`(벤더 제어 호출의 결과), `admin_action`(관리자가 벤더 콘솔에서 한 조치의 확인)이다.
좌석 행마다 **마지막으로 상태를 정한 원천**을 남긴다.

권위는 등록 제품 단위로 정하고, 판정의 입력은 "그 제품·계약 플랜에 커넥터가 있는가"와 "활성 연결이 있는가" 둘이다.

| # | 등록 제품 | 권위 | 수동·CSV의 배정·해제 | 수동 보정(구성원 연결·계약 등급·메모) | 커넥터 동기화 |
| --- | --- | --- | --- | --- | --- |
| 1 | 커넥터가 없는 플랜 | 수동·CSV | 허용 | 허용 | 없음 |
| 2 | 커넥터가 있는 플랜, 활성 연결 없음 | 수동·CSV(**임시**) | 허용 — 행은 임시로 드러난다 | 허용 | 없음 |
| 3 | 활성 연결 있음 | 커넥터 | 거부(`409 connector_managed`) | 허용 | 성공한 동기화가 목록 전체로 원장을 맞춘다 |
| 4 | 활성 연결 있음, 마지막 동기화 실패 | 커넥터(마지막 성공 값, **낡음**) | 거부 | 허용 | 실패한 동기화는 원장을 바꾸지 않는다 |

- 3행의 "맞춘다": 목록의 계정은 벤더가 보고한 상태가 되고(원천 `connector`), 목록에 없는 보유 좌석은 `released`가 된다. **수동·CSV 원천의 행도 같다** —
  같은 계정이면 원천이 `connector`로 바뀌고, 목록에 없으면 해제된다. 동기화는 목록을 끝까지 읽었을 때만 반영한다. 부분 목록으로 해제하지 않는다.
- 동기화가 덮지 않는 것: 관리자가 정한 구성원 연결, 메모, 계약 등급 연결.
- 수동·CSV는 커넥터가 있는 플랜에서 **연결 전의 임시 기록**이다. 기본 주 원천이 아니다. 연결을 만들면 수동 배정·해제는 그 순간부터 거부되고, 첫 성공한 동기화가 임시 행을 대체한다.
- 연결을 지우면 원장은 그대로 두고 권위가 2행으로 돌아간다. 커넥터 원천 행은 마지막 동기화의 값으로 남고, 관리자는 그것을 수동으로 고칠 수 있다.
- 벤더 제어·관리자 조치 확인은 원천이 무엇이든 해당 좌석의 전이만 한다. 로컬 원장만 바꿔 제어 성공으로 기록하지 않는다 — 벤더 호출이 성공했거나 관리자가 조치를 확인했을 때만 바꾼다.

### 4. 구성원 연결

- 이메일 계정은 조직에 그 이메일(대소문자 무시)의 구성원이 **정확히 하나**면 그 구성원에 잇는다(`email_match`). 없거나 여럿이면 잇지 않는다.
  연결 근거를 행에 남긴다. 동기화는 매번 이 규칙을 다시 적용한다.
- 관리자가 정한 연결(`admin`)이 우선하고 동기화가 바꾸지 않는다. 관리자는 "잇지 않음"도 정할 수 있다(연결 근거 `admin`, 구성원 없음).
- GitHub 로그인 계정은 자동으로 잇지 않는다. 관리자가 정한다.
- 잇지 않은 좌석도 원장에 남고 제품의 보유 좌석 수에 든다. 구성원별 좌석과 회수 후보에는 들지 않고 "미연결"로 따로 보인다.
- 연결 대상은 같은 조직의 구성원뿐이다.

### 5. 등급·계약

- 좌석은 등록 제품에 속하고, 계약은 그 제품의 현재 계약이다.
- 벤더가 등급을 주면 벤더 등급으로 남긴다. 계약 등급(`tierId`)은 수동 기록만 정하고, 기록 시점의 현재 계약에 있는 등급이어야 한다.
  모르면 null이다 — 구매 수량이나 등급 순서로 추정하지 않는다. 계약 정정이 등급 ID를 새로 만들면 이전 연결은 "등급 모름"으로 읽는다(원장을 고쳐 쓰지 않는다).

### 6. 벤더 연결과 자격증명

- **연결**은 등록 제품 하나에 커넥터 하나다. 활성 연결은 제품마다 하나다. 커넥터는 제품과 현재 계약의 플랜으로 고른다 — 계약이 없거나 그 플랜에 커넥터가 없으면 연결을 만들 수 없다.
  비밀이 아닌 설정(조직 이름·청구 계정 등)은 평문, 자격증명은 암호문이다.
- **저장**: 자격증명은 AES-256-GCM 암호문이고 추가 인증 데이터에 조직·등록 제품·연결 ID를 묶는다(행 사이로 옮기면 풀리지 않는다).
  키는 enrollment-api의 설정 `pulsemetry.vendor-connections.credential-keys`(키 ID → Base64 32바이트)와 현재 키 `credential-key-id`다. 행은 암호화에 쓴 키 ID를 남긴다.
  관리 응답 암호화 키와 따로 둔다. dashboard-api는 키를 갖지 않고 암호문 열을 읽지 않는다.
- **노출**: 응답·로그·오류 메시지에 자격증명을 싣지 않는다. 응답은 설정됨 여부와 갱신 시각만 낸다. 연결 명령은 멱등 응답 기록을 남기지 않는 방식(PUT·DELETE)이라 요청 본문이 저장되지 않는다.
- **교체**: 새 자격증명으로 덮고 확인 상태를 `unverified`로 되돌린다. 커넥터나 설정이 바뀌면 동기화 기록(마지막 성공·실패)도 비운다 — 다른 대상의 기록이다.
- **삭제**: 암호문을 즉시 지운다(NULL). 행은 이력으로 남는다. 등록 제품을 보관하면 그 제품의 연결도 같은 트랜잭션에서 지운다.
- **키 회전**: 새 키를 더하고 현재 키로 바꾼다. 옛 키는 그 키로 암호화된 행이 남아 있는 동안 설정에 둔다 — 자격증명을 교체하면 현재 키로 다시 암호화된다.
  행의 키 ID가 설정에 없으면 그 연결의 호출은 `credential_key_unavailable`로 실패한다(평문으로 떨어지지 않는다).
- **확인**: 커넥터의 확인 호출(읽기 하나) 결과를 `verified`·`invalid_credentials`·`insufficient_permission`·`unavailable`로 남긴다. 호출은 트랜잭션 밖에서 하고,
  그 사이 연결이 바뀌었으면 결과를 쓰지 않는다(`409 version_conflict`).

### 7. 동기화의 위치·중복 방지·신선도

- 위치는 **enrollment-api 안의 주기 작업**이다. 새 배포 단위를 만들지 않는다. 연결 행을 `FOR UPDATE SKIP LOCKED`로 선점하고 선점 기한을 둔다.
  연결마다 진행 중인 실행은 하나다(부분 유일 색인). 기한이 지난 실행은 다음 선점이 `abandoned`로 닫는다.
- 실행 기록은 시작·끝·결과·오류 코드·목록의 좌석 수·바뀐 좌석 수다. 성공은 연결의 마지막 성공 시각을, 실패는 마지막 실패 시각과 오류 코드를 바꾼다.
- **신선도**는 제품 단위다. 연결이 있고 성공한 동기화가 없으면 `pending`(값 없음), 마지막 시도가 실패면 `failing`, 마지막 성공이 조회 앱의 신선도 기준보다 오래면 낡음이다.
  낡은 값은 내되 낡았다고 표시한다(가용성 `partial`, 사유 `seat_sync_failing`·`seat_sync_outdated`). 연결 전 임시 기록은 사유 `seat_source_provisional`이다.
- 주기·선점 기한·호출 시간 제한·신선도 기준은 기본값 없는 필수 설정이다.

### 8. 커넥터 포트

- `:libs:vendor-connector`(`com.team376.pulsemetry.connector.vendor`)가 인터페이스와 값 타입을 둔다. Spring에 의존하지 않는다. 구현도 이 모듈에 두고 조립은 앱이 한다.
- **커넥터 설명**은 제품·플랜·계정 종류·필요한 설정과 기능 두 벌이다 — 벤더 문서가 근거를 준 기능(`supported`)과 이 저장소가 구현한 기능(capability ⊆ supported).
  기능은 `seat_list`·`seat_release`·`seat_restore`·`billing`이다. 호출 없이 읽는 값이라 조회 앱도 이것만 본다. 문서 근거가 없는 기능은 구현으로 선언하지 못한다.
- **지원하지 않는 기능은 타입으로 드러낸다** — 구현이 해제·복원·청구 인터페이스를 갖지 않는다(null). 설명의 capability와 구현이 다르면 조립이 실패한다.
  화면의 실행 가능 여부는 capability(구현)로 판단한다 — 벤더가 지원해도 구현하지 않은 기능을 가능하다고 내지 않는다.
- 실패는 종류로 나눈다: 자격증명 무효·권한 부족·IdP 관리·벤더 거절(영구), 한도 초과·일시 장애·응답 해석 불가(일시). 메시지에 자격증명을 싣지 않는다.
- 제어 결과는 완료·예정(효력일)·수락 대기로 나눈다. 요청 성공을 완료로 바꾸지 않는다.

## Alternatives Considered

### A. 수동·CSV를 주 원천으로 두고 커넥터는 보조로 대조만 한다
- 장점: 자격증명 없이도 곧바로 채울 수 있다. 규칙이 하나다.
- 단점: 커넥터가 있는 제품에서 벤더가 이미 아는 값을 사람이 따라 적는다. 회수·복원의 벤더 결과가 원장에 들어올 길이 없다.
- 탈락 이유: 벤더가 진실원인 제품에서 원장이 벤더와 어긋나는 것이 기본이 된다.

### B. 원천마다 행을 따로 두고 조회 때 합친다
- 장점: 원천의 값을 잃지 않는다.
- 단점: 한 좌석에 값이 둘이고 조회마다 합병 규칙이 돈다. `seatAssignmentId`와 판이 원천마다 갈라져 충돌 제어가 성립하지 않는다.
- 탈락 이유: 좌석 하나에 행 하나, 이력으로 원천을 남기는 편이 목록·상세·요약을 같은 값으로 만든다.

### C. 보유 구간마다 새 `seatAssignmentId`
- 장점: 구간이 곧 행이라 이력이 단순하다.
- 단점: 복원이 회수한 좌석과 다른 ID를 만든다. 회수 작업과 화면이 옛 ID를 들고 있게 된다.
- 탈락 이유: 회수·복원이 같은 좌석을 가리켜야 한다.

### D. 자격증명을 관리 응답 암호화 키로 암호화한다
- 장점: 키가 하나 준다.
- 단점: 24시간 재시도 응답과 장기 자격증명은 수명·노출·회전 주기가 다르다. 한 키의 유출이 둘을 함께 연다.
- 탈락 이유: 비밀의 종류마다 키를 나누는 기존 관례(메일 outbox 키)를 따른다.

### E. 동기화를 별도 작업 앱으로 둔다
- 장점: 관리 HTTP와 동기화의 장애가 섞이지 않는다.
- 단점: 새 배포 단위와 그 계정·스케줄이 필요하다.
- 탈락 이유: 메일 발송과 같은 방식(앱 안의 주기 작업 + DB 선점)으로 충분하다.

## Consequences/Tradeoffs

### Positive
- 좌석 수·구성원별 좌석·회수 후보가 하나의 원장에서 나온다. 구매 수량과 배정이 섞이지 않는다.
- 커넥터가 있는 제품은 벤더가 진실원이고, 없는 제품만 사람이 적는다. 연결 전 기록은 임시로 드러나 주 원천으로 굳지 않는다.
- 자격증명은 enrollment-api 밖으로 평문이 나가지 않고, 조회 앱은 비밀 없이 연결 상태를 낸다.

### Negative
- 커넥터가 있는 제품에서 연결을 만든 뒤 첫 동기화가 성공할 때까지 좌석 값이 비거나 임시 값이다.
- Copilot처럼 로그인만 주는 벤더는 관리자가 구성원을 이어야 구성원별 좌석과 회수 후보가 나온다.
- 암호화 키가 하나 늘고, 옛 키를 언제 뺄 수 있는지는 운영이 행의 키 ID로 확인해야 한다.

## Follow-up
- 커넥터 구현(벤더 문서의 요청·응답을 재현한 모의 서버 검증)과 동기화 작업, 실계정 검증 절차.
- 수동 단건·CSV 명령, 좌석 조회와 회수 후보, 회수·복원·관리자 조치 확인.
- 계약 정정 사이에 등급 ID를 유지하는 규칙. 옛 키로 암호화된 행을 한 번에 다시 암호화하는 운영 명령.
