# 0037. 메일은 outbox에 적재하고 enrollment-api의 발송 작업이 SMTP로 보낸다

## Status

Accepted — [ADR 0026](0026-사용자-인증으로-프론트-관리-요청을-연결한다.md)의 "초대는 코드 발급이며 이메일 발송 완료나 queued로 표시하지 않는다"를 부분 대체한다. 그 밖의 ADR 0026 결정은 유효하다.
발송 구현이 SMTP 하나라는 결정과 그에 딸린 설정·`send-timeout`의 뜻·`failure_detail`·`sent`의 뜻은 [ADR 0057](0057-배포-환경의-메일은-SES-API로-보내고-발송-구현은-설정으로-고른다.md)이 부분 대체한다 — 발송 구현은 설정으로 고르는 `smtp`(로컬·테스트)·`ses`(배포)다. outbox·선점·임대·상태·중복 방지 키·본문 암호화·공개 실패 코드 어휘·모듈 배치는 유효하다.

## Context

이 서버는 메일을 보내지 않는다. 초대는 코드를 발급해 응답으로 돌려줄 뿐이고(ADR 0026),
도입 문의(`POST /v1/inquiries`)는 저장만 한다(`docs/enrollment-server-spec.md` §2.2).
발급한 코드를 대상자에게 전하는 일과 접수된 문의를 담당자가 아는 일이 모두 시스템 밖에 있다.

이미 정해진 제약은 다음과 같다.

- 업무 쓰기는 `:libs:enrollment-persistence`의 저장소가 한 트랜잭션으로 한다(`ManagementStore.command`, `InquiryStore.receive`).
  초대 코드는 DB에 해시만 있고 원문은 발급 응답에만 있다. 멱등 재시도 응답은 AES-GCM으로 암호화해 저장한다(ADR 0026).
- 라이브러리 모듈은 Spring 스테레오타입과 Boot starter를 갖지 않는다. 조립은 앱이 한다(ADR 0011).
- 배포 단위는 enrollment-api · dashboard-api · telemetry-ingest · retention-worker 넷이다(`docs/module-map.md` §1).
  enrollment-api는 여러 인스턴스로 뜰 수 있다.
- 저장소에 메일 설정이 없다. 운영 SMTP 자격증명과 발신 도메인은 이 저장소 밖에서 주입된다.

정하지 않으면 생기는 일: 업무 쓰기와 발송을 한 요청 안에서 이어 하면 SMTP 지연·장애가 관리 명령의 응답 시간과 성공 여부가 된다.
트랜잭션 밖에서 보내면 "저장됐는데 메일이 없다"와 "메일이 나갔는데 롤백됐다"가 모두 생긴다.
여러 인스턴스가 같은 메일을 보내지 않게 할 규칙도, 실패를 다시 시도할 규칙도 없다.
메일 본문에 초대 코드가 들어가면 코드 원문이 평문으로 DB에 남는다.

## Decision

- **메일은 업무 쓰기와 같은 트랜잭션에서 `enrollment.mail_outbox`에 적재한다.** 적재 연산(`MailOutbox.enqueue`)은 자기 트랜잭션을 열지 않는다.
  업무 쓰기가 롤백되면 메일도 없고, 커밋되면 메일도 있다. 요청 처리 중에는 SMTP에 말하지 않는다.
- **발송은 enrollment-api 안의 주기 작업이 한다.** 새 배포 단위를 만들지 않는다.
  작업은 `FOR UPDATE SKIP LOCKED`로 메일을 **하나씩** 선점해 `sending`으로 바꾸고 커밋한 뒤 트랜잭션 밖에서 SMTP로 보내고, 결과를 다시 기록한다.
  인스턴스가 여럿이어도 한 메일을 선점하는 작업은 하나다.
- **상태**는 `queued → sending → sent | failed`와 `queued → cancelled`다.
  - 일시 실패(연결 실패, 인증 실패, SMTP 4xx)는 `queued`로 되돌리고 재시도 간격 뒤에 다시 시도한다. 시도 횟수가 최대 시도에 닿으면 `failed`다.
  - 영구 실패(SMTP 5xx, 주소 형식 오류)는 재시도하지 않고 바로 `failed`다.
  - 실패 사유는 분류 코드(`recipient_rejected` · `message_rejected` · `invalid_address` · `recipient_deferred` · `smtp_deferred` · `smtp_auth_failed` · `smtp_unavailable` · `send_error` · `outcome_unknown`)와 SMTP 응답 코드만 남긴다. 서버 응답 원문과 예외 메시지는 저장하지 않는다.
  - 아직 보내지 않은(`queued`) 메일만 취소할 수 있다. `sending`인 메일은 취소하지 못한다.
- **선점에는 임대 시간이 있다.** 작업이 죽어 `sending`에 남은 메일은 임대가 끝나면 다시 선점된다. 임대는 SMTP 제한 시간의 네 배다(연결·인증·전송·응답).
  최대 시도를 이미 채운 채 임대가 끝난 메일은 다시 보내지 않고 `outcome_unknown`으로 닫는다.
  따라서 보장은 **적어도 한 번**이다 — SMTP가 받은 직후 결과를 기록하기 전에 작업이 죽으면 같은 메일이 한 번 더 나갈 수 있다.
  "한 번만"은 동시에 도는 작업들 사이의 보장이다.
- **중복 방지 키**(`dedup_key`, 유일)가 메일의 정체다. 같은 키로 다시 적재하면 새 행을 만들지 않고 기존 메일의 상태를 돌려준다.
  실패하거나 취소된 메일을 같은 키로 되살리지 않는다. 다시 보내려면 업무 쪽에서 새 대상(예: 재발급한 초대)의 새 키로 적재한다.
- **본문은 AES-256-GCM으로 암호화해 저장하고 끝나면 지운다.** 키는 메일 전용 설정(`pulsemetry.mail.encryption-key`)이고 행 ID를 AAD로 묶는다.
  `sent` · `failed` · `cancelled`가 되는 같은 문장에서 암호문을 NULL로 바꾼다. 제목·수신자·종류는 평문이다 — **제목에는 비밀을 넣지 않는다.**
  본문과 제목은 로그에 남기지 않는다. 로그에는 메일 ID·종류·상태·실패 코드만 쓴다.
- **모듈 배치**: 테이블과 적재·선점·결과 기록(`MailOutbox`), 선점 → 발송 → 기록의 순서(`MailDispatcher`), 발송 포트(`MailTransport`)는 `:libs:enrollment-persistence`에 둔다.
  SMTP 구현(`SmtpMailTransport`)과 주기 실행(`MailDispatchJob`), 설정 바인딩은 `:apps:enrollment-api`가 갖는다. `spring-boot-starter-mail`은 그 앱에만 붙인다.
- **설정**: `pulsemetry.mail.enabled`(기본 false). 켜면 SMTP 호스트·포트·계정·암호·STARTTLS 여부, 발신 주소, 암호화 키, 발송 주기, 재시도 간격, 최대 시도, SMTP 제한 시간이 모두 필요하다.
  운영 수치에 배포 기본값을 두지 않는다 — 하나라도 비면 기동하지 않는다.
  꺼져 있으면 outbox 빈이 없다. 업무 쓰기는 메일을 적재하지 않고, 발송하지 않았다는 사실을 그대로 드러낸다(적재됨으로 표시하지 않는다).
- **ADR 0026의 부분 대체**: 초대는 여전히 코드 발급이고 발급 결과의 의미는 바뀌지 않는다. 메일 발송은 발급과 별개의 상태로 나타낸다.
  발급 성공을 발송 완료로 표시하지 않는다. `sent`는 SMTP 서버가 메시지를 받았다는 뜻이고 수신함 도착을 뜻하지 않는다.
  어떤 업무가 무엇을 적재하고 그 상태를 어떤 응답 필드로 내는지는 그 업무의 명세가 정한다.

## Alternatives Considered

### A. 업무 요청 안에서 SMTP로 바로 보낸다
- 장점: 테이블과 작업이 필요 없다. 결과를 응답에 바로 실을 수 있다.
- 단점: SMTP 지연이 관리 명령의 응답 시간이 된다. 트랜잭션 안에서 보내면 롤백돼도 메일은 나가고, 밖에서 보내면 커밋 뒤 실패를 다시 시도할 곳이 없다.
- 탈락 이유: 업무 쓰기와 발송의 원자성·재시도를 요청 하나로는 만들 수 없다.

### B. 발송 전용 배포 단위를 새로 만든다
- 장점: 발송 부하와 장애가 API 프로세스와 분리된다.
- 단점: 배포 단위가 하나 늘고 그 실행 환경(태스크 정의·스케줄)이 이 저장소 밖에서 준비돼야 한다. 메일 양은 초대·문의·안내 수준이다.
- 탈락 이유: 같은 DB를 보는 작업 하나를 위해 배포 단위를 늘릴 근거가 없다. `SKIP LOCKED` 선점은 작업이 어느 프로세스에 있든 같은 보장을 준다 — 나중에 옮겨도 테이블과 연산은 그대로다.

### C. 메시지 브로커에 발송 요청을 싣는다
- 장점: 재시도·지연 전달을 브로커가 맡는다.
- 단점: 저장소에 브로커가 없다. DB 커밋과 브로커 발행 사이의 원자성을 맞추려면 결국 outbox가 필요하다.
- 탈락 이유: 새 인프라를 들이고도 outbox를 없애지 못한다.

### D. 본문을 평문으로 저장하고 발송 뒤에 지운다
- 장점: 암호화 키가 필요 없다.
- 단점: 발송을 기다리거나 재시도 중인 동안 초대 코드 원문이 DB·백업·복제본에 평문으로 남는다. 초대 코드는 해시만 저장한다는 기존 규칙과 어긋난다.
- 탈락 이유: 대기 시간이 길어질수록(장애 중일수록) 노출이 길어진다.

### E. 관리 응답 암호화 키를 같이 쓴다
- 장점: 주입할 키가 하나 줄어든다.
- 단점: 메일은 관리 기능이 꺼진 배포에서도 쓸 수 있어야 한다(문의 통지). 키를 같이 쓰면 두 기능의 키 교체가 묶인다.
- 탈락 이유: 용도가 다른 비밀은 키를 나눈다.

## Consequences/Tradeoffs

### Positive
- 업무 쓰기와 메일의 존재가 한 트랜잭션으로 묶인다. SMTP 장애가 관리 명령을 실패시키지 않는다.
- 인스턴스 수와 무관하게 한 메일을 동시에 둘이 보내지 않는다. 실패는 기록되고 다시 시도된다.
- 초대 코드가 메일 본문에 들어가도 DB에는 암호문으로만, 발송이 끝날 때까지만 있다.
- 메일을 쓰는 업무(초대·문의 통지·설치 안내)가 같은 적재 연산과 같은 상태 어휘를 쓴다.

### Negative
- 발송은 요청보다 늦다(최대 발송 주기만큼). 화면은 발급과 발송을 다른 상태로 보여 줘야 한다.
- 작업이 SMTP 수락 직후에 죽으면 같은 메일이 두 번 나갈 수 있다.
- 주입할 설정이 늘어난다(SMTP 자격증명·발신 주소·암호화 키·운영 수치). 암호화 키를 바꾸면 대기 중인 메일의 본문을 읽지 못한다 — 그 메일은 `send_error`로 재시도하다 `failed`가 된다.
- 끝난 메일의 행(수신자 주소 포함)은 남는다. 보존 기간과 정리는 이 결정에 없다.
- `sent`는 SMTP 수락까지만 말한다. 반송·스팸 분류는 알 수 없다.

## Follow-up
- 초대 발급·재발급과 문의 접수가 메일을 적재하고 발송 상태를 응답·목록에 낸다.
- 운영 SMTP 자격증명·발신 도메인·암호화 키와 운영 수치의 주입.
- 끝난 outbox 행의 보존 기간과 정리.
