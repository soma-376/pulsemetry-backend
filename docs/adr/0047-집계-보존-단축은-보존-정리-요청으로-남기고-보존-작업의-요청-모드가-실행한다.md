# 0047. 집계 보존 단축은 보존 정리 요청으로 남기고 보존 작업의 요청 모드가 실행한다

## Status

Proposed — [ADR 0024](0024-조직별-보존-삭제-경계는-RDS-가-진실원이고-분석-INSERT-는-ClickHouse-fence-를-서버에서-다시-검사한다.md)(조직별 보존 삭제)와 [ADR 0039](0039-비동기-작업은-공통-작업-기록에-남기고-상태-조회는-dashboard-api가-한다.md)(공통 작업 기록)가 Accepted가 되면 Accepted.
ADR 0024 §5의 "조직 설정 변경을 이 명령으로 잇는 제품 흐름은 범위 밖"과 §1의 "보존 기간 수치를 이 저장소가 정하지 않는다"를 부분 개정한다. 삭제의 순서와 주체는 그대로다.

## Context

- 조직의 집계 보존(12·24·36개월·무기한)은 수집 정책 저장 명령이 `enrollment.organization_policy_settings`에 저장한다(ADR 0046). 저장만 하고 아무것도 지우지 않는다.
  응답의 `cleanupOperationId`는 늘 null이다.
- 조직별 보존 삭제는 `:apps:retention-worker`만 한다. tenant·보존 개월 수·asOf를 인자로 받는 일회성 실행이고, 경계 발효 → fence → drain → DELETE → 남은 행 0 확인의 순서로
  돈다. 경계는 asOf의 KST 날짜에서 N개월 전 자정이고(`RetentionBoundaryRule`) MAX로만 움직인다. 같은 입력으로 다시 실행하면 이어서 끝난다(ADR 0024 §1·§4).
  실행 한 번의 기록은 `telemetry_ops.retention_operations`이고 상태는 `running`·`incomplete`·`logically_deleted`·`failed`다.
- 공통 작업 기록(`enrollment.operations`·`operation_targets`)에는 이미 `retention_cleanup` 종류와 가장 최근 삭제 실행을 가리키는 `retention_operation_id`가 있다.
  작업 상태 조회(`GET O/operations/{id}`)는 그 실행의 상태·경계·시각을 `retention`으로 싣는다. 삭제 실행의 상태를 작업 상태로 옮기는 규칙은 정해지지 않았다(ADR 0039 Follow-up).
- enrollment 스키마와 `telemetry_ops` 스키마는 같은 RDS 데이터베이스에 있다. enrollment-api가 두 스키마의 DDL을 적용한다(ADR 0021 §3).
- 보존 작업은 서버가 아니다. HTTP 진입점을 두지 않는다(ADR 0024 §5).

정하지 않으면 생기는 일: 조직이 보존 기간을 줄여도 오래된 원본이 남는다. 화면은 줄인 결과를 볼 곳이 없다. 설정 변경을 보존 작업에 잇는 방법이 앱마다 달라진다.

## Decision

### 1. 요청이 생기는 조건

- 집계 보존이 바뀐 저장만 요청을 다룬다(같은 값의 재전송·회수 기준만 바꾼 저장은 무관하다). 요청은 저장 명령과 **같은 트랜잭션**에서 만든다.
- **줄였을 때**(유한 값이 더 작아졌거나 무기한 → 유한) 새 요청과 `retention_cleanup` 작업(대기, 대상 하나 `analysis_source`)을 만든다. 응답의 `cleanupOperationId`가 그 작업이다.
- **아직 한 번도 실행하지 않은 요청**이 있으면 다음 저장이 대체한다 — 그 요청은 `superseded`로 닫고 작업은 같은 사유로 실패시킨다. 새 값이 유한이면 늘린 값이라도 새 요청을 만든다
  (대체한 요청이 있었다는 것은 아직 경계를 적용하지 않았다는 뜻이다). 새 값이 무기한이면 요청이 없다.
- **늘렸고 대체할 요청이 없으면** 아무것도 하지 않는다. 지운 기록은 되돌리지 않는다(ADR 0024 §7). 실행을 시작한 요청은 대체하지 않는다 — 끝까지 실행된다.
- 조직마다 한 번도 실행하지 않은 요청은 하나다(부분 유일 색인).

### 2. 요청의 저장과 쓰기 소유

- `enrollment.retention_cleanup_requests`(enrollment Flyway)다. 작업 하나와 짝이고(PK = 작업 ID) 보존 개월 수, 경계의 기준 시각 `as_of`(저장 시각), 실행 횟수,
  선점(`claimed_by`·`claimed_until`), 닫힌 시각과 결과(`logically_deleted`·`failed`·`superseded`)를 담는다.
- 쓰기 소유는 `:libs:enrollment-persistence`의 요청 저장소다. 만드는 쪽은 enrollment-api의 저장 명령, 선점·결과 기록은 보존 작업이다(공통 작업 기록과 같은 방식 — ADR 0039).

### 3. 실행 — 보존 작업의 요청 모드

- `:apps:retention-worker`에 인자 `--requests` 모드를 더한다. 저장된 요청을 하나씩 **선점**해 요청의 조직·보존 개월 수·`as_of`로 **기존 보존 삭제를 그대로** 실행한다.
  삭제 순서와 삭제 주체는 바뀌지 않는다. 기존 인자 모드와 그 종료 코드는 그대로다. HTTP 진입점은 여전히 없다.
- 선점: 조직마다 가장 오래된 열린 요청부터 한 번에 하나만 잡는다. `FOR UPDATE SKIP LOCKED`로 동시에 도는 두 실행이 같은 요청을 잡지 않는다.
  선점 기한(`pulsemetry.retention.requests.lease`)이 지나면 다른 실행이 다시 잡는다 — 같은 입력의 재실행이 이어서 끝낸다. 선점을 잃은 실행은 결과를 쓰지 않는다.
  한 번의 실행에서 다룬 요청은 다시 잡지 않는다.
- 요청 모드의 설정 둘(선점 기한, 한 요청의 최대 실행 횟수 `max-runs`)은 기본값이 없다. 없으면 요청 모드는 아무것도 하지 않고 종료 코드 2다.
- 종료 코드: 다룬 요청이 모두 논리 삭제 완료(또는 요청 없음)면 0, 실패가 있으면 1, 인자·설정 오류는 2, 미완이 있으면 3.
- 주기 실행은 배포 환경(infra)의 몫이다.

### 4. 삭제 실행의 상태 → 공통 작업

| 삭제 실행 | 작업·대상 | 요청 |
| --- | --- | --- |
| 선점 | 대기 → 진행(`running`) | 실행 횟수 +1 |
| `logically_deleted` | 대상 성공 → 작업 `succeeded` | 닫힘(`logically_deleted`) |
| `incomplete`·`failed`(또는 실행 기록조차 열지 못함) | 진행 그대로 | 선점을 풀어 다음 실행이 이어서 끝낸다 |
| 위가 `max-runs`번째 실행 | 대상 실패(`retention_incomplete`·`retention_failed`) → 작업 `failed` | 닫힘(`failed`) |

작업은 언제나 가장 최근 삭제 실행을 가리키고, 작업 상태 조회의 `retention`이 그 실행의 상태(`incomplete` 포함)를 그대로 보인다.
`succeeded`는 **논리 삭제 완료**다 — 물리 제거(merge) 완료를 주장하지 않는다(ADR 0024).

### 5. 범위와 수치

- "집계 보존"이 지우는 것은 두 분석 테이블의 원본(모든 집계의 원천)이다. 수신 ledger와 수집 생애 요약은 대상이 아니다(ADR 0024).
- 보존 개월 수는 조직이 고른 값이다(ADR 0046의 선택지). 이 저장소가 기본 보존 기간을 정하지 않는 것은 그대로다(무기한이 기본이다).
- 보존 작업의 DB 계정은 요청 모드에서 enrollment의 요청·공통 작업 기록(`retention_cleanup_requests`·`operations`·`operation_targets`) 쓰기와 조직·구성원 읽기가 더 필요하다.

## Alternatives Considered

### A. enrollment-api가 저장 직후 보존 작업을 직접 실행한다
- 장점: 요청 표가 필요 없다.
- 단점: 원본 DELETE 권한과 ClickHouse 접근을 ClickHouse에 닿지 않는 앱에 준다. 긴 삭제가 요청 스레드에 묶인다.
- 탈락 이유: ADR 0024 §5가 삭제 주체를 보존 작업 하나로 좁힌 이유가 그대로 남아 있다.

### B. 보존 작업이 조직 설정을 주기적으로 읽어 경계를 맞춘다(요청 없음)
- 장점: 요청·대체 규칙이 없다. 설정이 곧 목표 상태다.
- 단점: 화면이 "이 저장의 정리"를 볼 작업 ID가 없다. 매 실행이 모든 조직을 훑는다. 늘린 설정과 이미 적용된 경계의 관계를 매번 다시 판단해야 한다.
- 탈락 이유: 공통 작업 기록(ADR 0039)이 명령 → 작업 → 상태 조회의 흐름을 이미 정했다.

### C. 요청을 `telemetry_ops`에 둔다
- 장점: 보존 작업이 이미 쓰는 스키마다.
- 단점: 요청은 공통 작업과 짝이라 보존 작업이 어차피 enrollment의 작업 기록을 써야 한다. 요청과 작업을 두 스키마에 나누면 대체·결과 기록의 원자성이 두 쓰기 소유 모듈에 걸친다.
- 탈락 이유: 작업과 같은 곳(enrollment, 같은 쓰기 소유 모듈)에 둔다.

### D. 실패는 곧바로 작업 실패로 닫는다
- 장점: 상태 전이가 단순하다.
- 단점: 일시 장애(ClickHouse 연결 실패 등)에도 조직의 보존이 영영 집행되지 않는다. 같은 값을 다시 저장해도 요청이 생기지 않는다.
- 탈락 이유: 보존 삭제는 같은 입력의 재실행이 이어서 끝낸다(ADR 0024). 정한 횟수까지는 다시 실행한다.

## Consequences/Tradeoffs

### Positive
- 보존 기간을 줄인 저장이 작업 ID를 돌려주고, 화면은 작업 상태 조회로 진행·미완·완료·실패를 본다.
- 삭제는 여전히 보존 작업 하나가 같은 순서로 한다. 기존 인자 모드는 그대로다.
- 실행 전의 요청은 마지막 저장으로 대체되어 사용자의 최신 선택만 집행된다.

### Negative
- 보존 작업의 DB 계정이 넓어진다(enrollment의 요청·작업 기록 쓰기).
- 정리가 바로 일어나지 않는다 — 요청 모드의 주기 실행을 배포 환경이 걸어야 한다. 그 전까지 작업은 대기다.
- 실행을 시작한 요청은 대체되지 않는다. 그 사이 늘린 설정은 이미 시작한 삭제를 막지 못한다.

## Follow-up
- 배포 환경: 요청 모드의 주기 실행, 요청 모드 설정 둘, 보존 작업 계정의 enrollment 권한.
- 끝난 요청·작업 기록의 보존 기간과 정리.
- 설정 화면이 저장 응답의 작업 ID로 정리 진행을 보여 준다.
