# 0025. 개발용 시드를 독립 Kotlin 도구 모듈로 관리한다

## Status
Accepted — 실행 방식과 서버 의존 제외는 [ADR 0027](0027-local-프로필에서-개발-시드를-초기화한다.md)이 부분 대체한다. 아래는 최초 결정이며 나머지 제한은 유지한다.
스키마 사전 준비·호스트 전용 연결 제한은 개발 Compose에 한해 [ADR 0030](0030-개발-Compose가-스키마와-시드를-준비한다.md)이 보완한다.

현재 실행 경로는 [ADR 0031](0031-개발-시드는-Docker에서만-실행한다.md)이 부분 대체한다. 서버 자동 실행·공유 코어·호스트 수동 시드는 제거하며, 로컬 제한·완료 데이터 보존·스키마 소유권은 유지한다.

## Context
대시보드 확인에 조직·팀·구성원·계약과 ClickHouse 사용량을 함께 준비해야 한다.
사용자가 Kotlin 전용 시드 모듈과 A/B/C 시나리오를 승인했다.

## Decision
`:tools:dev-seed`를 명시적으로 실행하는 Kotlin·Gradle 도구로 둔다.
서버 모듈은 이를 의존하지 않고 서버 기동이나 배포에 포함하지 않는다.
마이그레이션은 기존 소유 모듈이 적용하며, 도구는 이미 준비된 로컬 Docker DB에 데이터만 적재한다.
도구 자신의 실행 기록은 `dev_seed` 스키마에 둔다.
고정 조직 ID와 기준일로 재현하며, 같은 입력은 검증만 하고 추가 INSERT를 하지 않는다.
초기화는 실행 기록과 조직 slug가 일치하는 시드 조직에만 허용한다.
PostgreSQL 세션 잠금으로 동시 실행을 막고, DB 간 적재 실패는 명시적인 초기화 후 재실행한다.
로그인 구현·실제 요금·수집 완전성을 시드로 대신하지 않는다.

## Alternatives Considered
Python 스크립트는 관리 언어를 늘린다. 서버 시작 시 자동 시드는 개발 데이터의 실행 범위를 흐린다.

## Consequences
### Positive
프로젝트와 같은 언어·빌드·테스트 도구로 시나리오를 관리하고 서버에서 분리한다.
### Negative
시드 SQL은 스키마 변경 때 함께 유지해야 한다. 두 DB를 하나의 트랜잭션으로 묶지는 못한다.
