# 0050. 실제 청구액은 벤더 비용·지출 API의 정산 기간별 누계만 원천으로 하고 기간이 다른 벤더를 더하지 않는다

## Status

Proposed — [ADR 0048](0048-좌석-원장은-벤더-계정별-배정-이력이고-연결된-등록-제품에서는-커넥터-동기화가-권위를-갖는다.md)(Proposed)의 벤더 연결·동기화 위에 선다.
그 결정이 Accepted가 되고 청구 커넥터가 벤더 문서의 요청·응답을 재현한 모의 서버로 검증되면 Accepted.
[ADR 0026](0026-사용자-인증으로-프론트-관리-요청을-연결한다.md)의 "실제 청구액은 구현하지 않는다"를 부분 대체한다 — 근거 있는 벤더의 사용 비용·지출만 낸다.
좌석 구독료의 실제 청구액은 여전히 원천이 없다.
청구 조회 경로를 찾을 대상에서 GitHub Copilot·Gemini Code Assist를 뺀다 — [ADR 0054](0054-GitHub-Copilot과-Gemini-Code-Assist는-좌석-커넥터와-청구-연동의-대상이-아니다.md).

## Context

- 설정 응답의 등록 제품마다 `meteredMonthToDate`(종량 지출 — 기간·환산 비용·실제 청구액)가 있고 조직 합계가 `summary.meteredMonthToDate`다. 지금은 늘 `unavailable`·`source_not_available`이다.
- 환산 비용(분석 행의 추정 비용)과 계약액(좌석 단가 × 수량)은 청구액이 아니다. 둘을 청구액 자리에 두면 화면이 추정을 사실로 보인다.
- 벤더 문서(`docs/vendor-connector-evidence.md`)가 근거를 준 청구·비용 API는 둘뿐이다.
  - Claude Enterprise `GET /v1/organizations/analytics/cost_report`(`read:analytics`) — "Amount (post-discount, pre-credit) in fractional cents", 통화는 "Currently always USD",
    기간과 칸(`starting_at`·`ending_at` 최대 31일, `bucket_width` `1d`·`1h`·`1m`)을 고른다. 사용량 기반 Enterprise의 사용 비용이고 좌석 기반 Enterprise에서는 사용 크레딧만이다.
    값은 30일까지 고쳐질 수 있다.
  - Cursor Enterprise `POST /teams/spend` — 이번 청구 주기(`subscriptionCycleStart`)의 구성원별 지출. `spendCents`는 on-demand(구독에 든 사용 제외), `overallSpendCents`는 구독에 든 사용 포함.
    지난 주기를 고를 수 없다.
  - Copilot·Gemini·OpenAI·Claude Team·Cursor Teams는 청구 조회를 확인하지 못했거나 공개 API가 없다. 어느 벤더도 좌석 구독료 청구액을 주지 않는다.
- 동기화는 enrollment-api 안의 주기 작업이 연결마다 선점해 돈다(ADR 0048 §7). 조회 앱은 원천을 읽기만 한다.

정하지 않으면 생기는 일: 원천이 없는 벤더의 청구액이 0이나 계약액으로 채워지거나, 기간이 다른 벤더의 금액이 한 합계로 더해져 "이번 달 실제 청구"로 보인다.

## Decision

### 1. 원천 — 벤더 비용·지출 API만

- 청구 누계는 커넥터가 벤더 API에서 읽은 금액뿐이다. 환산 비용·계약액·좌석 단가 × 수량으로 채우지 않는다.
- 구현한 커넥터(capability `billing`): Claude Enterprise(사용 비용 `usage_cost`), Cursor Enterprise(사용 지출 `usage_spend`). 나머지 제품·플랜은 청구 누계가 없다(`billing_not_supported`).
- 금액의 뜻을 종류로 남긴다 — `usage_cost`는 할인 뒤·크레딧 전 사용 비용, `usage_spend`는 이번 청구 주기의 on-demand 지출(`spendCents` 합 — 구독에 든 사용분은 좌석 구독료로 이미 내므로 더하지 않는다).
  어느 쪽도 좌석 구독료가 아니다.

### 2. 정산 기간과 기준 시각

| 종류 | 기간 | 끝 |
| --- | --- | --- |
| `usage_cost`(Claude Enterprise) | 조직 달력(서울)의 이번 달 1일 0시부터. 한 시간 칸으로 읽는다 — 서울 자정이 시 경계라 칸이 달의 경계와 맞는다 | 읽은 시각 |
| `usage_spend`(Cursor Enterprise) | 벤더의 이번 청구 주기 시작(`subscriptionCycleStart`)부터 — 벤더가 정한다 | 읽은 시각 |

- 기간마다 한 행이다(조직, 등록 제품, 기간 시작). 같은 기간을 다시 읽으면 금액·끝·읽은 시각을 덮는다 — 벤더가 값을 고칠 수 있다. 진행 중인 기간의 값은 확정이 아니다(`finalized=false`).
- 읽는 시점은 좌석 동기화와 같은 실행이다(좌석 목록 뒤). 결과는 연결의 청구 칸(마지막 성공·실패·오류 코드)에 **따로** 남는다 — 청구 실패가 좌석 동기화를 실패로 만들지 않고,
  좌석 목록이 실패해도 청구는 읽는다. 연결의 대상(커넥터·설정)이 바뀌면 그 연결이 읽은 누계를 지운다(다른 계정의 값이다).

### 3. 통화

USD만 받는다. 환율 원천이 이 저장소에 없으므로 USD가 아닌 금액은 환산하지 않고 응답 해석 불가로 실패한다(그 벤더만 값 없음). Claude는 행마다 통화를 주고("Currently always USD"),
Cursor는 필드 이름(`spendCents`·`monthlyLimitDollars`)이 USD 센트다.

### 4. 조회 — 등록 제품 단위의 가용성

청구 누계는 판이 없는 현재 값이다(연결 상태처럼 snapshot에 고정하지 않는다).

| 등록 제품 | 가용성 | 사유 |
| --- | --- | --- |
| 계약 플랜의 커넥터가 청구를 구현하지 않음(커넥터 없는 플랜 포함) | unavailable | `billing_not_supported` |
| 활성 연결 없음(또는 연결의 커넥터가 플랜의 것이 아님) | unavailable | `billing_source_not_connected` |
| 지금 기간의 누계 없음 — 달력 달 기간은 이번 달 시작에서 시작한 행만 지금 값이다 | unavailable | `billing_sync_pending` · `billing_sync_failing`(마지막 시도가 실패) |
| 마지막 읽기가 실패(마지막 성공 값은 남는다) | partial | `billing_sync_failing` |
| 누계를 읽은 지 신선도 기준(좌석 원장과 같은 `seats.stale-after`)을 넘음 | partial | `billing_sync_outdated` |

- 값은 `actualBilledUsd`(기간·종류·확정 여부·원천·읽은 시각과 함께)다. `equivalentCostUsd`는 이 절에서 내지 않는다(null) — 환산 비용은 개요·팀의 제품별 사용이 낸다.
- **조직 합계**는 모든 등록 제품이 값을 갖고 **기간이 같을 때만** 더한다. 한 제품이라도 값이 없으면 부분합을 내지 않는다(그 제품의 사유로 partial, 금액 null).
  기간이 다르면(달력 달과 청구 주기) `billing_periods_differ`로 더하지 않는다. 등록 제품이 없으면 `not_applicable`.

### 5. 개발 시드

시드의 청구 행은 원천을 `seed`로 남기고 조회도 그 원천을 낸다 — 실제 청구의 증거가 아니다.

## Alternatives Considered

### A. 원천이 없는 벤더는 계약액이나 환산 비용으로 채운다
- 장점: 합계가 늘 나온다.
- 단점: 추정이 청구액으로 보인다. 계약액은 좌석 구독료이고 종량 지출이 아니다.
- 탈락 이유: 청구액 자리에는 벤더가 준 값만 둔다.

### B. 원천이 있는 벤더만 더해 조직 합계를 낸다
- 장점: 값이 있는 벤더의 합은 보인다.
- 단점: 부분합이 조직의 이번 달 청구로 읽힌다. 기존 합계 규칙(유효 계약 일부가 비면 합계 null)과 어긋난다.
- 탈락 이유: 합계는 모든 제품이 있을 때만이다.

### C. 모든 벤더를 달력 달로 맞춘다
- 장점: 기간이 같아 더할 수 있다.
- 단점: Cursor는 이번 청구 주기만 준다 — 달력 달로 자르려면 일별 값이 필요한데 문서에 없다.
- 탈락 이유: 벤더가 주지 않는 구간을 추정하지 않는다. 기간을 함께 내고, 다르면 더하지 않는다.

### D. 청구 동기화를 좌석 동기화와 따로 돌린다
- 장점: 주기를 따로 정할 수 있다.
- 단점: 같은 연결의 선점·자격증명 복호화·주기 설정이 한 벌 더 생긴다.
- 탈락 이유: 같은 실행이 읽고 결과만 따로 남긴다.

## Consequences/Tradeoffs

### Positive
- 종량 지출이 벤더 원천에서 오고, 원천이 없는 제품은 그 제품만 사유와 함께 없다.
- 금액의 종류·기간·확정 여부·원천이 함께 나와 추정과 섞이지 않는다.

### Negative
- 대부분의 조직에서 조직 합계는 null이다(청구 API가 없는 제품이 하나라도 있거나 기간이 다르다).
- Claude Enterprise 값은 30일까지 바뀔 수 있다. 좌석 기반 Enterprise에서는 사용 크레딧만이다.
- 좌석 구독료의 실제 청구액은 여전히 없다.

## Follow-up
- 실계정 검증(청구 누계와 벤더 콘솔·인보이스 대조).
- OpenAI의 청구 조회 경로가 확인되면 커넥터를 더한다(Copilot·Gemini는 연동 대상이 아니다 — ADR 0054).
- 지난 기간(정산이 끝난 달)의 확정 값을 읽는 규칙(Claude는 30일 지난 날짜).
