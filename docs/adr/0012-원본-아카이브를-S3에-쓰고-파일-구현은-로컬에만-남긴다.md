# 0012. 원본 아카이브를 S3 에 쓰고 파일 구현은 로컬에만 남긴다.

## Status

Accepted

## Context

[허브 ADR 0005](../../../docs/adr/0005-single-app-telemetry-topology.md)가 OTel Collector 바이너리를
걷어내기로 정하면서, 수집 단계의 세 책임 — OTLP 수신 · 마스킹 · **마스킹 이후 원본의 외부 저장소
적재** — 이 이 저장소로 왔다. 앞의 둘은 무엇을 만들지가 정해져 있지만 셋째는 **적재 대상이
미정인 채로 넘어왔다.** 두 문서가 그 결정을 이 작업에 명시적으로 미뤄 두었다.

- 허브 ADR 0005 Follow-up — *"마스킹 이후 원본의 적재 대상을 정한다 — infra ADR-0017 은 이미
  `awss3` 를 선호한다."*
- infra ADR-0013 Follow-up — *"재검토 조건: collector 의 backend 이관이 확정되면 그 작업에
  `awss3` 전환과 root 실행 제거를 포함할지 함께 판단한다."*

**현행은 파일이고, 그 선택에는 기록된 대가가 있다.** infra ADR-0017 이 셋을 적어 두었다.

1. **collector 컨테이너가 root 로 돈다.** `otel/opentelemetry-collector-contrib` 는 scratch 기반이라
   비root 가 쓸 수 있는 디렉터리가 없고 `/tmp` 조차 없다. `file` exporter 가 `/data` 를 만들려면
   `user: '0'` 이 필수였다. 그 결과 **ALB 로 들어오는 외부 OTLP 입력을 파싱하는 프로세스가 root** 다.
2. **파일이 무한히 증가한다.** `append: true` 는 `rotation` 과 함께 쓸 수 없다. 임시 스토리지
   기본 20 GiB 를 채우면 태스크가 죽는다.
3. **재시작하면 사라진다.** Fargate 임시 스토리지에 쓰기 때문이다. MVP 에서 의도적으로 감수했다.

셋 다 파일시스템을 쓴다는 사실에서 나온다. 그래서 infra ADR-0017 은 대안을 이미 적어 두었다 —
*"위 두 대가는 `awss3` exporter 로 옮기면 동시에 사라진다. 파일시스템을 아예 쓰지 않으므로 root 가
필요 없어지고 휘발성도 해소된다. `rawSignalBucket.grantReadWrite(task.taskRole)` 가 이미 태스크
역할에 S3 쓰기 권한을 주고 있어 IAM 변경 없이 config 만 바꾸면 된다."*

버킷은 이미 있다. [infra ADR-0013](../../../infra/docs/adr/0013-raw-signal-retention-for-mvp.md)이
보존 기간까지 정해 두었다 — prod 30일 · dev 7일, S3 Standard, 티어링 없음. 다만 같은 ADR 이
*"이 버킷에 쓰는 exporter 가 없다"* 고 적은 대로 **아직 아무것도 쌓이지 않고 있다.**
"최근 30일 재처리" 보장이 발효되지 않은 상태다.

### 이 결정이 이 저장소의 것인 이유

허브 ADR 의 Follow-up 이 던진 질문이지만 답은 레포 안에 떨어진다. 뒤집는 데 필요한 PR 이 하나이기
때문이다 — 조립 앱이 어느 구현을 만드느냐가 전부이고, 버킷과 IAM 은 이미 서 있어 infra 변경이
필요 없다. 

**이 ADR 이 정하지 않는 것**: infra 가 collector 컨테이너를 내리는 일과 root 실행을 없애는 일은
허브 ADR 0005 와 PROJ-106 의 몫이다. 여기서는 **이 저장소의 모듈이 어디에 쓰는가**만 정한다.

## Decision

- **`archive` 패키지가 `ArchiveWriter` 인터페이스를 소유하고 구현을 둘 둔다.**
  적재 대상은 이 모듈의 계약이 아니라 조립의 선택이다.
- **배포는 `S3ArchiveWriter` 다.** infra ADR-0017 이 기록한 세 대가가 파일시스템을 쓰지 않는 순간
  함께 사라진다. 보존은 infra ADR-0013 이 정한 값을 그대로 쓴다.
- **로컬 dev 와 테스트는 `FileArchiveWriter` 다.** 현행 `file` exporter 여섯의 동작을 그대로 옮긴다 —
  `/data/<제품>/<시그널>.jsonl` 에 JSONL 로 append 하고 회전하지 않는다.
  **LocalStack·MinIO 컨테이너를 새로 띄우지 않는다.**
- **어느 것을 쓸지는 조립 앱이 정한다**([ADR 0011](0011-라이브러리-모듈은-spring-조립을-앱에-위임한다.md)).
  라이브러리는 빈을 등록하지 않고 값을 생성자로 받는다. AWS SDK 는 `implementation` 으로 두어
  파일 구현만 쓰는 앱의 컴파일 의존에 SDK 타입이 나타나지 않게 한다.
- **S3 키 배치는 앞 두 구간(`<제품>/<시그널>`)이 현행 파일 경로를, 파티션 형식이 상위 `awss3`
  exporter 의 기본값을 옮긴 것이다.**

  ```
  <prefix>/<제품>/<시그널>/year=%Y/month=%m/day=%d/hour=%H/minute=%M/<시그널>_<uuid>.json
  ```

  파티션 시각은 **UTC 로 고정한다.** 상위 기본값은 로컬 타임존이지만, 태스크의 타임존에 따라 키가
  달라지면 재처리 배치가 범위를 잡을 수 없다.
- **객체 하나가 수신 한 건이다.** 현행은 `batch` 프로세서가 앞에 있어 파일 한 줄이 배치 하나였지만,
  홉이 사라지면서 `batch` 도 함께 사라졌다(허브 ADR 0005). 재처리는 객체 단위로 읽으므로 경계가
  어디든 성립한다.

## Alternatives

### A. S3 한 벌만 두고 파일 구현을 만들지 않는다

- 장점: 결정이 명확하고 구현이 하나다. 배포와 로컬이 같은 경로를 지나 드리프트가 없다.
- 단점: 로컬 dev 와 테스트가 LocalStack 이나 MinIO 컨테이너에 묶인다. **현재 이 저장소의
  Testcontainers 는 Postgres 하나뿐이고**, 수집 모듈의 테스트는 정규식과 바이트 계약이 본체라
  컨테이너가 필요한 성질의 것이 아니다. 테스트 한 번의 비용을 올리는 대가가 얻는 것보다 크다.
- 탈락 이유: 적재 대상은 이 모듈이 **하는 일이 아니라 향하는 곳**이다. 그것 때문에 모듈의 테스트가
  컨테이너를 요구하게 되면 경계를 잘못 그은 것이다.

### B. 파일 한 벌만 두고 S3 전환을 다음 티켓으로 미룬다

- 장점: 현행과 1:1 이라 동작 동일성 검증이 가장 쉽다. 이식과 저장소 전환이 한 PR 에 섞이지 않는다.
- 단점: infra ADR-0017 이 기록한 세 대가를 그대로 물려받는다. 그런데 **이식이 끝나는 시점이 곧 그
  대가를 없앨 수 있는 시점**이다 — collector 컨테이너가 사라지면 root 실행의 근거도 사라지는데,
  파일 구현만 옮기면 그 자리를 우리 앱이 이어받는다. 부채의 주인만 바뀌고 부채는 남는다.
- 탈락 이유: 두 Follow-up 이 이 작업을 재검토 시점으로 지목한 이유가 바로 그것이다.
  여기서 미루면 다음 재검토 시점이 없다.

### C. 적재 대상을 설정 문자열로 받아 한 클래스가 분기한다

- 단점: 두 저장소의 오류 모델·재시도·자격증명이 한 클래스에 섞인다. 분기 하나가 아니라
  생성자·수명주기·예외 변환이 전부 갈린다.
- 탈락 이유: 인터페이스 하나와 구현 둘이 정확히 그 문제를 위한 형태다.

## Consequences/Tradeoffs

### Positive

- infra ADR-0017 의 세 대가가 배포 경로에서 동시에 사라진다. root 실행의 근거가 없어지고,
  무한 증가가 없어지고, 태스크 재시작에도 데이터가 남는다.
- infra ADR-0013 이 상정한 "최근 30일 재처리" 보장이 **실제로 발효된다.** 지금까지 그 버킷은 비어
  있었다.
- IAM 변경이 없다. `rawSignalBucket.grantReadWrite(task.taskRole)` 가 이미 서 있다.
- 로컬 dev 가 가벼워진다. 파일 구현이 있어 컨테이너 없이 아카이브 경로까지 돈다.

### Negative

- **구현이 둘이라 배포에서만 드러나는 버그가 생길 수 있다.** 로컬에서 지나가는 경로와 배포에서
  도는 경로가 다르다. `ArchiveWriter` 의 표면을 좁게 유지하는 것(메서드 하나)이 유일한 방어다.
- **metrics 는 마스킹을 거치지 않은 채 보존 기간이 있는 버킷에 쌓인다.** 현행 설정의 metrics
  파이프라인에 `redaction/secrets` 가 없고(허브 계약 §5 의 M6), 이 이식은 동작 동일성이 판정
  기준이라 고치지 않았다. **저장 매체가 휘발성 임시 스토리지에서 30일 durable 버킷으로 바뀌므로
  같은 결함의 노출이 길어진다.** M6 를 고치는 티켓의 우선순위는 이 결정 때문에 올라간다.
- AWS SDK 가 `:libs:` 의 의존에 들어온다. `implementation` 으로 두어 계약에는 새지 않지만,
  파일 구현만 쓰는 앱의 런타임 클래스패스에도 올라간다.
- 상위 `awss3` exporter 의 설정 표면 중 옮긴 것은 키 배치뿐이다. `storage_class` · `acl` ·
  `compression` · `sending_queue` 는 필요해질 때 넣는다. 지금 넣으면 쓰지 않는 노브가 사양처럼 보인다.
- **하류가 503 을 내면 같은 원본이 한 번 더 쓰인다.** 아카이브가 다음 단계보다 앞이라, 적재가
  일시 장애로 실패하고 데몬이 재시도하면 이미 쓴 객체 옆에 같은 내용의 객체가 하나 더 생긴다
  (S3 는 uuid 가 다른 객체, 파일은 줄 중복). 데이터는 `record_id` 로 멱등이라 안전하지만 재처리
  리더는 객체 중복을 전제해야 한다. 설계상 감수한다 — 순서를 뒤집으면 변환 실패가 곧 유실이다.
- 객체 하나가 수신 한 건이라 요청이 잘면 객체가 많아진다. 현행은 `batch` 가 앞에서 묶어 주었다.
  PUT 요청 수와 객체 수가 늘어나는 비용은 감수한다 — 묶으려면 버퍼와 플러시 정책이 필요하고,
  그것은 재시도·백프레셔 정책(허브 ADR 0005 Follow-up)과 같이 정해야 할 문제다.

## Follow-up

- **재검토 조건 — 객체 수나 PUT 비용이 문제가 되면 묶는다.** 그 시점의 설계는 재시도·백프레셔
  정책과 함께 정한다(허브 ADR 0005 Follow-up 이 그 항목을 열어 두었다).
- **M6(metrics 미마스킹)를 고치는 티켓.** 이 결정이 그 결함의 노출을 길게 만들므로 함께 다룬다.
  고칠 때 바꿀 자리는 셋이다 — `Signal.METRICS.masked` · `AttributeWalker` · 이 ADR 의 Negative.
- infra ADR-0013 의 *"재처리 보장은 현재 보류 상태다 — 이 버킷에 쓰는 exporter 가 없다"* 는 서술은
  `:apps:telemetry-ingest` 조립(PROJ-105)이 실제로 배포된 시점에 고친다. **이 ADR 만으로는 아직
  사실이 바뀌지 않는다** — 모듈은 섰지만 그것을 올린 앱이 없다.
- 재처리 리더는 여전히 없다. 허브 `architecture/overview.md` 5절이 Raw Signal Object Storage 를
  **write-only** 로 적어 둔 상태 그대로다.
