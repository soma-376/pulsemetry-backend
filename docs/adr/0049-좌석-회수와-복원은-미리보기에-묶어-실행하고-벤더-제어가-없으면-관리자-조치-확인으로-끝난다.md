# 0049. 좌석 회수와 복원은 미리보기에 묶어 실행하고 벤더 제어가 없으면 관리자 조치 확인으로 끝난다

## Status

Proposed — [ADR 0048](0048-좌석-원장은-벤더-계정별-배정-이력이고-연결된-등록-제품에서는-커넥터-동기화가-권위를-갖는다.md)(Proposed)의 원장·원천 규칙과
[ADR 0039](0039-비동기-작업은-공통-작업-기록에-남기고-상태-조회는-dashboard-api가-한다.md)(Proposed)의 작업 기록 위에 선다. 두 결정이 Accepted가 되고
해제·복원 커넥터가 벤더 문서의 요청·응답을 재현한 모의 서버로 검증되면 Accepted.
[ADR 0026](0026-사용자-인증으로-프론트-관리-요청을-연결한다.md)의 "벤더 좌석 제어는 구현하지 않는다"를 ADR 0048과 함께 대체한다 — 이 결정이 제어(회수·복원) 자체다.

## Context

- 좌석 원장(ADR 0048)은 벤더 계정별 좌석과 판마다 이력을 남긴다. 원천에는 이미 `vendor_control`(벤더 제어 호출의 결과)과 `admin_action`(관리자가 벤더 콘솔에서 한 조치의 확인)이 있고,
  §2의 전이 표가 두 원천이 할 수 있는 전이를 정해 두었다. 하지만 그 전이를 일으키는 명령이 없다. 구성원 화면의 회수 후보는 `canReclaim=false`, `reason=vendor_control_unavailable`로 끝난다.
- 공통 작업 기록(ADR 0039)은 `seat_reclaim`·`seat_restore` 종류, 대상별 결과, 관리자 조치 대기(`awaiting_admin_action` + 조치 코드), 확인한 구성원이 있어야만 성공이 되는 CHECK,
  회수 작업의 복원 기한과 "한 회수에 살아 있는 복원 하나"를 이미 갖고 있다. 만드는 명령만 없다.
- 벤더마다 제어 수단이 다르다(`docs/vendor-connector-evidence.md`의 "결론 — 구현 방식"):
  - 해제는 Claude Enterprise(`DELETE /v1/organizations/users/{user_id}` — 구성원 ID 필요, 관리자 역할·SCIM 조직은 400), Cursor Enterprise(`POST /teams/remove-member`),
    Copilot(`DELETE …/copilot/billing/selected_users` — "pending cancellation", 주기 말 효력, 응답은 `seats_cancelled`뿐), Gemini(`licensePool:unassign`)가 문서로 확인됐다.
  - 복원은 Copilot(`POST …/selected_users` — 새로 만들거나 되살린 좌석 수)과 Gemini(`licensePool:assign`)가 요청·응답까지 확인됐다. Claude Enterprise는 재초대(`POST /v1/organizations/invites`)라
    역할을 정해 보내야 하고 수락 전까지 끝나지 않는다. Cursor는 복원 API가 없다.
  - Claude Team, OpenAI, Cursor Teams, `other`는 공개 제어 API가 없거나 확인할 수 없다.
- 요청 성공은 완료가 아니다. 벤더가 거절할 수 있고(IdP 관리 조직, 마지막 관리자, 남은 라이선스 없음), Copilot은 주기 말에야 효력이 생긴다.
- enrollment-api는 분석 행(ClickHouse)을 읽지 않는다. 좌석의 유휴 판정(회수 후보)은 dashboard-api가 원장·분석 행·완전성 근거로 계산한다(대시보드 명세 "좌석 원장 조회").
- 회수는 사람이 확인하고 누르는 명령이다. 화면이 확인 창을 연 뒤 다른 탭·동기화·CSV가 좌석을 바꿀 수 있다.

정하지 않으면 생기는 일: 벤더 호출 없이 로컬 원장만 바꿔 회수 성공으로 보이거나, 제어 API가 없는 벤더는 회수를 영영 기록할 수 없다.
확인 창이 본 좌석과 실행한 좌석이 달라도 알 수 없고, 부분 실패가 성공으로 묻힌다.

## Decision

### 1. 흐름 — 미리보기 → 실행 → (벤더 제어 | 관리자 조치 확인) → 복원

| 단계 | 명령 | 결과 |
| --- | --- | --- |
| 미리보기 | `POST O/seat-reclaims/preview` `{seats: [{seatAssignmentId, expectedVersion}]}`(1~100) | 대상마다 실행 가능 여부·사유·실행 방식, 영향(절감 추정·회수 뒤 미배정), `previewId`와 기한 |
| 실행 | `POST O/seat-reclaims` `{previewId}` | 202 + 회수 작업(`seat_reclaim`). 벤더 제어 대상은 대기, 관리자 조치 대상은 조치 대기 |
| 확인 | `POST O/operations/{operationId}/targets/{seatAssignmentId}/confirm` | 조치 대기 대상의 원장 전이·대상 성공(확인자 = 요청한 관리자) |
| 취소 | `POST O/operations/{operationId}/targets/{seatAssignmentId}/cancel` | 조치 대기 대상의 실패(`cancelled`). 원장 불변 |
| 복원 | `POST O/seat-reclaims/{operationId}/restore` `{}` | 202 + 복원 작업(`seat_restore`). 회수에서 성공한 대상만 |

- 모두 enrollment-api의 관리 명령이다(owner·admin, `Idempotency-Key`, 24시간 같은 응답). 쓰기 소유는 `:libs:enrollment-persistence`의 좌석 원장 모듈이다.
- 결과 조회는 공통 작업 조회(`GET O/operations/{operationId}`, dashboard-api)다. 접수(202)는 성공이 아니다.

### 2. 실행 방식 — 커넥터가 구현했으면 벤더 제어, 아니면 관리자 조치

| 좌석의 제품 | 해제 | 복원 |
| --- | --- | --- |
| 활성 연결 + 계약 플랜의 커넥터가 그 연결의 커넥터 + 그 기능을 구현 | 벤더 제어 | 벤더 제어 |
| 활성 연결 + 커넥터가 그 기능을 구현하지 않음 | 관리자 조치 | 관리자 조치 |
| 연결 없음(커넥터가 없는 플랜, 연결 전 임시 기록 포함) | 관리자 조치 | 관리자 조치 |

구현한 기능(커넥터 설명의 capability, ADR 0048 §8): 해제는 넷 모두, 복원은 Copilot·Gemini만. Claude Enterprise 재초대는 역할을 정해 보내야 하는데 원장은 옛 역할을 모른다 —
고정 역할로 재초대하면 권한이 바뀔 수 있어 구현하지 않는다(관리자가 콘솔에서 재초대하고 확인한다). 청구는 이 결정의 범위 밖이다.

거절 사유(대상 단위): `not_assigned`(해제는 배정 좌석만 — 해제 예정·배정 대기·해제는 아니다), `seat_reassigned`(복원할 좌석이 이미 다시 보유됨), `plan_mismatch`(연결의 커넥터가
지금 계약 플랜의 것이 아님), `vendor_account_unknown`(그 기능에 벤더 내부 ID가 필요한데 연결 전 수동 기록이라 없음), `connector_unavailable`(이 배포에 커넥터 호출이 없음),
`not_restorable`(해제 예정 좌석은 벤더 제어로만 되살린다 — 관리자 조치 전이 표에 없다), `control_in_progress`(끝나지 않은 회수·복원 대상이 있음), `version_conflict`, `not_found`.

- 규칙은 순수 함수 하나(`SeatControl.choose`)이고 조회 앱도 같은 함수로 좌석마다 `canReclaim`·사유·실행 방식을 낸다. 조회 앱은 이 배포에 커넥터가 조립됐는지 모르므로 명령이 한 번 더 확인한다.

### 3. 미리보기 — 요청자·좌석 판·실행 방식에 묶고 5분 동안 둔다

- 미리보기는 좌석마다 판·상태·실행 방식을 **다시 계산한다**(화면이 가진 값을 믿지 않는다). 실행할 수 있는 대상만 (좌석, 판, 방식, 연결)로 저장하고 기한은 5분이다.
- 실행은 그 미리보기를 잠그고 대상마다 판·방식·연결·진행 중인 작업을 **다시 검사한다**. 하나라도 다르면 `409 preview_stale`로 전부 거절한다(일부만 실행하지 않는다).
  기한이 지나면 `409 preview_expired`, 이미 쓴 미리보기는 `409 preview_used`(같은 키의 재시도는 같은 응답), 실행할 대상이 없으면 `422 no_eligible_seats`.
  다른 관리자가 만든 미리보기는 `404` — 확인 창을 본 사람만 실행한다.
- **유휴 판정은 다시 하지 않는다.** 회수는 관리자가 좌석을 골라 내리는 결정이고 후보는 그 결정을 돕는 검토 목록이다. 유휴 판정에는 분석 행이 필요한데 enrollment-api는 읽지 않는다.
  확인 창은 조회 앱의 구성원 좌석(`GET O/members/{memberId}/seats`의 최근 사용·검토 사유)을 새로 읽어 함께 보여 준다.
- **영향**: `estimatedMonthlySavingsUsd`는 실행할 좌석마다 유효한 계약에서 그 좌석 등급의 좌석당 단가를 더한 값이다(근거 `savingsBasis: contract_unit_price`).
  한 좌석이라도 등급·단가·유효 계약을 모르면 null이다. 구매 수량을 줄여야 실현되는 추정이고 그 시점은 모르므로 `savingsEffectiveAt`은 null이다 — 실제 청구액이 아니다.
  `resultingUnallocatedSeats`는 대상 제품마다 max(계약 좌석 − (보유 좌석 − 회수 좌석), 0)의 합이고, 유효한 계약이 없는 제품이 있으면 null이다.

### 4. 원장이 바뀌는 시점

- **벤더 제어**: 대상은 대기로 남고 enrollment-api의 주기 작업(좌석 동기화와 같은 작업, 같은 한 바퀴에서 제어가 먼저)이 선점해 커넥터를 부른다.
  대상 행을 `FOR UPDATE SKIP LOCKED`로 선점하고 기한(`sync.lease`)을 둔다. 호출 전에 좌석이 제어할 수 없는 상태가 됐으면(동기화가 먼저 해제) 부르지 않고 `seat_changed`로 끝낸다.
  - 벤더가 받아들이면 원장을 옮긴다(원천 `vendor_control`, 이력의 행위자 = 작업): 해제 끝남 → `released`, 해제 예정 → `pending_release`(예정일은 벤더가 주면, 아니면 다음 동기화가 채운다),
    복원 끝남 → `assigned`, 초대 수락 대기 → `pending_assignment`. 지금 상태에서 그 전이가 표에 없으면 원장은 두고 대상만 성공이다(다음 동기화가 벤더 값으로 맞춘다).
  - 실패는 대상의 사유(커넥터 실패 종류 `invalid_credentials`·`insufficient_permission`·`vendor_rejected`·`rate_limited`·`vendor_unavailable`·`invalid_response`, 또는
    `connection_removed`·`plan_mismatch`·`connector_unavailable`·`credential_key_unavailable`·`control_error`)이고 원장은 그대로다.
    일시 장애도 대상 실패다(호출 하나의 재시도는 HTTP 정책이 이미 했다) — 다시 하려면 관리자가 새로 회수한다.
  - 선점 기한이 지나면 다른 실행이 가져간다. 그래서 벤더 호출이 두 번 갈 수 있다(해제·복원은 같은 대상에 다시 불러도 상태가 같다). 옛 선점은 결과를 쓰지 못한다.
- **관리자 조치**: 대상은 조치 대기(`release_in_vendor_console`·`restore_in_vendor_console`)다. 관리자가 벤더 콘솔에서 조치하고 **확인**해야 원장이 옮겨진다(원천 `admin_action`,
  해제는 `released`, 복원은 `assigned`) — 확인자는 작업 대상(`confirmed_by`)에, 이력의 행위자는 작업이다(이력의 행위자는 하나라는 ADR 0048 §2 규칙).
  확인 사이에 좌석이 이미 그 상태면 원장은 그대로 두고 성공, 표에 없는 전이면 `409 seat_changed`(대상은 대기로 남는다).
- **조치 대기에는 기한이 없다.** 기한이 지나 실패로 닫으면 관리자가 실제로 콘솔에서 해지했는지 모른 채 "안 했다"고 기록하게 된다. 원장은 확인 전까지 바뀌지 않으므로 대기가 남아도
  좌석 값은 틀리지 않다. 하지 않기로 하면 **취소**한다(대상 `cancelled`, 원장 불변).
- 작업 상태는 대상 결과에서 계산한다(ADR 0039) — 조치 대기만 남으면 `awaiting_admin_action`, 섞이면 `partially_failed`, 성공이 없으면 `failed`. 부분 실패를 성공으로 올리지 않는다.

### 5. 복원 — 그 회수에서 성공한 대상만, 30일 안

- 복원 기한은 회수 작업을 만들 때 30일로 정한다. 벤더는 기한을 두지 않는다(재배정·재초대는 언제든) — 30일은 되돌리기를 "그 회수"에 묶어 두는 기간이고, 그 뒤의 재배정은 보통의 배정이다.
- 되돌릴 수 있는 회수(성공한 대상이 있고 기한 안이며 살아 있는 복원이 없음, ADR 0039)가 아니면 `422 restore_not_available`. 대상마다 §2로 방식을 다시 정하고,
  그 사이 다시 보유된 좌석은 그 대상만 실패(`seat_reassigned`)로 남긴다. 모든 대상이 불가면 작업을 만들지 않고 422(대상별 사유는 `details`).
- 복원도 원장이 바뀌는 시점은 §4와 같다. Copilot의 해제 예정 좌석은 재배정이 되살린다(`pending_release` → `assigned`).

### 6. 조회 앱의 capability

- 구성원 화면의 `capabilities.reclaimSeats`·`restoreSeats`는 관리 기능이 켜진 배포면 true다 — 벤더 제어가 없는 좌석도 관리자 조치로 끝나므로 제품과 무관하다.
- 좌석마다(`ReclaimCandidate`·`MemberSeat`) `canReclaim`과 불가 사유(§2 + 관리 기능이 꺼진 배포 `management_disabled`)를 내고, 가능하면 실행 방식(`reclaimMethod`, 가산)을 낸다.
  회수 후보인가와 회수할 수 있는가는 별개다. 연결·진행 중인 작업은 현재 값이다.

## Alternatives Considered

### A. 미리보기 없이 좌석 목록과 판으로 바로 실행한다
- 장점: 요청이 하나고 저장할 것이 없다.
- 단점: 확인 창이 보여 준 방식·영향과 실행이 다를 수 있다(그 사이 연결이 생기면 관리자 조치가 벤더 호출로 바뀐다). 여러 탭의 중복 실행을 판만으로 막기 어렵다.
- 탈락 이유: 사람이 확인한 내용과 실행을 한 기록으로 묶어야 한다.

### B. 미리보기가 유휴 판정까지 다시 한다(enrollment-api가 분석 행을 읽는다)
- 장점: 회수 직전에 사용이 재개된 좌석을 서버가 막는다.
- 단점: enrollment-api에 분석 저장소 계정·설정이 생기고 유휴 판정 코드가 두 앱에 두 벌이 된다. 회수를 후보에만 허용하면 퇴사자 좌석 같은 정당한 회수를 막는다.
- 탈락 이유: 회수는 관리자의 결정이고 판정은 조회 앱 한 곳에 둔다. 확인 창이 최신 판정을 함께 보여 준다.

### C. 관리자 조치 대기에 기한을 두고 지나면 실패로 닫는다
- 장점: 열린 작업이 쌓이지 않는다.
- 단점: 관리자가 콘솔에서 해지하고 확인만 늦었을 때 "안 했다"로 기록된다. 그 뒤의 확인을 받을 길이 없다.
- 탈락 이유: 원장은 확인 전까지 바뀌지 않아 대기가 남아도 값이 틀리지 않다. 명시적 취소로 충분하다.

### D. 벤더 호출을 명령 요청 안에서 한다
- 장점: 응답이 곧 결과다.
- 단점: 벤더 지연·재시도가 관리 요청과 DB 트랜잭션을 붙잡는다. 대상이 많으면 요청이 시간 제한을 넘는다.
- 탈락 이유: 동기화와 같은 주기 작업·선점 방식으로 요청 밖에서 한다(ADR 0048 §7, 새 배포 단위 없음).

### E. Claude Enterprise 복원을 고정 역할로 재초대한다
- 장점: 복원이 자동이다.
- 단점: 원장은 구성원의 옛 역할을 모른다. 문서의 예시 역할로 보내면 권한이 바뀔 수 있다. 초대는 수락 전까지 끝나지 않는다.
- 탈락 이유: 권한을 바꿀 수 있는 호출을 추측으로 하지 않는다. 관리자가 콘솔에서 재초대하고 확인한다.

## Consequences/Tradeoffs

### Positive
- 원장은 벤더가 받아들였거나 관리자가 확인했을 때만 바뀐다. 제어 API가 없는 벤더도 회수를 기록할 수 있고, 그 기록은 누가 확인했는지를 남긴다.
- 확인 창의 대상·방식이 실행과 같다. 다른 탭의 변경은 stale 로 드러난다.
- 부분 실패·예정 해제·수락 대기가 작업 결과와 원장 상태로 구분된다.

### Negative
- 회수 직전에 사용이 재개돼도 서버가 막지 않는다 — 확인 창이 최신 판정을 보여 주는 데 기대다.
- 벤더 제어는 주기 작업이 돌 때까지 기다린다(`sync.check-interval`). 선점 기한이 지나 넘어간 대상은 벤더 호출이 두 번 갈 수 있다.
- 절감 추정은 계약 단가의 합이라 구매 수량을 줄이지 않으면 실현되지 않는다. 시점은 모른다.
- 조치 대기 작업은 관리자가 확인·취소할 때까지 열려 있다.

## Follow-up
- 화면: 확인 창(미리보기·최신 판정)·실행·조치 확인·취소·복원과 작업 상태.
- Claude Enterprise 재초대의 역할 규칙(원장에 역할을 남길지). Cursor 복원 API가 생기면 capability를 넓힌다.
- 실계정 검증 절차의 "상태를 바꾸는 검증"을 테스트 조직에서 돌린다.
