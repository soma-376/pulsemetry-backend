# 0029. 온보딩은 저장된 정책과 벤더 선택으로 완료한다

## Status
Accepted — ADR 0026을 확장한다. 사용자 요청에 따라 계약 상세 입력은 선택이며 UI 변경은 이번 작업 범위가 아니다.

[ADR 0035](0035-공통-벤더와-제품과-플랜은-데이터베이스에서-관리한다.md)가 코드 기반 카탈로그를 DB 기준 데이터로 대체한다. 목록 API와 온보딩 조건은 유지한다.

[ADR 0033](0033-로그인은-온보딩과-분리하고-최초-정책에서-manifest를-생성한다.md)이 초기 manifest 사전 준비 조건을 대체한다. 기존 정책 복사와 완료 조건은 유지한다.

[ADR 0032](0032-온보딩-완료는-조직에-저장하고-시드는-ABC만-유지한다.md)가 일부 결정을 대체한다. 완료 시각은 tenants로 옮긴다. 정책 확인과 완료 조건은 유지한다.

## Context
온보딩의 저장한 설정을 재사용하고 벤더 선택과 계약 상세 입력을 분리해야 한다.
현재 프론트의 상수 목록과 서버의 검증 목록이 중복돼 있다.

## Decision
공통 벤더·플랜 정의는 enrollment-persistence가 관리하고 dashboard-api가 인증된 관리자에게
검색·커서 페이지 목록과 벤더별 플랜을 제공한다. 서버 저장 검증도 같은 정의를 사용한다.
enrollment-api는 정책 저장, 계약 없는 벤더 등록, 온보딩 조회·완료, 초대 조회·재발급을 제공한다.
온보딩은 수집 여부를 명시적으로 저장하고 활성 벤더를 하나 이상 등록하면 완료 가능하다.
중간 폼과 현재 단계는 저장하지 않는다. 저장된 자원으로 재개 단계를 계산하고 완료 시각만 기록한다.
원문 수집 선택은 manifest의 user_prompts·assistant_responses 두 키만 바꾼다.
기존 활성 manifest를 복사해 새 판을 만들며 endpoint·signals·다른 privacy 설정은 유지한다.
**대체됨(ADR 0033)** — 초기 manifest는 최초 정책 저장 시 명시적인 서버 수집 주소로 생성한다. 서버가 endpoint를 추측하지 않는 조건은 유지한다.
정책 저장은 이후 enroll의 기본 판에 반영하며 기존 설치의 원격 갱신 완료를 의미하지 않는다.
초대 재발급은 이전 코드 폐기와 새 코드 생성을 한 트랜잭션으로 수행한다.
가입·설치의 기존 소비 상태는 새 초대에 계승해 소비한 권한을 다시 열지 않고, 계정·설치는 유지한다.
서버별 HTTP 명세는 enrollment-server-spec과 dashboard-server-spec으로 나누고 api-reference를 폐기한다.

## Alternatives Considered
폼 전체와 단계 번호를 저장하면 실제 자원 상태와 이중 관리가 된다.
벤더 목록을 프론트와 서버에 각각 두면 선택 가능 항목과 저장 검증이 달라질 수 있다.

## Consequences
### Positive
계약 단가를 몰라도 벤더 선택 후 온보딩을 마치고 사용량을 확인할 수 있다.
### Negative
기존 설치의 정책 갱신은 별도다. 공통 카탈로그 변경 시 서버 배포가 필요했던 제약은 ADR 0035로 해소한다.
프론트의 계약 필수 조건과 메모리 저장 흐름은 후속 배선에서 이 API에 맞춰 바꿔야 한다.
