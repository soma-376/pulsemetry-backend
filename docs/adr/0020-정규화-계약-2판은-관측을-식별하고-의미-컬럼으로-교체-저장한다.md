# 0020. 정규화 계약 2판은 관측을 식별하고 의미 컬럼으로 교체 저장한다.

## Status

Accepted — 부분 대체: [ADR 0013](0013-정규화-입력은-protobuf-이고-원본-해시는-정규-json-으로-되살린다.md) 의 멱등 키 `record_id` 와 [ADR 0017](0017-정규화-불변-규칙과-enrichment-json-승격-금지는-이-저장소가-정한다.md) 규칙 2·4·6 을 대체하고, 0017 규칙 7 의 승격 목록을 넓힌다. 두 ADR 의 나머지 결정은 유효하다.

## Context

Claude Code 와 Codex 가 보내는 OTLP 는 지금 한 경로로 정규화·보강·적재된다. 조직 → 팀 → 구성원 축으로
사용량과 비용을 보여 주는 것이 이 제품의 첫 요구인데(AGENTS.md 서두), 현행 경로의 다음 사실들이
그 요구와 맞지 않는다.

### 저장 모양 — 의미가 문자열 안에 있다

- 적재 타깃 `enriched_events` 는 아홉 컬럼(`event_id`·`ts`·`tenant_id`·`installation_id`·`signal`·
  `product`·`team_ids_as_of`·`raw_json`·`enrichment_json`)이다(`V1__enriched_events.sql`,
  ADR 0017 규칙 6). 토큰·비용·모델·세션 같은 측정값과 분류는 전부 `raw_json` 문자열 안에 있다.
  토큰 하나를 더하려면 매 행의 JSON 을 파싱해야 한다.
- `ts` 는 `DateTime('UTC')` 라 초로 절사되고, 신원·분류 컬럼은 non-nullable 이라 없는 값이 빈 문자열이
  된다(`EnrichedEventRow` KDoc). 미보고와 빈 값이 구별되지 않는다.
- 정렬 키가 `event_id` 하나라 tenant·기간으로 자르는 조회는 전부 풀스캔이다 —
  [ADR 0015](0015-clickhouse-ddl-은-번호-붙은-멱등-파일이고-기동-시-적용한다.md) Follow-up 이 이미 적었다.

### 멱등 키 — 매핑을 고치면 키가 바뀐다

`record_id`(`RecordId.finalize`)는 `tenant | product | session | sequence | nanos | type | discriminator`
를 SHA-1 해 앞 16자리를 쓴다. 재료에 **파생값**(`product`, 이벤트 `type`)이 들어가므로 매핑을 고쳐
재처리하면 같은 원본이 다른 키가 되어 합쳐지지 않고 중복으로 쌓인다. 나노초는 Double 초를 거쳐 깎이고,
`None`·`True` 같은 Python `str()` 표기를 재료로 쓴다(ADR 0013 Negative, `Stringify`). 세션이 없으면
`(unknown)` 이 들어간다.

### 토큰·비용의 의미 — 근거 없이 합친다

- ADR 0017 규칙 2 는 billable 을 `input + output + cache_read + cache_create` 로 고정한다. 벤더·버전마다
  input 이 캐시 성분을 **포함하는지**가 다르면 이 식은 이중 계산이거나 누락이다. 저장소 안에 그 포함관계를
  검증한 근거가 없다.
- `Pricing` 의 단가는 KDoc 이 스스로 "자리표시자"라 밝히고, 모르는 모델에는 `DEFAULT` 단가를 적용한다.
  근거 없는 금액이 실제 값처럼 쌓인다.
- 규칙 4 는 `call_id` 를 조인 키로 삼고, 벤더가 주지 않으면 `session|tool|seq|ts` 로 합성한다(`CallId`).
  이름과 시각이 비슷한 것을 같은 호출로 보는 키다.

### 시간 — 발생 시각의 출처가 행마다 다르다

`OtlpTimestamp.parse` 는 속성 `event.timestamp`(자기신고 ISO 문자열)를 OTLP `timeUnixNano` 보다 먼저
읽고, 파싱에 실패하면 `0.0`(1970-01-01)을 돌려준다. 같은 테이블 안에서 어떤 행은 SDK 시각, 어떤 행은
속성 시각이고, 실패한 행은 1970년에 쌓인다.

### 수집 — 원본을 가리킬 수 없고, 일부 제품은 아카이브되지 않는다

- `ArchiveWriter.write(product, signal, body)` 는 반환값이 없다. 적재된 행이 아카이브의 어느 객체에서
  왔는지 가리킬 방법이 없다.
- `Product` 는 `claude-code`·`codex_cli_rs` 두 `service.name` 만 안다. `ProductRouter` 는 모르는 서비스의
  resource 를 어느 아카이브에도 쓰지 않는다 — `codex-app-server`·`Codex Desktop` 이 보내는 원본은 남지
  않는다.
- metrics 는 마스킹을 거치지 않는다(`Signal.METRICS.masked = false`,
  [ADR 0012](0012-원본-아카이브를-S3에-쓰고-파일-구현은-로컬에만-남긴다.md) Negative).

### 조직 귀속 — 구성원이 없고, 팀이 여럿일 수 있다

- 보강 단계가 만드는 조직 값은 `team_ids_as_of` 하나다. 어댑터의 `Identity.memberId` 는
  `developer.email`·`developer.id` 자기신고이고, 검증된 관계 `installations.member_id` 는 enrollment
  스키마에 있지만 파이프라인이 읽지 않는다.
- 현행 소속 조회 `findActiveTeamMembershipsByInstallationId` 는 `team_memberships` 에서 시작해
  `teams.status = 'active'` 를 INNER JOIN 한다. 무소속 구성원은 0행이고, archived 된 팀의 과거 소속은
  결과에서 빠진다.
- `TeamMembership` 은 다중 소속을 의도적으로 허용한다(엔티티 KDoc, 반개방 `coversAt`). 한 관측이 같은
  시각에 두 팀에 속할 수 있다.

### 검증 기준 — 구 golden 은 동일성 오라클이다

`libs/telemetry-adapter/src/test/resources/otlp/` 의 `*.normalized.jsonl` 은 구 Python normalizer 가 구운
이식 오라클이다. 그 README 가 스스로 적었다 — 보증하는 것은 "이식본이 현행과 같은 값을 낸다"이고,
보증하지 못하는 것은 "그 값이 벤더 실데이터에 대해 옳다"이다. codex·traces·metrics 는 실캡처가 0건이고
결함 넷이 일부러 고정돼 있다.

### 정하지 않으면

대시보드는 `raw_json` 을 매번 파싱하고, 의미가 확인되지 않은 토큰을 더하고, 자리표시자 단가로 계산한
금액을 보여 주게 된다. 매핑을 고칠 때마다 중복이 쌓이고, 팀 합계와 조직 합계가 맞지 않으며, 행에서
원본으로 돌아갈 길이 없다.

## Decision

### 1. 두 분석 테이블과 49컬럼 봉투

- 로그와 선별된 스팬은 **`telemetry_events`**(107컬럼), 모든 OTLP metric point 는
  **`telemetry_metric_points`**(85컬럼)에 저장한다. 두 테이블의 앞 49컬럼은 같은 **봉투**다(아래 표).
  봉투를 고치는 변경은 두 테이블을 같은 커밋에서 고친다. 테이블별 컬럼은 부록 D 가 담는다.
- DDL 진실원은 `libs/telemetry-persistence/src/main/resources/clickhouse/V2__telemetry_analysis_tables.sql`
  **한 파일**이고 두 `CREATE TABLE IF NOT EXISTS` 를 담는다(ADR 0015). 번호가 `V2` 인 것은 `V1` 이
  `enriched_events` 이기 때문이다 — 새 테이블은 새 파일로 더하고 `V1` 은 그대로 둔다.
- 엔진은 `ReplacingMergeTree(row_version)`, `PARTITION BY toYYYYMM(source_time)`,
  `ORDER BY (tenant_id, source_time, installation_id, observation_id)` 다. 정렬 키는 전부 원본에서 오는
  불변값이다 — `product`·`event_type`·`event_time`·`series_id`·프로파일은 넣지 않는다. skip index 는 셋뿐이다:
  `installation_id`·`session_id` bloom_filter, `event_type`(set 128) 또는 `metric_name`(set 256).
- **타입 원칙.** 분류 컬럼은 `LowCardinality(String)` 에 정해진 `unknown`/`none` 을 쓰고(부록 A.1),
  측정값·선택 시각·자유 문자열(ID·버전·이름)만 `Nullable` 이다. 배열은 해당 없으면 빈 배열이다.
  토큰·duration·count 는 `Int64`, histogram·summary 의 count 와 bucket 은 `UInt64`, 돈은
  `Decimal(38, 12)`, 시각은 `DateTime64(9, 'UTC')` 다. `raw_json` 은 없다.
- **직렬화.** sink 는 모든 컬럼을 명시적으로 쓴다 — ClickHouse 의 누락 컬럼 기본값으로 미보고를 0 으로
  채우지 않는다. `DateTime64(9)` 는 UTC `YYYY-MM-DD HH:MM:SS.nnnnnnnnn` 문자열, Decimal 은 지수 없는
  정확한 10진 문자열, `Int64`·`UInt64` 는 Double 을 거치지 않는 정수 표기다. 범위를 넘는 값은 절삭하지
  않고 검증에서 거부한다. `observation_id`·`analysis_hash`·`series_id` 는 64자리 소문자 hex 인지 sink 가
  검증한다.
- **`metadata_json`** 은 버전이 있는 이름별 **allowlist** 속성만 담는 원형이다 — resource/scope/record(point)
  경계, 중복 키, OTLP AnyValue 타입을 보존한다. **`attrs`**(`Map(LowCardinality(String), String)`)는 같은
  allowlist 중 스칼라 키만 문자열로 펼친 조회용 파생값이다. 같은 키가 다른 값·타입으로 중복되면 Map 에서
  빼고 `ambiguous_attribute` 를 남긴다. 미등록 필드는 분석 JSON 에 자동으로 복사하지 않는다.
- 본문·프롬프트·도구 arguments/output·명령문·자유 형식 오류 메시지·절대 경로·자격증명은 어떤 분석 컬럼과
  `metadata_json` 에도 넣지 않는다(ADR 0017 규칙 1 의 확장). 길이·상태·종류·안전한 분류만 남긴다.
  metric 라벨과 exemplar 도 예외가 아니다.

### 2. 관측 식별과 source_time

- **`source_time`** 은 원본 OTLP 시각이다 — 로그는 유효한 `timeUnixNano`, 없으면 `observedTimeUnixNano`,
  스팬은 `startTimeUnixNano`, metric point 는 `timeUnixNano`. 출처를 `source_time_origin`
  (`otlp_event`/`otlp_observed`/`span_start`/`metric_point`)에 남긴다. 기간·일자·조직 as-of 귀속의 기준은
  `source_time` 이고 UTC 로 저장한다.
- 시각은 UInt64 나노초 원본을 그대로 읽고 `DateTime64(9)` 의 표현 범위를 확인한다. Double 초를 거치지
  않는다. OTLP 의 미설정 0, 범위 밖, 파싱 실패를 서로 구분한다.
- `source_time` 을 얻지 못한 관측은 **두 분석 테이블에 넣지 않는다.** `received_time` 을 대입하지 않는다.
  원본은 아카이브에 남고, 거부 사유별 수를 정규화 결과에 담아 구조화 로그와 수집 운영 기록으로 센다.
  스팬 허용 목록 밖으로 버린 수도 같은 방식으로 센다. 이 계수를 위해 메트릭 라이브러리를 새로 들이지 않는다.
- `event.timestamp` 같은 의미 속성의 시각은 검증된 프로파일에서 파생 **`event_time`** 후보로만 쓴다.
  `source_time` 을 대체하지 않고, 둘이 다르면 원본을 지우지 않고 `event_time_mismatch` 를 남긴다.
- **`observation_id`** 는 `identity_version` 별로 고정한 canonical typed 원본의 SHA-256, 64자리 소문자
  hex 다. 재료에는 **항상** `tenant_id`·`installation_id`·`signal`·원본 `service.name`·`source_time`·producer
  범위가 들어간다. 그 위에 검증된 관측 고유 ID 가 있으면 그것(`source_identity_kind = native_id`), 없으면
  마스킹·신원 스탬프를 거친 resource/scope/record(point)의 canonical 내용(`fingerprint`)을 쓴다. 요청 ID 나
  tool call ID 하나만으로 로그 관측을 식별하지 않는다.
- **canonicalization.** protobuf 의미를 먼저 읽고 정규화한다. JSON/protobuf 의 숫자 표기·필드 순서·
  non-optional 기본값의 표현 차이는 같은 의미로 본다. optional·oneof 의 존재 여부와 타입은 유지한다.
  객체 필드는 정렬하고 숫자는 손실 없는 고정 표기다. KeyValue 배열은 key·typed value 로 정렬하되 중복
  개수를 보존한다. 일반 `arrayValue`·span event·histogram 배열처럼 순서에 의미가 있는 배열은 순서를 유지한다.
- **재료가 아닌 것**: 파생 `product`·`event_type`·`event_time`, 총계·가격·조직 보강, `row_version`,
  `received_time`, 아카이브 객체 이름·배치 안 위치, `mapping_version`. 매핑을 고쳐도 `observation_id` 는
  그대로다. `identity_version`·마스킹 정책의 변경은 일반 매핑 정정과 분리하고, 아카이브 재처리는 원래의
  identity 문맥을 쓴다.
- **한계.** fingerprint 는 내용과 시각까지 완전히 같은 별개의 발생을 구분하지 못한다. 이것을 exactly-once
  라 부르지 않는다. 마스킹으로 식별 성분이 사라진 경우도 같다. upstream 이 `source_time` 을 바꿔 다시 보낸
  레코드는 다른 관측이지 기존 관측의 새 버전이 아니다 — 검증된 정정 관계가 없으면 관계를 추정하지 않는다.
- 관계 ID(session·turn·request·client request·response·call·trace/span)는 `observation_id` 와 다르고 서로도
  다르다. 각각 namespace 와 함께 저장하며, 없으면 null 이다(`(unknown)` 이나 다른 종류의 ID 로 대체하지
  않는다). 같은 `call_id` 의 다른 `tool_result_seq` 는 서로 다른 관측이다. 관계 조회는 tenant·installation·
  product·producer·검증된 session/namespace 범위 안에서만 하고, 이름·시각 유사성으로 키를 합성하지 않는다.

### 3. 교체 저장

- 분석 테이블은 관측당 **최신 결과 한 행**이다. `row_version UInt64 = (normalizer_rev << 32) | ingest_seq`.
  - `normalizer_rev`(상위 32비트)는 배포된 정규화 규칙의 버전이다. 매핑·스키마·의미·가격 프로파일·보강
    규칙이 바뀌면 올린다. 코드 상수이고 1 부터 시작한다. 높은 `normalizer_rev` 는 언제나 이기므로 구 규칙의
    결과가 늦게 도착해도 새 결과를 되돌리지 못한다.
  - `ingest_seq`(하위 32비트)는 같은 규칙 안의 수신 순서다. live 수신은 archive receipt 수신 시각의
    epoch 초이며 UInt32 범위를 검증한다. 재처리 경로의 값은 재처리 기능을 만들 때 정한다(Follow-up).
  - 실행 시각 자체를 버전으로 쓰지 않는다.
- 같은 관측을 두 번 처리하면 나중 것이 이긴다. 상황별 의미는 다음과 같다.

  | 상황 | 예 | 결과 |
  |---|---|---|
  | 재전송 | 원본 O1 이 같은 `normalizer_rev` 에서 두 번 도착(`ingest_seq` 만 다름) | 나중 행이 이긴다. 내용이 같으므로 결과도 같다. `FINAL` 이 병합 전에도 한 행을 돌려준다 |
  | 정상 정정 | O1 을 `normalizer_rev` 2 로 재처리해 분류·금액·팀을 수정 | rev 2 행이 rev 1 행을 교체한다. rev 1 의 재전송이 뒤늦게 와도 `row_version` 이 낮아 복귀하지 않는다 |
  | 소속 편집 뒤 재처리 | O2 가 같은 `normalizer_rev` 에서 조직 보강만 다르게 다시 도착 | 나중 행(새 귀속)이 이긴다. 정상 갱신이다. `analysis_hash` 는 같다 |
  | 분석 대상 제외 | 기존 primary 관측을 새 규칙에서 제외 | 같은 관측의 더 높은 `row_version` 에 `record_status = excluded` 와 `exclusion_reason` 을 쓴다 |
  | null 정정 | 이전 추정 비용을 근거 부족으로 null 로 정정 | 최신 행 전체가 선택되어 null 이 유지된다. 이전 금액을 가져오지 않는다 |

- `record_status` 는 `active`/`excluded` 다. 행을 쓰지 않는 것만으로 이전 결과가 철회되지 않는다 —
  제외는 더 높은 `row_version` 의 excluded 행이다. excluded 는 분석용 논리 제외이지 물리 삭제가 아니다.
  재처리는 아카이브 범위 전체를 새 `normalizer_rev` 로 다시 흘리는 것이고, 새 규칙에서 빠지는 관측은 그
  경로에서 excluded 행으로 나온다. 범위 밖의 관측은 구 결과가 남는다 — 그것을 막으려면 범위를 넓히지,
  `normalizer_rev` 필터로 가리지 않는다.
- **`analysis_hash`** 는 키가 아니라 진단 컬럼이다. 어댑터 출력과 가격 단계의 결과(분류·품질·측정값·
  metadata·계산 근거)의 canonical 표현을 SHA-256 한다. 조직 보강(`member_id`·`team_id_as_of`·
  `team_ids_as_of`·`enrichment_json`·`enrichment_version` 과 그 단계가 붙이는 `member_unresolved`·
  `multi_team_membership` 플래그), `received_time`, archive receipt, `row_version` 은 **제외**한다. 정규화는 결정적이므로 같은 원본·같은 `normalizer_rev` 에서 hash 가 다르면 버그다 — 재처리
  전후를 비교할 때 쓴다. 의미 없는 표현 차이(속성 순서 등)는 §2 의 canonical 규칙으로 정리한다.
- 처리 순서는 어댑터 의미 정규화 → 가격 단계 → `analysis_hash` → 조직 보강 → sink 다.
- 두 테이블 사이의 원자적 적재를 가정하지 않는다. 일부 테이블만 쓰인 뒤 재시도해도 같은 `observation_id`·
  `row_version` 이라 교체로 수렴한다.

### 4. 의미 컬럼

- **null ≠ 0.** 측정된 0 은 0 이고 미보고는 null 이다. 보고 성분은 필드별로 허용한 wire 타입(정수 또는
  엄격한 10진 문자열)만 읽는다. bool·소수·overflow·음수 토큰은 정상 수치로 바꾸지 않고 그 필드만 null +
  `invalid_measurement` 다. 한 필드의 오류 때문에 나머지 유효 성분을 버리지 않는다. 일반 속성을 숫자로
  추측하지 않는다.
- 불리언은 `boolValue` 또는 프로파일이 허용한 정확한 `true`/`false` 문자열만 읽는다. 누락을 false 로
  바꾸지 않는다.
- 같은 스칼라 필드에 서로 다른 값·타입의 후보가 충돌하면 그 필드는 null + `ambiguous_attribute` 다.
  같은 타입·같은 값의 중복은 한 값으로 읽고, 원형의 중복 개수는 `metadata_json` 에 남는다.
- **세 분류를 섞지 않는다.** `usage_role`(`primary`/`diagnostic`/`none`)은 대표성,
  `usage_scope`(`response`/`turn`/`interval`/`unknown`)는 보고 단위, `workload_kind`
  (`main`/`subagent`/`compaction`/`memory`/`guardian`/`unknown`)는 작업 목적이다. primary 는 프로파일로
  검증된 사용량 보고 **로그**뿐이다. 스팬·메트릭의 토큰과 비용은 diagnostic 이며 primary 에 더하지 않는다.
- **토큰 의미 프로파일.** `input_semantics`(`inclusive_cache`/`exclusive_cache`/`unknown`)는 input 이 캐시
  성분을 포함하는지, `output_semantics`(부록 A.1)는 reasoning·tool 성분이 output 에 포함되는지를 적는다.
  `semantics_profile` 은 그 관계와 cache write 상태(`reported`/`not_applicable`/`unknown`)를 고정한 검증된
  프로파일의 ID 이고, 제품·producer 버전·provider·설정 범위에 묶인다. 검증되지 않았으면 null 이다.
  `cached ≤ input` 같은 표본의 부등식은 포함관계의 증거가 아니다.
- **파생 토큰.** `tokens_total_reported` 는 원본이 사용량 총계로 정의한 필드만 담는다 — input 을 옮겨 적지
  않는다. `tokens_total_derived`·`tokens_input_uncached` 는 검증된 프로파일이 있고 산식에 필요한 성분이
  **모두 보고됐을 때만** 계산한다.

  | 프로파일 | `tokens_input_uncached` | `tokens_total_derived` |
  |---|---|---|
  | `inclusive_cache`, cache write 가 input 에 포함되고 보고됨 | `input − cache_read − cache_create` | `input + output` |
  | `inclusive_cache`, cache write 가 그 범위에서 해당 없음으로 확정 | `input − cache_read` | `input + output` |
  | `exclusive_cache`, cache write 보고됨 | `input` | `input + cache_read + cache_create + output` |
  | `exclusive_cache`, cache write 해당 없음으로 확정 | `input` | `input + cache_read + output` |
  | `unknown`, 또는 필요한 성분 미보고 | null | null |

  reasoning·tool 이 output 의 부분집합이면 다시 더하지 않는다. `output_semantics` 가 그 성분을 output 밖으로
  정한 프로파일만 보고된 reasoning·tool 을 더한다. **미보고 cache write 를 0 으로 추정해 식을 고르지 않는다.**
  "해당 없음"은 프로파일에 고정된 사실이고, 그때도 `tokens_cache_create` 는 미보고 null 그대로다. 계산의
  overflow·음수 결과·포함관계 위반은 파생값 null + `derived_value_invalid` 다. 사용량 관측에 검증된 프로파일이
  없으면 파생값 null + `usage_semantics_unverified` 다. 고정 billable 식은 두지 않는다.
- **비용.** 두 값을 분리하고 서로 더하지 않는다.
  - `cost_reported_usd` 는 벤더가 보고한 USD 금액이고 `reported_cost_basis`(`estimate`/`billed`/`unknown`)가
    그 성격이다. 벤더가 보고했다는 이유만으로 `billed` 를 붙이지 않는다. 같은 금액의 두 표기(예: 달러와
    백만분의 일 정수)가 함께 오면 프로파일이 정한 정밀도로 비교하고, 어긋나면 보고 금액 null +
    `cost_conflict` 다. 토큰 성분은 유지한다.
  - `cost_estimated_usd`·`pricing_version` 은 Pulsemetry 의 추정이다. **검증된 불변 가격 프로파일이 주입될
    때만** 계산한다. 가격 단계는 외부 조회 없이 결정적이며, 모델·성분 의미·유효 기간·통화 등 필요한 차원이
    하나라도 없으면 null 이다. 모르는 모델에 기본 단가를 쓰지 않고, 총토큰에 단일 단가를 곱하지 않는다.
    가격 프로파일 데이터가 없는 동안 추정 비용은 전부 null 이다.
  - 명시된 0 은 유지하고 미보고는 null 이다. USD 가 아닌 금액을 USD 컬럼에 넣지 않는다. 이름에 cost 가
    있어도 통화 금액의 정의가 없는 값은 비용으로 올리지 않는다.
- **제품과 공급자.** `product`·`surface` 는 정확한 `service.name` 별칭 registry 로만 정한다(부록 A.1).
  substring 판별은 하지 않는다. 서비스 이름과 관측 이름의 제품 근거가 충돌하면 `product = unknown`,
  `mapping_status = ambiguous` 다. **모델 공급자는 `product` 로 추정하지 않는다** — `codex` 라는 사실은
  OpenAI 의 근거가 아니다. 공급자는 그 행에 실린 검증된 provider 근거(allowlist metadata)로만 정하고,
  근거가 없거나 충돌하면 `provider_unresolved` 다. 다른 신호의 값(예: 세션 시작 로그의 provider)을 세션 없는
  사용량 행으로 옮기지 않는다. 분석 테이블에 공급자 컬럼은 두지 않는다.
- **로그 의미 이름.** 제품별 프로파일이 정한 경로에서 읽고 원래 이름을 `original_name` 에 보존한다. 최상위
  OTLP `eventName`·속성 `event.name`·body·severity 는 서로 다른 필드다. 최상위 `eventName` 이 소스 위치
  (`파일:행`)일 때 의미 이름으로 쓰지 않는다 — 버전 고정 프로파일이 그 위치를 `operation` 판별 근거로 쓰는
  것만 허용하고, 프로파일 밖의 위치는 `unknown` 이다. 한 위치를 여러 요청 경로가 공유하면 위치만으로 정하지
  않고, 그 위치가 싣는다고 프로파일이 검증한 경로 속성을 함께 본다. 원래 위치 문자열은 `metadata_json` 에 남는다.
- **정규화 단계의 책임.** 외부 I/O·가격 조회·신호 간 조인·push 사이의 상태 없이 결정적으로 처리한다
  (ADR 0017 규칙 5 유지). 매핑 실패와 비지원 이유를 결과로 돌려준다. 개별 관측의 미지원·측정 오류는
  `generic`/`invalid` 행이나 거부 계수로 남기며 **push 전체를 400 으로 실패시킬 근거가 아니다.** push 단위의
  형식 오류·신원 오류와 예외 → 상태 매핑은 `IngestPipeline` 의 표 그대로다(허브 ADR 0006).
- **metrics.** point 하나가 관측 하나다. 이름이 아니라 실제 OTLP 타입·temporality·단위로 처리한다.
  - Gauge 는 int/double oneof 를, Sum 은 start/end·temporality·monotonic 을, Histogram 은
    count/sum/min/max·bounds·buckets 와 존재 여부를, ExponentialHistogram 은 scale·zero count/threshold·
    positive/negative offset·buckets 를, Summary 는 count/sum·quantile/value 배열을 보존한다.
    histogram·summary 를 스칼라로 납작하게 만들지 않는다.
  - NaN/±Infinity 스칼라는 `value_double = null` + `non_finite_value` 다. histogram 구조 안의 비유한 값이나
    bounds·buckets 불일치(엄격 증가, bounds+1 개 buckets, bucket 합 = count)는 배열을 부분 수정하지 않고
    `structural_status = invalid` 로 남긴다. `point_flags` 를 그대로 보존하며 no-recorded-value 는 0 측정이
    아니다.
  - `series_id` 는 tenant·installation·producer/resource·scope/schema·metric name/type/unit/temporality/
    monotonic·원본 point 차원으로 만든다. 설명·값·point 시각·파생 family 는 재료가 아니다. 마스킹이나
    제거로 서로 다른 series 가 합쳐질 수 있으면 `series_identity_status = unverified` 이고, 그런 series 는
    자동 합산하지 않는다. 만들 수 없으면 null 이다.
  - metric token 라벨(`cacheRead`·`cacheCreation`·`cached_input`·`cache_write_input`·`reasoning_output` 등)은
    `token_component` 로 대응시키되 원래 라벨을 보존한다. 라벨 이름의 대응이 성분 포함관계의 검증은 아니다.
  - DELTA·CUMULATIVE 의 조회 기간 집계 규칙은 이 ADR 의 범위가 아니다(Follow-up). 저장은 그 규칙이 필요로
    하는 원형을 전부 담는다.

### 5. 조직 보강 — 구성원과 대표 팀

- **`member_id`** 는 인증된 `installation_id` 의 `installations.member_id` 다. 소속 조회와 독립된
  installation 단독 조회로 얻고, 무소속 구성원도 채운다. revoked 된 installation 도 채운다 — 과거 사용량은
  그 사람의 것이다. 조회되지 않으면 null + `member_unresolved` 다. 벤더 자기신고(`developer.*`·
  `user.email` 등)는 allowlist metadata 일 뿐 `member_id` 의 출처가 아니다.
- **`team_id_as_of`** 는 `source_time` 시점에 유효한 소속(`joined_at <= t < left_at`)을 **서로 다른 팀 ID
  로 중복 제거**해 하나면 그 팀, 둘 이상이면 null + `multi_team_membership`, 없으면 null 이다. 같은 팀의
  중복 소속 행은 하나로 본다. 팀의 현재 상태(archived 등)는 보지 않는다 — 이벤트 시점의 소속만 쓴다.
  **이 규칙은 근거가 없을 때의 보수적 처리이고, 대표 팀을 고르는 정책 자체는 제품 결정으로 남긴다**
  (Follow-up). 하나를 고르는 규칙(최근 가입 등)을 두지 않는다.
- **`team_ids_as_of`** 는 같은 as-of 소속의 팀 ID 배열이며 진단용으로 유지한다. 팀 상태 필터가 없다.
- 소속 조회는 팀 상태로 거르지 않는 새 as-of 조회다. push 단위 캐시를 허용하고, 소속 변경은 다음 push 부터
  반영되며, 이미 적재된 행은 재처리(같은 `normalizer_rev`, 큰 `ingest_seq`)로 갱신된다. 규칙 자체가 바뀌면
  `normalizer_rev` 를 올린다.
- 세 값은 `observation_id` 와 `analysis_hash` 의 재료가 아니다. 보강 규칙의 버전을 `enrichment_version` 에
  남긴다.
- ADR 0017 규칙 7 의 승격 예외는 `team_ids_as_of` · `team_id_as_of` · `member_id` 셋이다. 그 밖의 provider
  산출물은 계속 `enrichment_json` 에만 적재하고, 규칙 8(스텁도 빈 항목을 쓴다)은 유지한다.

### 6. 수집 선행 — archive receipt

- 수집 단계는 아카이브에 **실제로 쓴 객체**의 receipt — 객체 key(URI), signal, 원본 안의 source selector,
  서버 수신 시각, 신뢰 신원, `masking_version`·`identity_version` — 를 돌려주고 다음 단계로 넘긴다.
  `archive_ref`·`archive_selector` 는 receipt 에서만 채운다. 보존에 실패하면 가상의 참조를 발급하지 않는다.
- receipt 가 없으면 `archive_ref` 는 null 이고 `quality_flags` 에 `archive_receipt_missing` 을 남긴다.
  **적재를 막지 않는다.**
- 모르는 `service.name` 의 원본도 제품을 추정하지 않는 경로로 아카이브한다. `codex-app-server`·
  `Codex Desktop` 처럼 현재 버려지는 서비스가 여기에 든다.
- metrics 도 아카이브 전에 마스킹한다 — 라벨과 exemplar 에 대한 보호가 로그·스팬과 같아야 allowlist 가
  의미를 가진다.
- 신뢰 신원과 스탬핑 순서(마스킹 뒤·아카이브 앞, 중복 키 전부 덮어쓰기)는
  [ADR 0016](0016-조립-앱은-인증-체인과-단계-호출을-배선하고-스키마-적용-실패를-견딘다.md) 그대로다.

### 7. 조회 규칙

부록 B 가 예시 SQL 을 담는다. 규칙은 다음과 같다.

- 최신 선택은 `FINAL` 한 단계다. 정렬 키가 같은 행 중 `row_version` 이 가장 큰 행만 남고, 기본키 컬럼 밖의
  조건은 **그 뒤에** 적용된다. 그래서 `record_status = 'active'` 같은 필터가 excluded 행 아래의 구 active
  행을 되살리지 못한다. 이 성질은 적재 모듈의 테이블 테스트가 고정한다.
- 조회는 `do_not_merge_across_partitions_select_final = 1` 을 켠다 — 정렬 키에 파티션 기준 컬럼이 있어 같은
  관측이 두 파티션에 걸치지 않는다.
- base table 을 `FINAL` 없이 합산하지 않는다. 단순 SUM incremental materialized view 를 두지 않는다
  (교체 전 행을 합산한다). 컬럼마다 `argMax` 로 최신 값을 고르는 우회를 두지 않는다 — 최신 행 전체를 고른다.
- 사용량 KPI 는 `signal = 'log'`·`event_type = 'model.response.usage'`·`usage_role = 'primary'`·
  `record_status = 'active'`·`mapping_status = 'mapped'` 인 최신 행에서만 나온다. 같은 활동의 스팬·메트릭
  수치를 더하지 않는다. 관측 수는 고유 호출 수가 아니다.
- **팀 집계는 `team_id_as_of` 로 묶는다.** 각 행이 정확히 한 팀 또는 미배분(null)에 속하므로 조직 합계는
  팀별 합과 미배분의 합과 같다. `team_ids_as_of` 는 진단에만 쓴다. 구성원 축은 `member_id` 다.
- 결과 행이 없는 기간은 "관측 없음"이다. 0 으로 채운 가짜 행을 만들지 않는다. 보고값이 전부 null 이면
  합계도 null 이다(`sumOrNull`).
- 별도 current·일별 집계 테이블은 초기에 두지 않는다. 월 파티션 하나가 tenant 당 수천만 행을 넘기 시작하면
  latest·제외 계약을 지키는 일별 재계산 집계를 설계한다 — 그것이 전환 트리거다.

### 8. 삭제 원칙

- 분석 행의 삭제는 **관측 단위 전체 삭제와 영속 삭제 경계의 지속 집행**을 함께 적용한다. 어떤 관측의 일부
  `row_version` 만 지워 구 행이 되살아나는 경우와, 삭제 뒤 재전송·재처리로 같은 관측이 다시 들어오는 경우를
  모두 막는다.
- 조직별 보존 삭제는 두 분석 테이블에 `tenant_id = {t} AND source_time < {경계}` 조건으로 한다. 조건에
  `row_version`·`record_status`·`normalizer_rev` 를 넣지 않는다. 경계는 tenant 별로 영속하고 단조롭게만
  움직이며, 적재·재처리·조회가 모두 같은 경계를 집행한다. 경계를 읽지 못하면 과거 행을 허용하는 쪽으로
  실패하지 않는다.
- 월 파티션은 여러 tenant 가 공유하므로 `DROP PARTITION` 은 그 파티션의 모든 tenant 에 삭제가 허용될
  때만 쓴다. DDL 에는 자동 TTL·물리 삭제 작업을 넣지 않는다.
- 삭제를 실행하는 작업·경계 저장·진행 중인 쓰기와의 조정은 후속 ADR 이 정한다.

### 9. fixture

- 구 golden(`libs/telemetry-adapter/src/test/resources/otlp/**/*.normalized.jsonl`)은 **퇴역**한다. 구 모델이
  사는 동안 손대지 않고, 구 모델을 제거할 때 함께 지운다. 새 계약의 정확성 근거로 쓰지 않는다.
- 새 계약의 fixture 는 `libs/telemetry-adapter/src/test/resources/otlp-v2/` 다. 실캡처를 익명화한 추출본은
  `<product>/real/`, 명세 사례는 `<product>/synthetic/` 또는 `common/synthetic/` 에 둔다. 디렉터리 README 가
  실캡처/합성 구분, producer·버전, 캡처 기간, 선택 기준, 치환 규칙을 적는다.
- 기대값은 이 ADR 에서 **구현과 독립적으로** 쓴다. 구현을 돌린 출력을 기대값으로 붙여 넣지 않는다.
- 토큰 의미 프로파일을 검증 완료로 표시하려면 **원천 근거(producer 소스 또는 공식 문서)와 저장소 fixture
  가 둘 다** 있어야 한다. 부록 C 가 그 기록이다. 문서상 근거는 기대값일 뿐이고, fixture 에 보이지 않았다는
  것은 "해당 없음"의 증거가 아니다.

### 10. 다른 ADR 과의 관계

- **ADR 0013** — 멱등 키 `record_id` 를 `observation_id`(§2)로 대체한다. 입력이 protobuf 라는 결정은
  유지한다. `_ingest.source_record_id`(원본 추적 해시)와 그것을 되살리는 정규 JSON 은 구 모델과 함께 남고
  함께 퇴역한다.
- **ADR 0017** — 규칙 2(billable 고정식)는 폐기하고 §4 의 파생 토큰으로 대체한다. 규칙 4(`call_id` 조인 키)는
  `call_id` + `call_id_namespace` + `tool_result_seq` 를 tenant·installation·producer·session 범위 안에서만
  쓰는 것으로 바꾸고 합성 키를 두지 않는다. 규칙 6(9컬럼 화이트리스트 + `raw_json`)은 폐기하고 §1 의 typed
  컬럼으로 대체한다. 규칙 1·3·5·8 은 유지하고, 규칙 7 은 승격 목록을 §5 대로 넓혀 유지한다. 구 모델이 사는
  동안 `enriched_events` 경로에는 0017 원문이 그대로 적용된다.
- **ADR 0014·0015·0016** — 유지한다. 새 모델도 단계 사이의 데이터 타입 간선(0014)으로 넘기고, 새 DDL 은
  멱등 파일로 더하며(0015), 신원 스탬핑과 상태 매핑은 0016 그대로다.
- **`enriched_events`** — 새 경로로 전환한 뒤 쓰기를 멈추고 이중 적재하지 않는다. 테이블과 `V1` 파일,
  `ClickHouseSchemaMigrator` 의 `V1` 항목은 남긴다. 폐기는 별도 결정이다.
- **어휘의 소유자는 이 ADR 이다.** `event_type`·`metric_family`·분류 컬럼 어휘와 품질 플래그는 부록 A 가
  정한다. 새 이름을 generic 으로 **받아들이는 것**과 그 이름을 KPI 로 **승인하는 것**은 다른 변경이다 —
  후자는 부록 A 의 registry 표를 고치는 변경이며, 코드 주석은 규칙을 반복하지 않고 이 ADR 번호를 가리킨다.

## Alternatives

### A. 현행 `enriched_events` 에 컬럼을 몇 개 승격한다

- 장점: 변경이 작고 구 golden 을 그대로 쓸 수 있다.
- 단점: 멱등 키가 파생값에 묶인 문제, billable 고정식, 자리표시자 단가, 초 절사, 빈 문자열 null 이 그대로
  남는다. 정렬 키를 바꾸려면 어차피 테이블을 다시 만들어야 한다(ADR 0015 Negative).
- 탈락 이유: 고치려는 것이 컬럼 수가 아니라 식별·의미·교체 규칙이다.

### B. 처리 이력을 모두 남긴다 — revision·`analysis_hash` 를 정렬 키에

- 장점: 어떤 규칙이 어떤 결과를 냈는지 분석 테이블 안에서 감사할 수 있다.
- 단점: 조직 보강은 push 마다 소속을 조회해 변경을 곧바로 반영한다. 조직 상태를 revision 에 묶으면 새 팀원이
  다음 revision 까지 귀속되지 않고, 묶지 않으면 소속 편집 뒤의 평범한 재전송이 "같은 revision 의 모순"이
  되어 KPI 에서 빠진다. 재처리에서 제외 행을 빠짐없이 내려면 이전 분석 행 집합을 아는 배치 재처리 시스템이
  필요한데 그것이 없다.
- 탈락 이유: 두 조건이 모두 이 저장소에 없다. 이력이 필요하면 아카이브 재처리로 복원하거나 별도
  append-only 테이블로 분리한다.

### C. `product`·`event_type` 을 정렬 키에 넣는다

- 장점: 제품·유형별 조회가 기본키로 잘린다.
- 단점: 매핑을 정정하면 같은 관측이 다른 키가 되어 교체되지 않고 두 행이 된다.
- 탈락 이유: 교체 저장의 전제(불변 키)가 깨진다. 유형 조회는 skip index 로 충분하다.

### D. 속성을 `Map` 하나에 원형으로 둔다

- 장점: 스키마가 좁고 새 속성이 저절로 들어온다.
- 단점: 같은 키의 중복·AnyValue 타입·resource/scope/record 경계가 사라진다. 미등록 속성이 자동으로
  분석 저장소에 들어와 allowlist 가 무력해진다.
- 탈락 이유: 원형은 allowlist `metadata_json` 이 맡고, Map 은 그 파생 조회값으로만 둔다.

### E. 여러 팀에 속한 관측에서 하나를 골라 대표 팀으로 삼는다

- 장점: 미배분이 줄어든다.
- 단점: 어느 팀을 고를지는 제품이 정할 일이다. 다중 소속은 엔티티가 의도적으로 허용한 상태다.
- 탈락 이유: 근거 없는 선택이 비용을 특정 팀에 귀속시킨다. 결정 전에는 미배분 + 플래그로 드러낸다.

## Consequences/Tradeoffs

### Positive

- 조회가 typed 컬럼과 `(tenant_id, source_time, installation_id)` 기본키·월 파티션으로 잘린다. JSON 파싱이
  없다.
- 매핑 정정·소속 편집·제외·null 정정이 전부 같은 교체 규칙으로 수렴한다. 구 규칙의 결과가 늦게 와도 이기지
  못한다.
- 모르는 것이 0 이 아니라 null 과 품질 플래그로 보인다. 근거 없는 총계·금액이 사라진다.
- 팀별 합과 미배분의 합이 조직 합계와 같다. 구성원 축이 검증된 관계로 생긴다.
- 행에서 아카이브 원본으로 돌아가는 길(receipt)이 생기고, 버려지던 제품의 원본이 남는다.

### Negative

- **검증 전에는 파생 토큰이 null 이다.** 제품별 프로파일을 부록 C 에 검증하기 전까지 `tokens_total_derived`·
  `tokens_input_uncached` 가 비어, 대시보드의 총토큰이 null 로 보인다. 완화책은 프로파일 검증이며 그 전에는
  보고 성분을 성분별로만 보여 준다.
- **가격 데이터가 없는 동안 추정 비용이 전부 null 이다.** 가격 프로파일의 관리 주체가 정해지기 전까지
  비용 화면은 비어 있다.
- **`FINAL` 읽기 비용.** 모든 조회가 tenant×기간 범위를 `FINAL` 로 읽는다. 규모가 커지면 §7 의 전환
  트리거에서 집계를 설계해야 한다.
- **fingerprint 는 exactly-once 가 아니다.** 원본 고유 ID 가 없는 producer 에서 완전히 같은 두 발생은 하나로
  합쳐진다.
- **같은 초의 재전송은 같은 `row_version` 이다.** 이때는 ReplacingMergeTree 가 나중에 삽입된 행을 남긴다.
  어댑터 출력은 같으므로 보강 결과가 달랐을 때만 삽입 순서가 결과를 정한다. `ingest_seq` 가 epoch 초이므로
  UInt32 가 넘치는 2106 년 전에 구성을 다시 봐야 한다.
- **두 테이블은 원자적으로 적재되지 않는다.** 재시도가 교체로 수렴하기 전까지 한쪽 테이블만 새 행을 가질 수
  있다.
- **다중 소속 사용량은 미배분이다.** 대표 팀 정책이 정해질 때까지 팀 화면의 합이 조직 합계보다 작을 수 있고,
  그 차이는 `multi_team_membership` 로 설명된다.
- **구 파이프라인과의 동일성 검증 수단을 버린다.** 새 기대값의 정확성은 명세와 리뷰에 기댄다.
- **`enriched_events` 는 전환 뒤 새 행을 받지 않는다.** 그 테이블을 읽는 소비자가 생겼다면 전환 전에 옮겨야
  한다.
- 컬럼이 107·85 개라 sink 직렬화 규칙(시각·Decimal·UInt64)이 넓다. 잘못 쓰면 조용히 값이 바뀌므로 인코더
  테스트가 필요하다.

## Follow-up

- **대표 팀 선정 정책(제품 결정).** 단일 소속을 제품 원칙으로 할지, 비용 귀속용 대표 팀 이력을 따로 둘지
  결정되면 §5 를 개정하고 `normalizer_rev` 를 올려 재처리한다.
- **가격 프로파일 데이터의 관리 주체와 저장소.** 정해지기 전에는 주입 인터페이스만 있고 추정 비용은 null 이다.
- **`enriched_events` 폐기** — 테이블, `V1__enriched_events.sql`, `ClickHouseSchemaMigrator` 의 `V1` 항목.
- **메트릭 구간 KPI** — DELTA·CUMULATIVE 기간 집계, reset·중단 marker·겹침 구간의 조회 규칙.
- **일별 재계산 집계** — 월 파티션 하나가 tenant 당 수천만 행을 넘기 시작하면 설계한다.
- **재처리 경로의 `ingest_seq`** — 같은 `normalizer_rev` 의 재처리가 live 결과를 이기도록 하위 32비트를
  부여하는 규칙.
- **조직별 보존 삭제** — 경계 저장, 삭제 작업, 진행 중 쓰기·조회 결과와의 조정은 후속 ADR.
- 부록 A 의 어휘(`decision_scope`·`ttft_scope`·`error_type` 등)에 검증된 값을 더할 때는 이 ADR 을 개정한다.

## Acceptance Criteria

- 봉투가 두 테이블에 같은 순서로 있다 — 적재 모듈의 DDL 테스트가 두 테이블의 앞 49컬럼 이름·타입을 비교한다.
- `V2__telemetry_analysis_tables.sql` 을 두 번 적용해도 성공한다.
- §3 표의 다섯 상황과 §7 의 "필터가 구 행을 되살리지 못한다"를 ClickHouse 컨테이너 테스트가 고정한다.

## 부록 A. 어휘와 이벤트 타입 registry

### A.1 분류 컬럼의 초기 어휘

`none` 은 "이 관측에 해당하지 않음", `unknown` 은 "해당하지만 근거가 없음"이다. 둘을 바꿔 쓰지 않는다.
"검증된 값"이라 적은 칸은 프로파일이 원본 값과의 대응을 검증해 이 표를 개정할 때만 늘어난다. 모르는 원본
값은 `unknown` 이고 원래 값은 allowlist metadata(또는 `decision_raw` 처럼 지정된 raw 컬럼)에 남는다.

### A.2 로그 매핑

Claude 이름은 `claude_code.` 접두사를, Codex 이름은 `codex.` 접두사를 생략했다. 모든 행에서 원래 이름과
안전한 metadata 를 보존한다. "초기 처리"는 registry 에 들어간 뒤의 의미이고, 해당 producer 버전의 wire
형식·토큰 포함관계가 검증됐다는 뜻이 아니다(부록 C).

| 제품·원본 | `event_type` | 초기 처리 |
|---|---|---|
| Claude `api_request` | `model.response.usage` | 프로파일로 검증된 사용량 보고에서 유효한 토큰 성분 또는 보고 비용이 있으면 primary/response. 토큰·비용·model·duration·TTFT·query source 를 추출한다. 비용만 있으면 토큰은 null 이다 |
| Claude `api_error` / `api_retries_exhausted` | `model.request.error` / `model.retry.exhausted` | attempt·HTTP 상태·총 재시도 시간. 사용량에 더하지 않고, 두 종류를 합해 고유 실패 요청 수라 부르지 않는다 |
| Claude `assistant_response` / `api_refusal` | `model.response.text` / `model.response.refusal` | 응답 길이·request ID·검증된 거부 분류만. 사용량·호출 수에 더하지 않는다 |
| Claude `api_request_body` / `api_response_body` | `model.body.metadata` | 허용된 request ID·attempt·길이·잘림 여부만. 본문과 body 참조 대상은 읽지 않는다 |
| Codex `sse_event` | A.3 의 네 분기 | 완료·토큰·오류를 따로 검증한다. 사용량 보고가 아닌 stream 이벤트도 generic-safe metadata 로 보존한다 |
| Codex `api_request` | `transport.request.attempt` | HTTP 상태·attempt·duration·명시 success. `operation` 은 버전 고정 프로파일이 등록한 소스 위치·연결 스팬 근거로만 `models_list`/`responses`, 그 밖은 `unknown`. 여러 요청 경로가 공유하는 위치는 그 위치의 `endpoint` 가 `/responses` 일 때만 `responses` 다. 세션·success 유무로 추론하지 않는다 |
| Codex `websocket_connect` / `websocket_request` | `transport.connection` / `transport.request.attempt` | transport=websocket, duration·명시 success·HTTP 상태. 상태와 success 를 서로 대신 채우지 않는다 |
| 두 제품 `user_prompt` | `prompt.submitted` | 보고된 길이·허용된 명령 종류. 프롬프트 제출 수이며 고유 턴 수가 아니다 |
| 두 제품 `tool_result` / `tool_decision` | `tool.result` / `tool.decision` | native 관계 ID·`tool_result_seq`·도구 출처/동작·측정 success·결정·출처. 거절 뒤 결과가 없는 것은 유실이 아니다 |
| Codex `sandbox_outcome` / `turn_ttft` | `sandbox.outcome` / `turn.first_token` | outcome·초기 duration / 보고 duration(`ttft_scope = turn`) |
| Codex `conversation_starts` | `conversation.started` | 검증된 정책·provider·auth mode·terminal metadata. Claude 세션 카운터와 같은 세션 수로 통합하지 않는다. 그 값을 다른 행으로 옮기지 않는다 |
| Codex `startup_phase` / `auth_recovery` / `agent_communication` | `startup.phase` / `auth.event` / `agent.communication` | phase·status, auth step·outcome, communication ID·state·kind·명시 sender/receiver ID 만. content 제외 |
| Claude `compaction` / `subagent_completed` | `context.compacted` / `agent.completed` | 컨텍스트 전후 크기·duration, agent 종류·상태·model. 전후 크기와 subagent 의 total tokens 는 컨텍스트 크기이지 소비 사용량이 아니다 |
| Claude `skill_activated` / `permission_mode_changed` / `mcp_server_connection` / `auth` | `skill.activated` / `permission.changed` / `mcp.connection` / `auth.event` | 해당 사건의 허용 metadata. 사용자 지정 이름·서버명도 privacy 정책을 통과해야 한다 |
| Claude `hook_registered` / `hook_execution_start` / `hook_execution_complete` | `hook.registered` / `hook.started` / `hook.completed` | 명시적인 종류·상태·duration. 시간 근접성으로 시작과 완료를 잇지 않는다 |
| Claude `internal_error`·`plugin_installed`·`plugin_loaded`·`at_mention`·`hook_plugin_metrics`·`feedback_survey`·`retention_sweep` | `vendor.unknown` | `mapping_status = generic`, 원래 이름과 허용 metadata 만. 분석이 필요해지면 registry 를 개정한다 |
| 의미 이름이 없는 로그 | `diagnostic` | 안전한 봉투·scope·허용 metadata 를 저장하고 분포를 센다. 사용량 KPI 밖 |
| 그 밖 미등록 이름 | `vendor.unknown` | 위와 같다 |

작업 목적이 compaction 이라는 이유로 실제 API 사용량을 제외하지 않는다 — query source 가 compaction 인
API 사용량은 `usage_scope = response`, `workload_kind = compaction` 이며 primary 가 될 수 있다.

### A.3 Codex `sse_event` 의 분기 순서

위에서부터 처음 맞는 분기를 쓴다. 기준 키는 `event.kind` 이고 `kind` 는 그 producer 버전에서 검증된 alias
일 때만 읽는다. 두 키가 다른 값으로 함께 오면 `ambiguous_attribute` 이고 어느 쪽도 우선하지 않는다.

1. 토큰 필드와 오류 근거가 함께 있으면 `model.response.usage`, `mapping_status = ambiguous`,
   `usage_role = diagnostic`, `ambiguous_payload`. KPI 에서 빠진다. 오류 원문은 저장하지 않는다.
2. 오류만 있으면 `transport.stream.error`, `usage_role = none`. 오류 존재와 검증된 오류 종류만 남긴다.
   명시 success 가 없으면 null 이다.
3. 검증된 `event.kind = response.completed` 이고 유효한 토큰 성분이 하나 이상이면 `model.response.usage`,
   primary/response. 0 도 유효한 보고다. 누락 성분은 null 이다.
4. 나머지는 `transport.stream.event`. 완료 이름만으로 사용량·성공·턴 완료를 만들지 않는다. 토큰이 전부
   파싱 불가능하면 `invalid_measurement` 를 남기고 primary 로 올리지 않는다.

`success` 는 bool 또는 프로파일이 허용한 정확한 문자열만 읽는다. `output_truncated` 를 실패로 읽지 않는다.

### A.4 스팬 허용 목록

허용 목록 밖의 스팬은 아카이브에만 남고 분석 테이블에 넣지 않으며, 버린 수를 센다(§2). 부모를 받지 못한
스팬이 root 라는 뜻은 아니고, status `unset` 은 성공이 아니다.

| 제품·원본 | `event_type` | 초기 처리 |
|---|---|---|
| Claude `claude_code.interaction` · `claude_code.llm_request` | `turn` · `model.request` | 시작·종료·상태·native trace/관계 ID. 보고 토큰이 있으면 diagnostic |
| Claude `claude_code.tool` · `claude_code.tool.execution` · `claude_code.tool.blocked_on_user` · `claude_code.hook` | `tool` · `tool.execution` · `tool.wait` · `hook` | 전체 시간·실행 시간·승인 대기·훅 시간을 각각 보존한다. 도구 이름은 사용자 지정 이름이 없는 producer 표기(`tool_name_safe`)를 쓴다 — 스팬의 `tool_name` 은 MCP 서버 이름을 그대로 싣는다 |
| Codex `session_task.turn` · `session_task.compact` · `try_run_sampling_request` | `turn` · `context.compaction` · `model.request` | 검증된 속성·구간. turn 토큰(`codex.turn.token_usage.*`, 턴 동안의 증분)은 `usage_scope = turn`, diagnostic 이며 response 사용량에 더하지 않는다. compaction 은 `workload_kind = compaction`. 턴 ID 는 `turn.id`·`turn_id` 두 표기이고 같을 때만 값이다. 작업 스팬의 `thread.id` 는 세션 ID 로 쓰지 않는다. 같은 작업 스팬 계열의 다른 이름(`session_task.review`·`session_task.user_shell` 등)은 허용 목록 밖이다 |
| Codex `mcp.tools.call`; 검증된 도구 스팬 프로파일 | `tool.execution`; `tool` | MCP 는 도구 call ID 의 출처를 보존한다 — Codex 의 `tool.call_id` 는 도구 결과 로그의 `call_id` 와 같은 호출 ID 라 같은 namespace 다. 일반 도구 프로파일은 도구 이름 + native call ID 등 확인된 필드 조건을 검사한다. 이름 모양만으로 도구 실행을 만들지 않는다 — Codex 의 일반 도구 스팬(`handle_tool_call` 등)은 그 필드를 싣지 않아 이 판에서 `tool` 행이 없다 |

### A.5 메트릭 family

이름은 family 후보를 찾는 단서이며 실제 wire 타입을 대체하지 않는다. 이름·family 가 같아도 타입·
temporality·단위·producer·차원 정의가 다르면 합치지 않는다. 모든 metric point 는 `usage_role` 이
diagnostic 또는 none 이다.

| 제품·원본 | `metric_family` | 초기 처리 |
|---|---|---|
| Claude `session.count` · `lines_of_code.count` · `pull_request.count` · `commit.count` | `session.started` · `code.lines.changed` · `scm.pull_request.created` · `scm.commit.created` | 실제 OTLP 타입·temporality·단위·라벨을 그대로 보존한다 |
| Claude `cost.usage` · `token.usage` · `code_edit_tool.decision` · `active_time.total` | `cost.reported` · `token.usage` · `tool.edit.decision.count` · `activity.active.duration` | 비용·토큰은 diagnostic 대조 계열이다. activity 는 턴 지연과 다른 시간량이다 |
| Codex `turn.token_usage` | `token.usage` | histogram count 는 관측 수, sum 은 성분 토큰 합이다. `usage_scope = interval`, diagnostic. 측정 대상이 턴이라는 사실은 `metric_profile`(`codex-v1/turn` — 제품·판·측정 대상)이 표현한다. `token_type` 의 `total`·`non_cached_input` 은 성분이 아니라 `token_component = unknown` 이다 |
| Codex `turn.tool.call` · `tool.call` · `tool.call.duration_ms` | `tool.calls.per_turn` · `tool.execution.count` · `tool.execution.duration` | count·sum 을 wire 타입에 따라 해석하고 `tool.result` 로그와 더하지 않는다 |
| Codex `turn.e2e_duration_ms` · `turn.ttft.duration_ms` · `turn.ttfm.duration_ms` | `turn.duration` · `turn.first_token` · `turn.first_item` | 서로 다른 관측량. canonical unit 은 검증된 registry 로만 부여한다 |
| Codex `thread.started` · `conversation.turn.count` | `conversation.started` · `conversation.turns` | Claude 세션 수와 구분한다 |
| Codex approval·MCP·hook·skill·multi-agent·task 계열 | 검증된 개별 이름의 family | 접두사 전체를 같은 KPI 로 올리지 않는다. 미등록이면 `vendor.metric` — 이 판에서 개별 등록한 이름은 없다 |
| Codex guardian·memory token usage 계열 | `token.usage`, `workload_kind` = `guardian`/`memory` | 명시된 관측 범위만 부여한다. 로그 대표 사용량과의 중복이 확인되지 않아 diagnostic. 등록한 이름: `guardian.review.token_usage`·`guardian_v2.classification.token_usage`(guardian) |
| 그 밖 모든 metric | `vendor.metric` | point 구조·원래 이름·단위·temporality·허용 차원을 generic 으로 보존한다. 의미 검증 전 KPI 밖 |

### A.6 품질 플래그

`quality_flags` 의 값이다. 한 행에 여럿이 올 수 있다. API 가 null 의 사유로 내는 코드(조회 계층의 어휘)와
다르다 — 이 표는 행 단위 사실만 담는다.

| 플래그 | 뜻 |
|---|---|
| `archive_receipt_missing` | archive receipt 가 없어 `archive_ref` 가 null 이다(§6) |
| `ambiguous_attribute` | 같은 키·alias 가 서로 다른 값·타입으로 와서 그 필드를 null 로 두었거나 `attrs` 에서 뺐다 |
| `ambiguous_payload` | 한 레코드에 서로 모순되는 의미 근거가 함께 있다(예: SSE 의 토큰 + 오류) |
| `invalid_measurement` | 측정 필드의 값이 허용 wire 타입·범위를 벗어나 그 필드를 null 로 두었다 |
| `derived_value_invalid` | 파생 토큰 계산이 overflow·음수·포함관계 위반이라 파생값을 null 로 두었다 |
| `usage_semantics_unverified` | 사용량 관측에 검증된 토큰 의미 프로파일이 없어 파생값을 계산하지 않았다 |
| `cost_conflict` | 같은 보고 비용의 두 표기가 프로파일의 정밀도를 넘어 어긋나 보고 금액을 null 로 두었다 |
| `non_finite_value` | 스칼라 metric 값이 NaN/±Infinity 라 `value_double` 을 null 로 두었다 |
| `provider_unresolved` | 사용량 관측에 검증된 공급자 근거가 없거나 근거끼리 충돌한다 |
| `event_time_mismatch` | 검증된 의미 속성의 시각이 `source_time` 과 다르다(§2) |
| `invalid_relation_id` | 선택 관계 ID(trace/span 등)가 형식에 맞지 않아 null 로 두었다 |
| `identity_material_masked` | 마스킹으로 식별 성분이 사라져 fingerprint 가 서로 다른 발생을 구분하지 못할 수 있다 |
| `member_unresolved` | 인증된 installation 으로 구성원을 조회하지 못했다(§5) |

## 부록 B. 최신 결과 선택과 사용량 조회 예시

작업 종류별 response 사용량의 팀별 일간 조회다. main 뿐 아니라 subagent·compaction·unknown 작업의 유효한
대표 사용량도 포함한다. 기간 경계는 `source_time` 기준 UTC 이고 일자 그룹은 tenant timezone 을 쓴다.
원본 input 합계를 서로 다른 의미 프로파일 사이의 같은 지표로 비교하지 않는다.

```sql
SELECT
    toDate(source_time, {tenant_timezone:String}) AS day,
    product, workload_kind, semantics_profile, input_semantics, output_semantics, reported_cost_basis,
    sumOrNull(tokens_input) AS input_reported_sum,
    countIf(isNotNull(tokens_input)) AS input_measured_reports,
    sumOrNull(tokens_output) AS output_reported_sum,
    countIf(isNotNull(tokens_output)) AS output_measured_reports,
    sumOrNull(tokens_total_derived) AS verified_total_sum,
    countIf(isNotNull(tokens_total_derived)) AS verified_total_reports,
    sumOrNull(cost_reported_usd) AS reported_usd,
    countIf(isNotNull(cost_reported_usd)) AS reported_cost_reports,
    sumOrNull(cost_estimated_usd) AS estimated_usd,
    countIf(isNotNull(cost_estimated_usd)) AS estimated_cost_reports,
    count() AS usage_reports
FROM telemetry_events FINAL
WHERE tenant_id = {tenant:String}
  AND source_time >= {from:DateTime64(9)}
  AND source_time < {to:DateTime64(9)}
  AND record_status = 'active'
  AND mapping_status = 'mapped'
  AND signal = 'log'
  AND event_type = 'model.response.usage'
  AND usage_role = 'primary'
  AND usage_scope = 'response'
  AND team_id_as_of = {team:String}
GROUP BY day, product, workload_kind, semantics_profile, input_semantics, output_semantics, reported_cost_basis
ORDER BY day, product
SETTINGS do_not_merge_across_partitions_select_final = 1
```

- 이 조회는 병합 전후와 중복 재전송에 같은 결과를 낸다. `FINAL` 없이 base table 을 합산하면 교체 전 행이
  섞인다.
- 기간 경계 `{from}`·`{to}` 는 조회 계층이 tenant timezone 의 자정을 UTC 로 바꿔 넣는다.
- 보고 비용과 추정 비용은 출처별 값이다. 더하지 않고 나란히 쓴다. 미보고는 측정 건수와 `usage_reports` 의
  차이로 함께 보인다.
- 미배분은 `team_id_as_of IS NULL` 로 같은 조회를 한다. 팀별 합과 미배분의 합이 조직 합계다.
- primary 프로파일이 확정되지 않은 관측은 diagnostic/none 이다. `usage_role` 을 최신 선택 전에 거르지
  않는다 — 위 조회의 조건은 전부 `FINAL` 뒤에 적용된다.

같은 범위의 제외량은 다음으로 센다. 모두 `FINAL` 뒤의 최신 행 기준이고 물리 행 수가 아니다.

```sql
SELECT
    count() AS latest_observations,
    countIf(record_status = 'excluded') AS excluded_observations,
    countIf(record_status = 'active' AND mapping_status != 'mapped') AS unmapped_active_observations,
    countIf(record_status = 'active' AND usage_role = 'primary' AND isNull(tokens_input)) AS primary_without_input,
    countIf(record_status = 'active' AND has(quality_flags, 'multi_team_membership')) AS multi_team_observations
FROM telemetry_events FINAL
WHERE tenant_id = {tenant:String}
  AND source_time >= {from:DateTime64(9)}
  AND source_time < {to:DateTime64(9)}
SETTINGS do_not_merge_across_partitions_select_final = 1
```
