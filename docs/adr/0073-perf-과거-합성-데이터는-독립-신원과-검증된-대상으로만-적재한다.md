# 0073. perf 과거 합성 데이터는 독립 신원과 검증된 대상으로만 적재한다

## Status

Proposed — PROJ-295 구현 계약. 실제 환경 적용과 대표 데이터 규모의 승인은 별도다.

## Context

기존 `historical-plan`과 `historical_seed.py`는 local/dev의 soma 화면 데이터를 생성하고 직접 적재한다.
perf 준비에 dev artifact나 DB를 복제하면 신원·로그인 설정과 기존 자료가 섞인다. 환경 라벨만 perf로
바꾸는 입력도 실제 접속 대상이 격리 환경이라는 증거가 되지 않는다.

교차 저장소의 환경·실행 조건은 [허브 ADR 0029](https://github.com/soma-376/docs/blob/main/adr/0029-perf-strimzi-readiness-and-path-comparison.md)가 정한다.
이 ADR은 backend의 기존 생성기와 importer가 그 경계를 검증하는 방법을 정한다.

## Decision

- local/dev의 기존 파일·ID·OIDC·속도·보존 경계·검증 계약을 유지한다. prod, DB migration,
  전체 reset과 삭제는 지원하지 않는다.
- perf는 명시적인 `perfEnvironmentId`를 UUID 영역·조직 slug·합성 이메일에 포함한다. 기존 합성
  생성 규칙으로 새 파일을 만들며 dev DB·artifact·credential을 복제하지 않는다.
- perf의 OIDC 연결과 회원 subject는 비우고 SSO 및 모든 알림 규칙은 끈다. `activate-login`은
  DB 접속 전에 거부한다. 검증·재개도 활성 상태를 허용하지 않는다.
- perf manifest는 합성 provenance와 `representativeness=INCONCLUSIVE`를 기록한다. 기존 rich
  프로필·180일·400명·50팀·398설치의 고정 생성량을 초기 기준으로 사용하며 운영 동등성은 별도 검증한다.
  실제 기간·초기 상태는 실행 명세에 고정한다. local/dev의 team-daily는 유지한다.
- perf target은 v3 resolved와 실제 적용 profile 및 원천 조회 증거의 SHA-256을 필수로 참조한다. 환경 ID,
  접속 대상과 PostgreSQL/ClickHouse 서버 identity가 모두 일치해야 한다. 증거가 없으면 DB에
  접속하지 않으며, 실제 identity가 다르면 쓰기 전에 중단한다. 이 파일은 자동 환경 조회나 승인
  시스템이 아니므로 운영자는 격리 환경에서 수집한 원천 증거의 출처를 확인한다. 증거 파일 자체가
  writer 권한이나 실행 승인을 부여하지 않는다.
- 두 DB의 원자적 commit은 없으므로 기존 파일·checkpoint·잠금·제한 속도·압력 감시·retention
  fence·물리 중복과 전체 생성 필드 대조를 유지한다. 직접 적재는 OTLP·Kafka·S3 성공 증거가 아니다.

## Alternatives Considered

dev DB 복제는 기존 사용자·인증·캐시·데이터를 옮기므로 채택하지 않는다. local 가드를 꺼서 perf에
접속하거나 URL 이름에 perf가 들어가는지만 검사하는 방법도 대상 검증을 대체하지 못한다.

## Consequences/Tradeoffs

### Positive

기존 dev 데이터를 보존하면서 동일한 합성 생성 규칙을 격리 환경에서 재현한다. 잘못된 대상과
불완전한 관측을 실패로 남기고, 로그인·알림의 부수 효과를 막는다.

### Negative

대상 identity와 원천 증거를 별도로 준비해야 한다. 서버 재생성으로 identity가 바뀌면 기존
checkpoint로 자동 재개할 수 없다. 고정된 합성 프로필은 운영의 tenant 편향이나 저장량을 보장하지 않는다.

## Follow-up

운영 동등성, 격리 perf의 실제 적재·저장 검증, ALB/내부 경로 시험은 별도 실행 조건이다.
DB 연결 예산과 기준선(B07)은 이 변경 범위에 포함하지 않는다.
