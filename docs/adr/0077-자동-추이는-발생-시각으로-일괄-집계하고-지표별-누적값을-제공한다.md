# 0077. 자동 추이는 발생 시각으로 일괄 집계하고 지표별 누적값을 제공한다.

## Status

Accepted

## Context

PROJ-317은 개요·팀 목록·팀 상세에 자동 시간 버킷을 추가한다. 일별 합계로는 실제 시간대별 사용량과 세션의 최초 관측을 복원할 수 없다. 버킷·팀마다 쿼리를 실행하면 최대 60개 버킷과 팀 수에 비례해 비용이 늘어난다.

제품·레포 간 정책은 허브 ADR 0031이 소유한다. 이 ADR은 dashboard-api의 집계·snapshot·누적 계산 구현을 정한다. ADR 0042의 기존 일별 관측 정책은 변경하지 않으며 그 정책 개정은 PROJ-315가 소유한다.

## Decision

### 1. 공통 버킷 계획을 사용한다

`TrendBucketPlan`이 KST 날짜 범위, 조회 시작에 고정된 버킷, 후보 간격 선택, 마지막 종료 절단, `elapsed|in_progress|upcoming`을 계산한다. 1시간·3시간·6시간·12시간·1일·3일·7일 중 최대 60개를 만족하는 가장 작은 간격을 선택한다. 최대 조회 366일과 오늘 전체 24개 구간을 유지한다.

버킷은 반개구간이다. `bucketEnd ≤ asOf`는 elapsed, `bucketStart ≤ asOf < bucketEnd`는 in_progress, 그 뒤는 upcoming이다. 기존 `snapshot_usage.source_time`의 정밀도를 사용하며 원본 스키마·일별 테이블을 추가하지 않는다.

### 2. 자동 입력은 별도 snapshot 계약으로 고정한다

자동 모드는 기존 `query_contract`에 `dashboard-auto-trend-v1`, 일별 모드는 기존 `dashboard-v7`을 사용한다. 새 DB 컬럼을 추가하지 않는다. 자동 snapshot을 생성할 때 현재·비교 기간의 사용량과 관측 metadata를 같은 원본 선택 결과에서 만들며 `source_time < snapshot.asOf`를 적용한다.

`asOf`는 발생 시각 상한이다. 수신 시각 기준 과거 상태를 재현하는 기능이 아니다. 합계·자동 추이·상세·사용자·CSV는 이 입력을 함께 읽는다. 명시적 또는 기본 일별 요청에 자동 snapshot을 넘기는 등 계약이 다르거나 만료되면 기존 409 재조회 흐름을 사용한다. 팀 사용자 API는 bucket 옵션 없이 전달받은 snapshot의 모드를 계승한다.

### 3. 모든 팀과 버킷을 일괄 집계한다

비용·토큰은 기간 전체를 한 번에 조회 시작부터의 경과 시간으로 그룹화한다. 세션 최초 관측도 전체 팀·기간을 한 번에 조회한다. 버킷별·팀별 반복 SQL을 추가하지 않는다. 원천에는 읽기만 하고 snapshot 생성·갱신은 기존 자기 cache 안에서 수행한다.

누적 시 금액·토큰 성분·각 결손 카운터를 합하고 토큰 의미 호환 그룹은 집합 합집합으로 관리한다. 버킷별 distinct 수나 `UsageTotals` 전체를 단순 합산하지 않는다. 세션 키는 `(팀, product, session namespace, session ID)`이며 첫 관측 버킷에서만 증가한다. 미배정과 팀 변경도 이벤트의 팀 기준으로 처리한다.

### 4. 자동 누적 지표를 별도 DTO로 제공한다

개요 자동 추이는 `bucket=auto`이며 `equivalentCostUsd`, `knownEquivalentCostUsd`, `totalTokens`를 각 버킷의 `Value<T>`로 반환한다. 팀 자동 추이는 `cumulativeEquivalentCostUsd`, `cumulativeKnownEquivalentCostUsd`, `cumulativeTotalTokens`, `cumulativeSessionCount`를 각각 `Value<T>`로 반환한다. 일별 DTO는 유지한다.

공통 `meta.trendAggregation`은 mode, intervalSeconds, valueMode, rangeStart, rangeEnd, asOf를 제공한다. 개요 valueMode는 interval, 팀은 cumulative다. 각 point의 bucketStart·bucketEnd·temporalState 외에 `usageRows`는 항상 해당 버킷의 비누적 행 수다. 팀 pricedUsageRows·unpricedUsageRows는 누적 범위이고 미래에는 null이다.

금액은 Decimal로 계산한 문자열이다. 명시적 0과 기록 없음은 구별한다. 중간 빈 버킷은 이미 확인한 누적값을 유지하고 전 기간에 기록이 없으면 0을 만들지 않는다. 미래 지표는 null·unavailable·upcoming 사유이며 usageRows·pricedUsageRows·unpricedUsageRows도 null이다.

각 누적 지표의 결손은 기간 합계와 같은 의미 규칙으로 판단한다. 미환산·필수 토큰 성분 결손·비호환 의미는 해당 지표 범위에 반영하고 뒤의 정상 버킷으로 지우지 않는다. 세션 ID 결손은 정상 비용·토큰의 값이나 상태에 전파하지 않는다. 기존 세션 집계·API·검증을 유지한다.

### 5. 수집 annotation과 활성화 gate를 분리한다

일별 완전성을 시간 버킷에 복제하지 않는다. 확인된 사용값은 지표별 근거로 제공하고 수집 상태는 PROJ-315 공통 annotation을 통해 별도로 전달한다. 공통 계약은 snapshot에 고정된 정책 버전·기준 시각·영향 범위·사유·근거 참조이며 범위를 특정할 수 없으면 기간 수준에 남긴다. 원천 계약 연결 전 meta.collectionPolicy는 policyVersion=proj-315-pending·status=pending과 policy_integration_pending 기간 annotation을 반환한다. adapter는 고정된 snapshot 값만 입력받으며 수집 완전성을 임의로 판정하지 않는다.

PROJ-316의 168시간 페이로드 손실을 source_time 버킷·팀·토큰·이벤트로 배분하지 않는다. 정확한 영향을 모르면 수집 상태 안내로만 연결한다. PROJ-315 계약·통합 검증이 완료되기 전 사용자 frontend의 `NEXT_PUBLIC_AUTO_TREND_ENABLED`는 기본 false를 유지한다.

## Alternatives Considered

### A. 일별 결과를 버킷에 나눈다
- 장점: 일별 SQL을 재사용한다.
- 단점: 실제 발생 시간과 세션 범위를 복원할 수 없다.
- 탈락 이유: 근거 없는 시간대별 값이 생긴다.

### B. 버킷마다 기간 합계를 다시 조회한다
- 장점: 기존 기간 집계를 호출하기 쉽다.
- 단점: 팀·버킷 수에 비례하는 쿼리와 중복 연산이 발생한다.
- 탈락 이유: 전체 기간 일괄 집계와 별도 누적이 같은 의미를 더 적은 조회로 보장한다.

## Consequences/Tradeoffs

### Positive
- snapshot 입력·합계·자동 추이·상세가 같은 발생 시각 상한을 공유한다.
- 지표별 결손과 고유 세션 누적을 독립적으로 검증할 수 있다.

### Negative
- 일별/자동 query_contract와 DTO의 호환 회귀가 필요하다.
- PROJ-315의 공통 annotation과 사용자 활성화 검증은 별도 작업으로 남는다.

## Follow-up

- PROJ-315 공통 원천 계약을 연결하고 동일 snapshot·영향 범위·근거 참조의 통합 fixture를 검증한다.

## Acceptance Criteria

- 1·2·3·7·8·15·16·30·31·60·61·180·181·366일 및 KST 경계·마지막 구간·asOf 정각 제외를 검사한다.
- 과거 마지막 버킷 또는 오늘의 마지막 미도래 전 버킷의 누적값이 기간 합계와 일치한다. 미환산 때는 확인된 부분합도 별도로 대조한다.
- 세션 중복·product/namespace·미배정·팀 변경·ID 결손, 지표별 상태, 일별 회귀, snapshot 불일치 409와 쿼리 수 상한을 검증한다.
