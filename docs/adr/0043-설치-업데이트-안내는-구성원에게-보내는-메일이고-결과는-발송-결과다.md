# 0043. 설치 업데이트 안내는 구성원에게 보내는 메일이고 결과는 발송 결과다

## Status

Proposed — [ADR 0039](0039-비동기-작업은-공통-작업-기록에-남기고-상태-조회는-dashboard-api가-한다.md)(작업 기록)와
[ADR 0040](0040-설치-보고는-최신-상태-한-행과-수집-구간-이력으로-저장한다.md)(설치 보고의 저장)이 Accepted가 되면 Accepted.
안내가 작업 기록의 첫 생산자이고, 적용 현황의 근거가 설치 보고다.
메일 본문의 확인 절차는 [ADR 0053](0053-데몬에-기대는-서버-동작은-telemetryctl-기본-브랜치의-구현만-전제한다.md)이 개정한다 — telemetryctl 기본 브랜치에는 `pulsemetry login`·설치 보고 송신·재조회가 없다.

## Context

설정 화면은 수집 정책의 적용 현황과 설치 목록을 보여 주고, 아직 새 정책을 적용하지 않은 설치에 "업데이트 안내"를 보낼 수 있게 하려 한다.
화면 요청서의 타입은 다음과 같다(`SettingsResponses.kt`).

- `policyRollout`: 활성 판, 대상 설치 수와 적용·미적용·미확인 수.
- `InstallationRow`: `appliedPolicyVersion`, `lastHeartbeatAt`, `canNotify`.
- `capabilities.notifyInstallations`: 안내를 보낼 수 있는 배포인가.
- 안내 요청 `{installationIds, expectedPolicyVersion}` → 202와 작업 상태(`OperationResponse`). 채널이 없으면 `notifyInstallations=false`와 422 `notification_channel_unavailable`.

지금까지의 구현과 사실:

- 설치 보고(ADR 0040)가 설치마다 마지막 보고 한 행(`installation_heartbeats`)을 남긴다. 그 행의 `applied_manifest_id`가 설치가 **지금 집행하는** 판이다.
  보고한 판이 그 조직의 manifest면 `installation_manifest_assignments.applied_at`에 그 판을 처음 보고받은 시각을 남긴다 — 그 판을 적용한 **적이 있다**는 이력이다.
- enroll과 정책 저장은 `applied_at`을 채우지 않는다. 적용 확인은 보고로만 생긴다.
- 대시보드 설치 조회는 `applied_at`이 있는 판 중 가장 높은 판을 적용 판으로 읽었고, `lastHeartbeatAt`은 null 고정, `canNotify`는 false 고정이었다. 필터는 `outdated` 하나였다.
- 서버는 설치에 정책을 밀어 넣을 수단이 없다. 설치는 설치 보고의 응답이 새 판을 알릴 때, 사용자 로그인 세션이 있으면 스스로 manifest를 다시 받아 적용하고 보고한다.
  세션이 없거나 잃었으면 데몬은 "로그인 필요"를 표시하고 적용하지 않는다(`pulsemetry status`).
- 서버가 사람에게 닿는 경로는 메일뿐이다. 메일은 outbox에 적재하고 enrollment-api의 발송 작업이 SMTP로 보낸다(ADR 0037). 메일 기능이 꺼진 배포가 있다.
- 비동기 명령의 결과는 공통 작업 기록(ADR 0039)에 대상별로 남기고 dashboard-api가 조회한다. 이 기록을 만드는 명령은 아직 없다.
- dashboard-api는 메일을 보내지 않고 enrollment-api의 설정을 읽지 않는다.

정하지 않으면 생기는 일: "안내"가 원격 업데이트처럼 읽히면 관리자는 안내 성공을 적용 완료로 오해한다. 적용 판을 적용 이력의 최댓값으로 읽으면 뒤로 돌아간 설치가
적용 완료로 보인다. 채널이 없는 배포에서 요청을 받아 두면 아무 일도 일어나지 않는 "접수"가 생긴다.

## Decision

### 지금 집행하는 판

설치의 적용 판은 **지금 집행하는 판**이다(`AppliedPolicyVersion`).

- 설치 보고가 있으면 마지막 보고가 말한 판이다. 그 조직이 모르는 판을 보고했으면 없다(확인 불가).
- 보고가 없으면 적용 확인 기록 중 가장 높은 판이다(보고가 생기기 전에 들어온 기록).

적용 상태는 지금 판이 활성 판 이상이면 `applied`, 낮으면 `outdated`, 없으면 `unknown`이다. 보고가 없는 설치를 적용 완료로 추정하지 않는다.
설정의 `policyRollout`, 설치 목록의 `appliedPolicyVersion`·필터(`policyStatus=applied|outdated|unknown`), 안내의 대상 확인이 **같은 식**을 쓴다.
`lastHeartbeatAt`은 마지막 설치 보고를 받은 서버 시각이다. 데이터 수신 시각을 넣지 않는다.

### 안내

- **안내는 설치를 쓰는 구성원에게 보내는 메일이다.** 원격 업데이트나 정책 배포가 아니다. 메일은 새 판이 있다는 사실과 확인 절차
  (`pulsemetry status`로 상태를 보고, 로그인이 필요하다고 나오면 `pulsemetry login`, 데몬이 멈췄으면 다시 띄우기)를 싣고,
  원격으로 아무것도 바꾸지 않는다고 적는다. 기기 이름·플랫폼·기대 판·지금 판을 싣고 비밀은 싣지 않는다.
- **채널이 없으면 받지 않는다.** enrollment-api의 메일 기능이 꺼져 있으면 422 `notification_channel_unavailable`이다.
  dashboard-api는 관리 기능과 메일 기능이 모두 켜진 배포에서만 `capabilities.notifyInstallations=true`다. 두 앱은 `pulsemetry.mail.enabled`에 같은 값을 받는다.
- **대상은 모두 확인한 뒤에만 보낸다.** 기대 판이 지금 활성 판이 아니면 409 `version_conflict`, 이 조직의 설치가 아니면 404,
  폐기된 설치·구성원이 활성이 아닌 설치·이미 기대 판을 집행하는 설치가 있으면 409 `installation_unavailable`이다. 하나라도 걸리면 작업도 메일도 만들지 않는다.
  `canNotify`는 이 조건을 미리 계산한 값이다(채널이 있고, 구성원이 활성이고, `applied`가 아닌 설치).
- **안내 한 번이 작업 하나다.** 작업 종류는 `installation_notification`, 대상 ID는 설치 ID다. 작업·메일 적재·멱등 기록은 한 트랜잭션이다.
  응답은 202와 작업 상태이고 `Location`이 dashboard-api의 작업 상태 조회다. 같은 멱등 키의 재시도는 같은 작업이고, 새 키는 새 안내다.
- **대상의 결과는 메일의 발송 결과다.** 메일 발송 작업이 한 바퀴 돈 뒤 끝난 메일을 대상 결과로 옮긴다.
  `sent` → `succeeded`, `failed` → `failed`(메일의 실패 분류 코드), `cancelled` → `failed`(`cancelled`). 재시도 대기 중인 메일의 대상은 `pending`이다.
  `succeeded`는 SMTP 서버가 받았다는 뜻이다. 설치가 새 판을 적용했는지는 적용 상태로 다시 확인한다.

## Alternatives Considered

### A. 안내를 설치에 직접 보낸다(설치 보고의 응답에 "다시 받아라"를 싣는다)
- 장점: 사람을 거치지 않는다.
- 단점: 설치 보고의 응답은 이미 새 판을 알린다. 그래도 적용하지 않는 설치는 로그인 세션이 없거나 데몬이 멈춘 설치라 같은 신호를 한 번 더 보내도 달라지지 않는다.
- 탈락 이유: 막힌 곳이 사람의 로그인이다. 사람에게 닿아야 한다.

### B. 안내의 결과를 설치의 적용으로 둔다(적용 보고가 오면 성공)
- 장점: 관리자가 원하는 결과와 같다.
- 단점: 작업이 사람의 행동을 무기한 기다린다. 메일이 거절된 것과 사람이 아직 로그인하지 않은 것이 구분되지 않는다.
- 탈락 이유: 작업은 시스템이 끝낼 수 있는 일의 결과다. 적용은 이미 적용 상태가 보여 준다.

### C. 채널이 없어도 받아 두고 나중에 보낸다
- 장점: 요청이 실패하지 않는다.
- 단점: 메일을 켜지 않는 배포에서는 영원히 나가지 않는 "접수"가 쌓인다.
- 탈락 이유: 보낼 수 없는 것을 접수한 척하지 않는다.

### D. 적용 판을 적용 확인 이력의 최댓값으로 둔다(지금까지의 방식)
- 장점: 표 하나만 읽는다.
- 단점: 새 판을 적용했다가 앞 판으로 돌아간 설치(상태 복원, 재설치)가 적용 완료로 남는다. 모르는 판을 보고하는 설치도 적용 완료로 보인다.
- 탈락 이유: 적용 확인은 이력이고 지금 상태는 마지막 보고다.

## Consequences/Tradeoffs

### Positive
- 적용 현황·목록·필터·안내 대상 확인이 한 규칙을 쓴다. 뒤로 돌아간 설치가 미적용으로 보인다.
- 안내의 결과가 시스템이 확인할 수 있는 사실(발송)이라 작업이 끝난다. 거절된 주소가 대상별로 보인다.
- 채널이 없는 배포는 버튼이 꺼지고 요청은 422라, 아무 일도 일어나지 않는 접수가 없다.
- 공통 작업 기록의 첫 생산자가 생긴다.

### Negative
- 안내가 성공해도 설치가 적용했다는 뜻이 아니다. 화면이 두 사실을 따로 보여 줘야 한다.
- 메일은 구성원 계정의 주소로 간다. 한 사람의 여러 설치를 안내하면 메일이 설치 수만큼 간다.
- 대상 결과는 메일 발송 주기만큼 늦게 채워진다.
- dashboard-api가 enrollment-api의 메일 설정과 같은 값을 따로 받는다. 두 값이 어긋나면 버튼과 요청 결과가 다르다(요청은 422로 안전하게 실패한다).
- 보고가 없는 설치의 적용 판은 적용 확인 기록을 쓴다. 그 기록은 보고로만 생기므로 실제로는 보고가 생기기 전 데이터에만 해당한다.

## Follow-up
- 화면이 적용 상태·마지막 보고 시각·안내 버튼과 작업 상태를 표시한다.
- 한 구성원의 여러 설치를 메일 한 통으로 묶을지는 사용 데이터를 보고 정한다.
