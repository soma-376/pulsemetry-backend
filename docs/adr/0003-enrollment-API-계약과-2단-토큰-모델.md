# 0003. enrollment API 계약을 클라이언트에 맞추고 자격증명을 2단으로 나눈다.

## Status
Accepted

## Context
데스크탑 CLI(`telemetryctl`, Go)는 이미 완성되어 배포를 앞두고 있다.
클라이언트는 enroll 응답을 `encoding/json` 의 `DisallowUnknownFields` 로 파싱하며,
이 설정은 **중첩된 manifest 객체까지 적용된다.** 응답에 계약에 없는 필드가 하나라도 있으면
설치가 그 자리에서 실패하고, 사용자는 원인을 알 수 없는 오류 메시지를 본다.

즉 서버가 "도움이 될 것 같아서" 필드를 하나 더 붙이는 순간 모든 설치가 깨진다.
계약의 진실원은 `telemetryctl/contracts` 의 JSON Schema 파일과
`telemetryctl/internal/contract` 의 Go 구조체다.

한편 설치된 클라이언트는 두 종류의 비밀을 다룬다.
하나는 이 설치가 누구인지 증명하는 장기 자격증명이고,
다른 하나는 Codex·Claude Code 의 OTLP exporter 설정(`OTEL_EXPORTER_OTLP_HEADERS`)에
평문으로 들어가 텔레메트리 전송에 쓰이는 토큰이다.
후자는 사용자 홈 디렉터리의 설정 파일에 남고, 로그·프로세스 목록·스크린 공유로 노출될 여지가 크다.

> **각주 (현재 구조)** — 위 문단은 결정 당시의 클라이언트 서술이다. 이후 클라이언트 실구현에서는
> enroll 이 로컬 파이프라인을 자동 배선해 벤더 설정에는 **로컬 ingest 토큰**만 들어가고,
> 회사 `ptt_` 는 OS 키링에 저장되어 데몬이 상위 전송 시 `Authorization` 헤더에 주입한다
> (현재 구조의 정본은 스펙 §4.3). 노출면이 줄었을 뿐, 노출 가능성이 높은 값과 신원을 나누고
> 유출 시 재발급 한 번으로 무효화한다는 이 결정의 근거는 그대로 성립한다 — 설계 변경이 아니다.

## Decision
- **계약은 클라이언트가 확정하고 서버가 거기에 맞춘다.** 서버가 계약을 만족하지 못하면 서버를 고친다.
  `telemetryctl` 의 Go 코드와 스키마 파일은 이 저장소에서 읽기 전용으로 취급한다.
- 계약 테스트가 서버의 직렬화 결과를 `telemetryctl/contracts` 의 스키마 파일 **원본**으로 검증한다.
  스키마를 이 저장소로 복사하지 않는다.
- `POST /v1/enroll` 응답 봉투는 `installation_id`·`installation_token`·`telemetry_token`·`manifest`
  **정확히 네 필드**다. 요청 역직렬화는 `FAIL_ON_UNKNOWN_PROPERTIES=true` 로 두어
  계약에 없는 필드를 400 `invalid_request` 로 거절한다.
- 자격증명을 2단으로 나눈다.
  - `installation_token` (`pit_` 접두사): 장기 신원. OS 키링에만 저장되며 서버 재발급 요청에만 쓰인다.
  - `telemetry_token` (`ptt_` 접두사): OTLP 헤더에 실리는 교체 가능한 토큰.
    `POST /v1/installations/telemetry-token` 으로 언제든 재발급할 수 있고,
    재발급하면 그 installation 의 기존 활성 토큰이 **전부** 폐기된다.
- 두 토큰과 초대 코드는 원본을 저장하지 않고 SHA-256 해시만 DB 에 넣는다.
  유니크 인덱스로 조회해야 하므로 해시는 결정론적이어야 한다.
- `installation_id` 와 토큰은 manifest **밖**, 봉투 상위에 둔다(봉투 분리).

## Alternatives
### A. 서버가 계약을 정의하고 클라이언트를 맞추게 한다
- 장점: 서버 구현의 자유도가 높다. 응답에 진단용 필드를 자유롭게 추가할 수 있고, 스키마 변경을 서버 일정에 맞춰 진행할 수 있다.
- 단점: 이미 배포 준비가 끝난 Go 클라이언트를 다시 빌드·배포해야 한다. 사용자 PC 에 이미 설치된 구버전 클라이언트는 서버 변경과 동시에 깨진다.
- 탈락 이유: 클라이언트가 먼저 완성됐고 사용자 PC 에서 도는 소프트웨어라 롤백이 사실상 불가능하다. 계약을 바꿀 권한은 나중에 배포되는 쪽이 아니라 이미 배포된 쪽이 갖는 것이 안전하다.

### B. 토큰을 하나로 합친다
- 장점: 발급·저장·검증 경로가 하나뿐이라 구현과 운영이 단순하다. 테이블도 하나 줄어든다.
- 단점: 그 하나의 토큰이 OTLP 헤더로 설정 파일에 평문 저장된다. 유출되면 텔레메트리 위조뿐 아니라 installation 자체를 사칭할 수 있고, 폐기하면 사용자가 재설치해야 한다.
- 탈락 이유: 노출 가능성이 높은 값과 신원을 증명하는 값의 수명이 같아진다. 텔레메트리 토큰은 유출을 전제로 자주 교체할 수 있어야 하는데, 합치면 교체 비용이 재설치가 된다.

### C. JWT 로 상태 없는 토큰을 만든다
- 장점: 서버가 토큰 저장소를 두지 않아도 되고 검증이 로컬에서 끝난다. 수평 확장에 유리하다.
- 단점: 발급 후 폐기가 어렵다. 폐기 목록을 두면 결국 상태를 갖게 되어 이점이 사라진다. 서명 키 회전 절차도 추가로 필요하다.
- 탈락 이유: 이 API 의 핵심 동작이 **폐기**다. installation 폐기, 토큰 교체, 초대 코드 일회성 소비가 전부 상태 변경이라 상태 없는 토큰의 이점이 나오지 않는다.

## Consequences/Tradeoffs
### Positive
- 계약 위반이 배포 후 사용자 PC 가 아니라 CI 의 계약 테스트에서 드러난다.
- 응답 필드를 늘리고 싶은 충동이 타입과 테스트로 막힌다. `manifest` DTO 에는 봉투 필드를 넣을 자리가 없다.
- telemetry token 이 유출돼도 재발급 한 번으로 무효화되며, 사용자는 재설치하지 않아도 된다.
- DB 가 유출돼도 해시만 있으므로 토큰과 초대 코드를 복원할 수 없다.
- 초대 코드의 원본이 서버 어디에도 남지 않으므로, 코드 유출 경로가 발급 응답 한 번으로 제한된다.

### Negative
- 클라이언트 계약이 바뀌면 서버가 따라가야 하며, 그 순서를 뒤집을 수 없다.
- 계약 테스트가 `telemetryctl` 저장소에 의존한다. CI 는 두 저장소를 함께 체크아웃해야 한다.
- 토큰이 두 종류라 테이블과 발급 경로가 각각 필요하고, 어느 토큰을 어디에 쓰는지 문서로 계속 설명해야 한다.
- 해시가 결정론적이어야 해서 bcrypt·Argon2 같은 salted KDF 를 쓸 수 없다.
  - 원본이 고엔트로피 난수(토큰 256비트, 초대 코드 60비트)라 사전 공격 대상이 아니라는 전제 위에 서 있다.
    사람이 고른 값에는 이 방식을 쓸 수 없다.

## Follow-up
- 초대 코드 원본을 다시 볼 수 있는 API 를 만들지 않는다. 관리자가 발급 응답을 잃으면 새로 발급한다.
- `GET /v1/manifest` 같은 설정 재조회 API 를 추가할 때도 봉투 분리를 유지한다.
  재조회 응답에는 토큰을 싣지 않는다.
  - **ADR 0007 로 일부 대체됨** — 재동기화 응답이 새 AT·RT 를 함께 내려준다. 토큰은 봉투 상위에 동봉한다.
    다만 **manifest 안에는 토큰을 넣지 않는다**는 원칙은 양쪽 모두 그대로 유지된다.
- 웹 대시보드가 생기면 관리자 인증을 정적 키에서 Cognito 로 옮긴다(ADR 별도 작성).
